# 키워드 추출 비교: 새 정답셋 100 (파인튜닝 GLiNER vs LLM)

- 작성일: 2026-11-04
- 질문: 파인튜닝 GLiNER가 **학습 때 한 번도 보지 못한 의료 컨셉**에서도 LLM만큼 키워드를 뽑는가
- 비교 대상: [09](09_키워드%20추출%20비교%20(파인튜닝%20GLiNER%20vs%20LLM).md)·[10](10_키워드%20추출%20비교%20—%20패러프레이즈%20573%20(파인튜닝%20GLiNER%20vs%20LLM).md)과 같은 파인튜닝 GLiNER(threshold 0.5)와 LLM
- 테스트셋: 이번에 새로 만든 100문장(N001~N100). **정답 의료 컨셉 227개가 모두 학습 데이터에 없다**(2절). 문장마다 사람이 정답을 검토해 확정했다
- 왜 새로 만들었나: 50문장 셋(09)은 정답 컨셉의 42%가, 패러프레이즈 셋(10)은 94%가 학습 데이터에 있었다. 10에서 처음 보는 컨셉의 재현율이 77.5%로 떨어졌지만 표본이 40개뿐이었다

## 요약

|---|---|---|---|
| 의료 컨셉 키워드 | 재현율 (227개) | 83.7 | **100.0** |
| 의료 컨셉 키워드 | F1 | 88.0 | **97.6** |

| 응답 속도 | 평균 / 중앙값 | **0.47초 / 0.45초** | 0.97초 / 0.88초 |

세 셋을 나란히 놓으면 다음과 같다.

| 지표 | 50문장 (09) | 패러프레이즈 573 (10) | **새 100 (11)** |
|---|---|---|---|
| 정답 컨셉 중 학습 데이터에 있는 비율 | 42% | 94% | **0%** |
| 의료 컨셉 재현율: 파인튜닝 GLiNER / LLM | 90.1 / 98.8 | 95.4 / 99.2 | **83.7 / 100.0** |
| 의료 컨셉 F1: 파인튜닝 GLiNER / LLM | 92.4 / 94.7 | 97.2 / 94.3 | **88.0 / 97.6** |
| 스키마 F1 (겹침 인정): 파인튜닝 GLiNER / LLM | 87.9 / 85.8 | — (정답 없음) | **83.5 / 82.9** |
| 방문 유형·성별: 파인튜닝 GLiNER / LLM | 18 / 16 (23개) | 25 / 23 (25개) | **22 / 27 (30개)** |
| 다운스트림 추론 포함 커버리지: 파인튜닝 GLiNER / LLM | 80% / 90% | 94.6% / 98.8% | **67% / 99%** |

**결론.** 학습 데이터에 없는 컨셉에서는 파인튜닝 GLiNER가 LLM보다 확실히 떨어진다.
1. **의료 컨셉을 6개 중 1개꼴로 놓친다** (37 / 227). LLM은 하나도 놓치지 않았다. 학습 데이터와 겹칠수록 점수가 높았던 흐름(94% 겹침 95.4 → 42% 겹침 90.1 → 0% 겹침 83.7)이 그대로 이어진다.
2. **가장 약한 곳은 시술명이다** (27 / 45, 60%). 영문 약어(TAVI, CABG, ECMO, CRRT, ERCP, CPR), 중환자 처치(기계환기, 기관 삽관), 이식(간이식, 신장이식), 영상(심초음파, 복부 초음파)이다. 09에서도 시술명이 약점(5 / 9)이었는데, 이번 셋에서 더 분명해졌다.
3. **라벨도 틀린다** (11개, LLM 0개). 심초음파·복부 초음파·허리둘레·심박수·세프트리악손을 진단명으로 붙였다. 이 때문에 다운스트림 추론으로 정하는 테이블도 틀어진다.
4. 그 결과 **SQL에 필요한 테이블을 다 가리킨 문장이 67%** 뿐이다(LLM 99%). 엔진 입장에서는 이 차이가 가장 크다.
5. **스키마 키워드는 LLM과 비슷하고, 속도는 여전히 2배 빠르다.** 스키마 단어는 종류가 정해져 있어 학습 데이터와 겹치기 때문이다(2절).

그래서 파인튜닝 GLiNER를 LLM 대신 쓰려면 **처음 보는 의료 컨셉, 특히 시술명의 일반화를 먼저 올려야 한다**(6절).

## 1. 테스트 조건

- **파인튜닝 GLiNER:** 09 1.1절과 같다. `POST <파인튜닝 서버>/keyword-extraction/llm-compat`, threshold 0.5, 사내 서버 CPU, 순차 호출.
- **LLM:** 09 1.2절과 같은 모델·프롬프트(sha256 `1bb9b021…`), temperature 0, thinking 끔, **순차 호출**.
- 두 모델을 같은 시간대에 함께 돌렸다. 실패는 둘 다 0 / 100.
- 채점은 09·10과 같은 채점기(`eval.csv_keyword_eval score`)다. 방문 유형·성별은 llm-compat 형식에서 스키마 항목으로 오기 때문에 10과 같은 방식으로 따로 셌다.

## 2. 정답셋

### 2.1 만든 방법

- Claude가 문장과 정답 초안을 만들고, 사람이 문장마다 검토해 확정했다(2026-11-04).
- 정답 형식과 열은 50문장 셋과 같다. 판단 근거는 CSV의 `note` 열에 남겼다.
- 파일: `test_set/keyword_ext/kw100/` (정답 CSV, 원본 `build.py`, 정답 규칙을 적은 README, 검토 목록)

### 2.2 학습 데이터와의 겹침

| 항목 | 결과 |
|---|---|
| 정답 의료 컨셉 227개 중 학습 데이터 정답 span에 있는 것 | **0** |
| 학습 문장에 그대로 나오는 것 | 0 |
| 학습 컨셉(3글자 이상)을 안에 포함하는 것 | 0 |
| 학습 문장과의 4글자 단위 유사도 | 중앙값 0.02, 최대 0.23 |
| 50문장 셋과의 4글자 단위 유사도 | 최대 0.25 |

- 스키마 단어(환자, 진단, 처방…)와 방문 유형·성별 단어(입원, 외래, 여성…)는 종류가 정해져 있어 학습 데이터와 겹칠 수밖에 없다. 그래서 이 셋이 "처음 보는 것"을 재는 것은 **의료 컨셉만**이다.

### 2.3 구성

- 의료 컨셉 227개: 진단명 91, 약물명 58, 시술명 45, 검사명 33
- 방문 유형 16, 성별 14
- 스키마 키워드 214개
- case_type: 기본형 24, 영문약어 17, 스키마단어없음 13, 사전누락 10, 경계사례 10, 복합 8, 구어체 6, 함축 5, 동의어 3, 연구설계 2, 오탐유도 2

### 2.4 검토에서 정한 정답 규칙

50문장 셋의 기준을 따르되, 검토 중에 아래를 정했다. 전체 규칙은 `kw100/` README에 있다.

- **테이블을 가리키는 단어는 스키마로 넣는다.**
  - 투약 표현: 주사, 약, 약물 이름 뒤의 치료·요법 ("펨브롤리주맙 치료", "병용 요법")
  - 컨셉 이름 안의 수술·치료: "방사성 요오드 치료", "물리치료" → 치료
  - 시술명 뒤의 검사·촬영: "PET-CT 촬영" → 촬영
  - 사람 명사: 아이·소아·영아·영유아·노인, 수혜자
- **넣지 않는 단어:** 시행, 기록, 이력, 날짜, 발생, 재발, 코호트, 시작한, 바꾼.
  - 재발은 SQL에서 "시술일 이후 같은 진단이 다시 나오는가"로 표현한다. OMOP CDM v5.3에는 재발 테이블이 없다.
- **원인이 붙은 진단명은 하나로 둔다** ("대상포진 후 신경통").

### 3.2 스키마 키워드

| 지표 | 파인튜닝 GLiNER | LLM |
|---|---|---|
| 정확 일치 P / R / F1 | 87.8 / 74.3 / 80.5 | 77.6 / 72.9 / 75.2 |
| 겹침 인정 P / R / F1 | 91.2 / 77.1 / **83.5** | 85.6 / 80.4 / 82.9 |
| 오탐 중 방문 유형·성별 위치 (형식 문제) | 16 / 22 | 23 / 45 |
| 위 오탐을 뺀 정확 일치 P / F1 (참고) | 96.4 / 83.9 | 87.6 / 79.6 |

- 09와 비슷한 결과다. 파인튜닝 GLiNER는 정밀도가 높고, LLM은 겹침 인정 재현율이 약간 높다.
- 오탐의 상당수는 "여성", "남성", "응급실" 같은 방문 유형·성별 단어다. llm-compat 형식은 방문 유형·성별을 스키마 항목으로 보내기 때문에 생긴다(09·10과 같다).
- **파인튜닝 GLiNER가 놓친 것:** 사람 ×12, 수치 ×9, 치료 ×4, 맞은 ×3, 검사 ×3, 수술 ×3, 퇴원 ×2, 촬영 ×2 등. "사람"은 문장에 나와도 거의 내지 않는다(2번만 냄, 그중 1번은 table을 death로 붙임). 09·10에서도 같은 약점이 있었다.
- **LLM이 놓친 것:** 수치 ×7, 투여 ×5, 치료 ×4, 수술 ×4 등.
  - LLM의 정확 일치 정밀도가 낮은 것은 "투여한 기록", "처방 이력", "병용 투여 이력"처럼 길게 내기 때문이다. 겹침 인정에서는 차이가 줄어든다.
  - LLM만의 진짜 오탐은 기록 ×3, 코호트, 가임기, 산모, 발생, 재발 여부, 시행한 등이다. 정답 규칙에서 빼기로 한 단어들이다.
- 구어체(먹고, 맞은)·사전누락 유형에서는 둘 다 스키마 재현율이 50%대로 낮다.

- 응답 그대로의 재현율은 두 모델 모두 낮다. 이 셋은 "진단", "시술" 같은 사건 단어 없이 컨셉만 있는 문장이 많아서, 스키마 키워드만으로는 테이블이 정해지지 않기 때문이다.
- 다운스트림 추론(의료 컨셉 라벨 → 테이블)을 포함하면 LLM은 거의 다 맞는다. 파인튜닝 GLiNER는 **procedure_occurrence가 64.3%** 에 그친다. 시술명을 놓치거나 다른 라벨로 냈기 때문이다(3.1절).
- 다운스트림 추론 포함 커버리지는 09보다 차이가 커졌다(10%p → 32%p).

### 3.5 응답 속도

| 지표 | 파인튜닝 GLiNER | LLM |
|---|---|---|
| 평균 | **0.47초** | 0.97초 |
| 중앙값 | **0.45초** | 0.88초 |
| 95백분위 | **0.57초** | 1.74초 |
| 실패 | 0 / 100 | 0 / 100 |

- 출력 jsonl의 `latency_ms`(HTTP 왕복)로 계산했다. 두 모델 모두 순차 호출이다. 서버는 다르다(파인튜닝 GLiNER는 사내 CPU, LLM은 원격 GPU).

## 4. 원본 결과 파일

정답과 답변을 문장별로 나란히 놓은 표를 모델마다 만들었다(`eval/raw_table.py`). 채점은 하지 않는 읽기용이다.

| 파일 | 내용 |
|---|---|
| `eval/runs/kw100/kw100_ft-gliner_compat/raw.md`, `raw.csv` | 파인튜닝 GLiNER |
| `eval/runs/kw100/kw100_prod_llm/raw.md`, `raw.csv` | LLM |

- 열: id, 문장, 정답 스키마 / 답변 스키마, 정답 의료 / 답변 의료, 정답 방문·성별 / 답변 방문·성별, 답변 기타, 지연(ms)
- 답변 스키마는 `텍스트(테이블)`, 의료 컨셉은 `텍스트(라벨)`로 적었다.
- 응답에는 방문 유형·성별 칸이 따로 없다. 그래서 답변 방문·성별에는 정답 방문·성별 위치와 겹치는 응답을 `텍스트(종류/테이블)`로 적었다.
- 답변 기타: 스키마·컨셉이 아닌 응답(OPERATOR, TIME, VALUE 등). 채점에 쓰지 않는다.
- 채점 결과(`kw50_scores.json`, `kw50_per_query.csv/json`)도 같은 폴더에 있다. 파일 이름의 `kw50_`는 채점기의 기본 이름이고, 내용은 100문장 결과다.

## 5. 이 비교의 한계

- **문장을 Claude가 만들었다.** 사람이 정답을 검토했지만, 문장 자체는 실제 운영 질의가 아니다. 문장이 짧고 정형화되어 있다(평균 30자 안팎).
- **같은 Claude가 문장과 정답 규칙을 만들었다.** LLM(Qwen)과 Claude의 표현 습관이 비슷해 LLM에 유리할 수 있다. 다만 의료 컨셉 정답은 이름 그대로라 영향은 작다고 본다.
- **스키마 단어와 방문 유형·성별은 처음 보는 것이 아니다.** 이 셋이 홀드아웃인 것은 의료 컨셉뿐이다.
- **표본:** 방문 유형·성별 30개, 시술명 45개로 크지 않다.
- **threshold:** 파인튜닝 GLiNER 0.5는 여전히 검증하지 않은 값이다. 놓침(37)이 오탐(15)보다 많아 낮추면 재현율이 오를 수 있다.
- **조건 항목:** 이 셋에도 정답이 없다. GLiNER는 여전히 내지 않는다.
