# NL2SQL 어댑터 평가 — validation 셋 (`proposed_input_val`)

> 종합 보고서와 지표 설명: [00_overview.md](00_overview.md) · 학습셋 결과: [01_train.md](01_train.md)

- 원본: `results/adapter_eval_{ft0_baseline,eval_loss,ft2_random,base,base_sysprompt_v2}_proposed_input_val.csv`, `results/adapter_eval_summary_261004_185030.json`(FT0), `results/adapter_eval_summary_261004_160834.json`(FT2), `results/adapter_eval_summary_261003_173605.json`(파인튜닝 + base), `results/adapter_eval_summary_261003_174450.json`(base+시스템 프롬프트)
- 테스트셋: `test_set/proposed_input_val.jsonl` (68건 / 시나리오 7개, 학습에 쓰지 않은 데이터)
- **집계 대상 63건:** id 290·535·721·447·299의 5건은 base+시스템 프롬프트의 few-shot 예시로 쓰여서 모든 모델에서 빼고 집계했어요.
  - query_type: COHORT_EXTRACTION 36 · STATISTICAL_AGGREGATION 14 · VALUE_RETRIEVAL 9 · EXPLORATORY_SEARCH 4
  - difficulty: EASY 18 · MEDIUM 35 · HARD 10
  - 개념 값 조건(앵커)이 있는 문항 56건 (concept_id 지표·하위 전개 반영도의 분모)
- **FT1 (input·1ep)** = `proposed_input`으로 1 epoch 학습한 첫 파인튜닝 모델의 eval_loss 기준 체크포인트(`by-loss`)예요([실험 목록](00_overview.md#파인튜닝-실험-목록)). 다른 두 체크포인트(concept_id, final_step)도 같이 돌렸지만 결과가 똑같아서 표에서 뺐어요(→ 1절 5번).
- **FT0 (baseline·1ep)** = input(재료) 없이 질문만으로 학습한 기준선 모델의 `by-loss` 체크포인트예요. 평가 프롬프트는 다른 모델과 똑같이 재료를 포함해요.
- **FT2 (random·1ep)** = `proposed_random`(concept_id 랜덤화, 4배)으로 1 epoch 학습한 모델의 `by-loss` 체크포인트예요([실험 목록](00_overview.md#파인튜닝-실험-목록)).
- 실행 설정은 학습셋과 같아요: temperature 0, max_tokens 512, 동시 요청 1. 파인튜닝 모델과 base는 시스템 프롬프트 없이, base+시스템 프롬프트는 학습셋과 같은 v2 프롬프트로 돌렸어요.
- 스키마 Usage는 고친 채점 방식으로 다시 채점한 값이에요([01_train.md](01_train.md) 5절).

## 1. 핵심 요약

0. **기준선 FT0(input 없이 학습)는 val EX 46.0%예요.** 학습 때 재료를 보여주면(FT1) 58.7%, 랜덤화 데이터로 학습하면(FT2) 88.9%로 올라요(→ 3.4절).
0. **FT2가 val에서도 가장 좋아요. EX 88.9%(56/63건)로 FT1(58.7%)보다 30%p, base+시스템 프롬프트(63.5%)보다 25%p 높아요.** FT2만 맞힌 문항은 FT1 대비 19건, base+시스템 프롬프트 대비 18건이고, 반대로 FT2가 놓친 문항은 각각 0건, 2건이에요. 학습셋(88.4%)과 val(88.9%)의 차이도 없어서, FT1처럼 학습셋에서만 점수가 높은 현상이 보이지 않아요(→ 3.3절).
   - **누수 확인:** FT2 학습 데이터(`proposed_random_train`)에 val의 id·시나리오는 하나도 없어요. val 정답 SQL과 문장 틀이 같은 학습 문항 비율도 FT1 학습 데이터와 똑같아요(숫자를 지운 SQL 기준 61/68건, SQL 완전 일치 20/68건). FT1과 비교해 새로 생긴 누수는 없어요.
1. **(FT1 기준) 학습하지 않은 데이터에서는 base+시스템 프롬프트가 파인튜닝 모델보다 약간 높아요.** EX는 base+시스템 프롬프트 63.5%, 파인튜닝 58.7%예요. 다만 차이는 3건이에요. 파인튜닝만 맞힌 문항이 4건, base+시스템 프롬프트만 맞힌 문항이 7건이라 **통계적으로 우열을 가릴 수 있는 차이는 아니에요.** 문항 1건이 약 1.6%p예요.
2. **학습셋 대비 하락폭은 파인튜닝 모델이 더 커요.** EX 기준으로 파인튜닝은 68.0%에서 58.7%로 9.2%p 떨어졌어요. base+시스템 프롬프트는 66.2%에서 63.5%로 2.7%p 떨어졌어요. 파인튜닝 모델의 학습셋 점수 일부는 학습 데이터를 본 덕분이었다고 볼 수 있어요.
3. **base+시스템 프롬프트의 val 점수는 조금 유리하게 나왔을 수 있어요.** few-shot 예시 5건이 val에서 뽑은 문항이라, 같은 시나리오와 같은 문장 틀을 쓰는 다른 val 문항에 정답 형태를 거의 그대로 보여준 셈이에요. 예를 들어 few-shot 721("…의 최초 발생일을 조회.")과 같은 틀인 720·469번은 base+시스템 프롬프트만 맞혔어요(→ 4절). 이 점을 빼면 두 모델은 사실상 비슷한 수준이에요.
4. **파인튜닝 효과(base 대비)는 val에서도 유지돼요.** base는 EX 20.6%, 하위 전개 0%, 자연어 답변 5건이에요. 파인튜닝 모델만 맞힌 문항이 24건, base만 맞힌 문항은 0건이에요.
5. **체크포인트 3개는 val에서도 같은 모델이에요.** 63건 중 61건에서 똑같은 SQL을 만들었고, 맞힌 문항(37건)까지 완전히 같아요. 그래서 eval_loss 체크포인트 하나로 대표했어요.
6. **파인튜닝 모델의 실행 안정성은 학습셋보다 좋아요.** 문법 100%, 실행검증 98.4%예요. 학습셋에서 문제였던 SQL 잘림·반복 루프가 val에서는 없었어요.
7. **틀린 원인이 두 모델에서 달라요(→ 4절).** 파인튜닝 모델은 출력 컬럼 구성이 다른 경우(12건)와 개념 코드 누락·오류(7건)가 많아요. base+시스템 프롬프트는 개념 코드 문제로 틀린 문항이 0건이고, 컬럼 구성(12건)과 조건·로직 차이(9건)로 틀렸어요.

## 3. 학습셋 대비 변화

EX 기준이에요(학습셋 612건, val 63건).

| 모델 | 학습셋 | val | 변화 |
|---|---:|---:|---:|
| FT0 (baseline·1ep) | 56.54% | 46.03% | −10.5%p |
| FT1 (input·1ep) | 67.97% | 58.73% | **−9.2%p** |
| FT2 (random·1ep) | 88.40% | 88.89% | +0.5%p |
| base | 23.69% | 20.63% | −3.1%p |
| base+시스템 프롬프트 | 66.18% | 63.49% | **−2.7%p** |

- base도 3%p 떨어졌어요. val 문항 자체가 학습셋보다 조금 어려울 수 있어요. 이를 감안해도 파인튜닝 모델은 약 6%p 더 떨어졌고, base+시스템 프롬프트는 거의 그대로예요.
- val은 63건이라 1건이 1.6%p를 움직여요. 이 하락폭들은 방향만 보고 크기는 변형 테스트셋 결과와 함께 판단하는 게 좋아요.

### 3.3 FT2 — concept_id 랜덤화 데이터로 학습한 모델

| 항목 | FT1 | FT2 | base+시스템 프롬프트 |
|---|---:|---:|---:|
| EX | 37건 | **56건** | 40건 |
| FT2와 비교해 한쪽만 맞힌 문항 | FT1만 0 / FT2만 19 | – | 이 모델만 2 / FT2만 18 |
| EM | 39.7% | **71.4%** | 9.5% |
| 정답 SQL과 글자까지 같은 답 | – | 39건 | – |

- **FT1의 대표 실수가 대부분 사라졌어요.** 4.결과의 "최초 발생일 조회"(환자별 집계 누락), EASY 문항의 불필요한 컬럼 추가가 줄어서 4.결과 8/8건, EASY 17/18건을 맞혔어요.
- **few-shot 이점도 넘어섰어요.** base+시스템 프롬프트가 few-shot 덕분에 맞혔던 720·469번도 FT2는 맞혔어요.
- **FT2가 틀린 7건**
  - **개념 코드 누락 4건(441·449·450·473):** "사쿠비트릴·발사르탄(ARNI)"처럼 앵커가 여러 개인 복합 약물에서 일부 앵커만 넣었어요(concept_id Correctness 0.33~0.50).
  - **불필요한 컬럼 추가 3건(443·295·264, 모두 3.비교군):** 정답은 `person_id`만 반환하는데 약물 코드·날짜 컬럼을 덧붙였어요. FT1의 대표 실수가 이 유형에만 남아 있어요.
- **향상 원인은 아직 구분할 수 없어요.** FT2는 데이터가 3.6배라 같은 1 epoch이어도 학습 횟수가 그만큼 많아요. 랜덤화 자체의 효과는 concept_id 변형 테스트셋에서 따로 확인해야 해요([01_train.md](01_train.md) 2.3절).

### 3.4 FT0 — input 없이 학습한 기준선 모델

- **EX를 틀린 원인(34건):** 하위 전개 안 함 10, 출력 컬럼 7, 실행 실패 7, 문법 실패 6, concept_id 누락 3, 조건·로직 1건이에요.
- 상세 분석은 [01_train.md](01_train.md) 2.4절에 있어요.

### 3.5 concept_id 핵심 지표

필요한 코드 79개, 불필요한 코드 11개 기준이에요. 지표 정의는 [00_overview.md](00_overview.md#concept_id-반영도--재료의-개념-코드를-제대로-썼는가)에 있어요.

| base+시스템 프롬프트 | 94.9% | **94.9%** | 93.7% | 81.8% |

- 학습셋과 같은 패턴이에요. FT0는 코드를 찾는 건 가장 잘하지만, 정답 형식으로 실행 가능하게 넣은 비율은 가장 낮아요.
- FT2는 올바른 반영률이 가장 높고 불필요한 코드도 가장 적게 써요. base+시스템 프롬프트는 올바른 반영률은 FT2와 비슷하지만 불필요한 코드를 가장 많이 써요.
- 불필요한 코드는 11개뿐이라 1개가 약 9%p예요. 경향만 참고해요.

## 4. 틀린 원인

EX가 fail인 문항을 원인별로 나눴어요. 하나의 문항은 위 순서로 먼저 해당하는 원인 하나에만 셌어요.

| 원인 | 파인튜닝(eval_loss) | base+시스템 프롬프트 |
|---|---:|---:|
| 실행 실패 | 1 | 2 (1건은 타임아웃) |
| 출력 컬럼 수가 정답과 다름 | 12 | 12 |
| concept_id 누락·오류 (Correctness < 1) | 7 | 0 |
| 컬럼 수는 같지만 결과가 다름 (조건·기간·로직) | 6 | 9 |
| **합계** | **26** | **23** |

**파인튜닝 모델의 대표 실수**

- **불필요한 컬럼 추가 (443번 "발사르탄 투여군.")**
  - 정답은 `SELECT DISTINCT de.person_id`예요.
  - 파인튜닝 모델은 `de.person_id, de.drug_concept_id, de.drug_exposure_start_date, de.drug_exposure_end_date`를 조회했어요.
  - 대상자는 맞게 골랐지만 결과 형태가 달라서 EX가 fail이에요.
- **환자별 집계 누락 (469·720번 "…의 최초 발생일을 조회.")**
  - 정답은 환자별 최초일이에요(`GROUP BY person_id`).
  - 파인튜닝 모델은 전체에서 하나의 최초일만 구했어요.
- **엉뚱한 컬럼에 개념 조건 (720번)**
  - 질병 코드 조건을 `co.person_id IN (SELECT descendant_concept_id …)`처럼 환자 번호 컬럼에 걸었어요.
  - concept_id Correctness 0점인 문항이 이 경우예요.

base+시스템 프롬프트는 few-shot 721번이 469·720번과 같은 문장 틀이라 정답 형태(환자별 `GROUP BY`)를 그대로 따라 했어요. 이 차이가 1절 3번에서 말한 few-shot 이점이에요.

**base+시스템 프롬프트의 EX가 낮은 이유:** 개념 코드 문제로 틀린 문항은 0건이고, 출력 컬럼 구성(12건)과 조건·로직(9건)에서 틀렸어요. 학습셋에서도 같은 경향이라, 상세 분석은 [01_train.md](01_train.md) 2.2.1절에 정리했어요.

**참고:** 출력 컬럼 수 차이는 두 모델 모두 가장 큰 실패 원인이에요(12건씩). 질문만으로는 어떤 컬럼을 보여줘야 하는지 정해지지 않는 문항이 많아서, 모델 오류라기보다 질문과 정답 사이의 모호함도 섞여 있어요.

## 6. 주의 사항

- **few-shot 출처:** base+시스템 프롬프트의 few-shot 5건이 val에서 뽑혔어요. 그 5건은 집계에서 뺐지만, 같은 시나리오·같은 문장 틀의 다른 val 문항에는 여전히 도움이 돼요. val에서 두 모델을 완전히 공정하게 비교하려면 few-shot을 학습셋 문항으로 바꾼 프롬프트로 val을 다시 돌려야 해요. 반대로 변형 테스트셋은 학습 데이터를 변형한 것이라, 지금처럼 val에서 뽑은 few-shot이 오히려 공정해요.
- **표본 크기:** 63건이라 1건이 1.6%p예요. 5%p 이하의 차이는 우연일 수 있어요.
