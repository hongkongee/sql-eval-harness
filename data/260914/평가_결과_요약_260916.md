# xiyan-sql-14b-sft-260914 평가 결과 요약 (2026-09-16)

두 가지 입력 파이프라인으로 같은 자연어 질의 88건(검증셋 시나리오 원본 68건 +
신규 작성 질의 20건)을 테스트했다.

- **A. 자연어만 입력** (`scripts/eval_api_model.py`) — 모델에 자연어 질문만 주고,
  모델이 `{{개념명}}` 플레이스홀더를 남기면 RAG가 나중에 문자열 치환으로
  concept_id를 채워넣는 원래 설계. 결과: `eval_results_v5.csv`
- **B. RAG 프롬프트 실시간 조립 입력** (`scripts/eval_api_model_rag.py`) — 자연어
  질문을 RAG API(`http://10.1.1.106:8080/materials`)에 먼저 보내 concept_id
  매핑 + 관련 테이블/조인이 합쳐진 프롬프트를 받고, 그 프롬프트를 모델에 바로
  넣어 완성된 SQL을 한 번에 받는 실험적 파이프라인. 결과: `eval_results_rag.csv`

둘 다 측정 지표: Syntactic Validity(sqlglot 정적 분석), omop-cdm 스키마 참조
정확도(테이블/컬럼 환각 여부), 샌드박스 PostgreSQL DB 실행검증(EXPLAIN 기준),
응답 속도. 샌드박스는 `10.10.30.32:5434` — OMOP CDM 스키마+전체 어휘사전
(concept 테이블 700만 행)은 있지만 **환자 임상 데이터(person/condition_occurrence/
drug_exposure 등)는 0건**이다.

## A. 자연어만 입력 (88건)

| 지표 | 결과 |
|---|---|
| Syntactic Validity | 87/88 (98.9%) |
| Format 이탈율 | 0/88 (0.0%) |
| omop-cdm 스키마 참조 정확도 | 81/88 (92.0%) |
| 샌드박스 DB 실행검증 | 80/88 (90.9%) |
| EM (정답 있는 68건) | 51/68 (75.0%) |
| EX (정답 있는 68건) | 68/68 (100.0%) |
| 응답 속도 평균/최대 | 4.99s / 20.03s |

**주요 발견**

- **정적 스키마 검사는 통과했지만 실제 DB 컴파일에서만 드러난 버그 2건**:
  서브쿼리 안에서만 정의된 alias(`d`=death, `po`=procedure_occurrence)를 그
  스코프 밖(다른 EXISTS 절이나 바깥 SELECT)에서 그대로 참조. 테이블/컬럼
  자체는 스키마에 실재해서 정적 분석은 못 잡고, 샌드박스 `EXPLAIN`에서만
  `missing FROM-clause entry` 오류로 잡혔다. → 정적 분석만으로는 부족하고
  실제 DB 실행검증이 필요하다는 근거.
- **`person.death_date` 환각 2건**: OMOP CDM에서 사망일은 `person`이 아니라
  별도 `death` 테이블에 있는데, 모델이 이를 혼동해 `person.death_date`를
  참조. `death` 테이블 관련 학습 예시가 부족할 가능성.
- **EM 75% / EX 100%의 간극**: EM fail로 잡힌 케이스 상당수는 괄호 위치·조건
  순서(`A OR B` vs `B OR A`) 같은 표현 차이였고, EX(실행 결과 비교)는 전부
  일치했다. 즉 의미상으로는 대부분 정답과 같다.
- **EX 100%는 액면 그대로 믿으면 안 됨**: 샌드박스에 임상 데이터가 0건이라
  예측/정답 쿼리 둘 다 빈 결과를 내고, 빈 결과끼리는 항상 일치한다. 지금의
  EX는 "실행 가능했다" 정도의 의미이지 "로직이 정확하다"는 증거가 아니다.
  실제 데이터가 채워져야 EX가 변별력을 가진다.

## B. RAG 프롬프트 실시간 조립 입력 (88건)

| 지표 | 결과 |
|---|---|
| Syntactic Validity | 72/88 (81.8%) |
| omop-cdm 스키마 참조 정확도 | 72/88 (81.8%) |
| **{{}} 플레이스홀더 잔존** | **51/88 (58.0%)** |
| 샌드박스 DB 실행검증 | 69/74 (93.2%) |
| EX (실제 실행 성공 여부, 정답 비교 아님) | 69/74 (93.2%) |
| **LLM API 400 (컨텍스트 초과)** | **14/88 (15.9%)** |
| 응답 속도 평균/최대 | 6.30s / 24.09s (RAG 호출 + LLM 호출 합산) |

이 모드는 정답 SQL을 전제하지 않는 테스트라 EM/정답 비교는 하지 않았고, "EX"는
정답과의 일치가 아니라 "샌드박스에서 실제로 실행해서 오류 없이 끝나는가"를
뜻한다.

**주요 발견 (두 가지 핵심 이슈)**

1. **모델이 실제 concept_id를 받고도 58%는 무시하고 예전처럼 `{{}}`를 남김.**
   RAG가 concept_id 리스트를 전부 계산해서 프롬프트에 넣어주고, 시스템
   프롬프트로 "그 concept_id를 그대로 IN절에 써라"고 명시해도, 파인튜닝 때
   학습된 `{{개념명}}` 습관이 프롬프트 지시보다 강하게 작용하는 것으로 보인다.
   → "RAG 프롬프트를 그대로 넣어 완성 SQL을 한 번에 받는" 이 파이프라인은
   지금 이 모델로는 신뢰하기 어렵다. concept_id가 채워진 프롬프트 형태로
   재학습하거나, few-shot 예시를 프롬프트에 추가하는 방안이 필요해 보인다.
2. **concept_id가 많은 개념(약물)은 프롬프트가 모델 컨텍스트(8192 토큰)를
   넘겨 요청 자체가 거부됨.** 14건 전부 동일한 원인:
   ```
   This model's maximum context length is 8192 tokens. However, you requested
   512 output tokens and your prompt contains at least 7681 input tokens...
   ```
   아토르바스타틴(concept_id 1014개), 로수바스타틴, 메트포르민, 글리메피리드,
   암로디핀, 비스포스포네이트 등 **concept_id 리스트가 긴 약물/질환**에서
   전부 발생. RAG가 `[재료]`에 concept_id를 전부 나열하는 방식이라, 이런
   개념 하나만으로도 프롬프트가 7000토큰을 넘는다. → RAG 쪽에서 concept_id
   개수가 많을 때 상위 N개만 쓰거나 다른 방식(vocabulary 테이블 조인 등)으로
   바꾸는 걸 검토할 필요가 있다.

## 결론 및 제언

- **파이프라인 A(자연어만 입력 → 모델이 `{{}}` 남김 → RAG가 문자열 치환)**가
  지금 이 모델의 학습 방식과 가장 잘 맞는다. Syntactic Validity 98.9%,
  스키마 정확도 92%로 안정적이다.
- **파이프라인 B(RAG 프롬프트 통째로 입력)**는 두 가지 문제 — concept_id
  무시(58%)와 컨텍스트 초과(15.9%) — 때문에 지금 상태로는 프로덕션에 쓰기
  어렵다. 도입하려면 (1) 이 프롬프트 포맷으로 파인튜닝 데이터를 다시 만들거나,
  (2) RAG의 concept_id 나열 방식을 프롬프트 길이가 안 터지게 바꾸는 작업이
  선행되어야 한다.
- **EX 지표는 샌드박스에 임상 데이터가 채워지기 전까지는 참고용**이다. 진짜
  로직 정확성을 검증하려면 실제(또는 합성) 환자 데이터가 필요하다.
