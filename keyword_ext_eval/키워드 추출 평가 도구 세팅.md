# 키워드 추출 평가 도구 세팅

- **작성일**: 2026-10-24
- **위치**: `sql-eval-harness/keyword_ext_eval/`
- **상태**: 도구 세팅 완료. 전체 데이터 평가는 아직 실행하지 않았습니다. 동작은 샘플 5~8건과 mock으로만 확인했습니다.
- **상세 사용법**: [eval/README.md](eval/README.md)

---

## 1. 목적과 범위

키워드 추출 API(`POST /keyword-extraction`)가 내는 **스키마 키워드**가 정답 SQL이 쓰는 테이블을 얼마나 가리키는지 측정합니다. 사전(`schema_keywords.yaml`)을 반복해서 보강하는 데 쓰는 도구입니다. API는 스키마는 사전 매칭, concept는 GLiNER로 뽑습니다.

비교 기준선 두 가지도 같은 기준으로 채점합니다.

- **zero-shot GLiNER (스키마 라벨)**: "사전 대신 GLiNER를 썼다면"의 기준선
- **개발서버 Qwen**: LLM 기준선이자 사전 보강 후보의 출처

이번 작업에서 지킨 원칙은 세 가지입니다.

- 서비스 코드와 사전은 수정하지 않았습니다.
- 평가 기준점은 실행 중인 API의 응답입니다. 평가 도구에는 사전 매칭 로직을 넣지 않았습니다.
- 추출과 채점을 분리했습니다. 모든 추출기는 같은 형식의 결과 파일을 내고, 채점기는 그 파일만 읽습니다.

### 3.1 평가 데이터

모든 파일이 JSONL이고 필드명이 같습니다. **id는 `id`, 자연어는 `text`, 정답 SQL은 `query`**입니다.

|---|---|---:|---|

- 파일마다 id 체계가 달라서, 결과 파일에서는 `<파일명>:<id>` 형식으로 구분합니다. 예: `paraphrase:seed_3_test_paraphrase`

### 3.2 Qwen 호출 코드와 프롬프트

- **호출 방식은 기존 코드를 따랐습니다.** `adapter_prompt_eval/inference.py`와 `scripts/eval_api_model.py`가 `requests`로 OpenAI 호환 `/v1/chat/completions`를 호출합니다(temperature 0). 기존 코드에는 재시도, 백오프, 파싱 실패 처리가 없어서 새로 만들었습니다.
- **키워드 추출용 프롬프트는 없었습니다.** 레포에 "Qwen" 모델명도 없습니다. 개발서버에 떠 있는 것은 XiYan-SQL 계열입니다. 그래서 프롬프트는 초안으로 새로 썼습니다.

### 3.3 API 구조에서 발견한 것

- **사전을 고치면 API를 재빌드해야 합니다.** 8001 컨테이너는 사전 파일을 볼륨으로 연결하지 않고 Docker 이미지에 넣어 빌드했습니다. 그래서 재시작만으로는 반영되지 않습니다.
  ```bash
  cd ~/Developer/gliner-entity-router && docker compose up -d --build keyword-extraction
  ```
- **API가 실제로 쓰는 사전은 컨테이너 안에서 확인할 수 있습니다.** `docker exec`로 컨테이너 안 사전 파일의 해시와 환경변수를 읽습니다. 서비스 코드는 고치지 않습니다. 현재 로컬 사전과 해시가 같습니다(`b1630690…`). 모델은 `Ihor/gliner-biomed-large-v1.0`, threshold는 0.1입니다.
- **concept에는 사전 매칭이 없습니다.** 지금 API의 concept는 GLiNER 4개 라벨(진단명/약물명/검사명/시술명)뿐입니다. "방문", "입원", "성별"은 concept가 아니라 schema 사전에 들어 있습니다.
- **API가 일반 단어를 concept로 잡습니다.** threshold가 0.1로 낮아 "이력", "환자군", "코호트" 같은 단어가 낮은 점수의 concept로 나옵니다(스모크 테스트에서 확인). 이 때문에 보강 후보 수집에 영향이 있어 옵션을 추가했습니다(5.3절).

## 5. 동작 방식

### 5.1 추출 (`python -m eval.extract`)

질의당 한 줄로, 세 추출기가 모두 같은 형식의 결과를 냅니다.

```json
{"id": "paraphrase:seed_3_test_paraphrase", "dataset": "paraphrase", "system": "api",
 "schema_keywords": ["투약", "환자"],
 "concept_spans": [{"text": "발사르탄", "start": 0, "end": 4, "score": 0.96, "label": null}],
 "latency_ms": 712.3, "attempts": 1}
```

| 추출기 | 방식 | 주요 설정 |
|---|---|---|
| **api** (기준점) | 실행 중인 API를 그대로 호출 | `KEYWORD_API_URL` (기본 `localhost:8001`) |
| **gliner** | `gliner-entity-router`의 `/extract` 컨테이너를 HTTP로 호출 (로컬 torch 설치 불필요) | 라벨 4개(환자 또는 대상자 / 진단 행위 / 처방 또는 투약 행위 / 측정 또는 검사 행위), threshold 0.3, 기본 모델 multi-v2.1 |
| **qwen** | OpenAI 호환 chat completions | `.env`의 `QWEN_*` (4.3절) |

공통 기능:

- **실행 정보 기록:** 결과 파일 옆 `.meta.json`에 실행 시각, 하드웨어, 시스템별 설정을 남깁니다.
  - api: 사전 해시(로컬 파일과 API 컨테이너 양쪽), GLiNER 모델·라벨·threshold
  - gliner: 모델명, 라벨, threshold
  - qwen: 모델명, 시스템 프롬프트 출처·해시, 작업 프롬프트 해시, 실제로 보내는 메시지 전체 해시, 요청 옵션
- **실패 기록:** 실패한 질의는 `.failed.jsonl`에 따로 남습니다.
- **이어하기:** 결과 파일에 이미 있는 id는 건너뛰고, 실패한 id만 다시 시도합니다. 사전 해시, 모델, 라벨, 프롬프트 중 하나라도 기존 실행과 다르면 결과가 섞이지 않도록 멈춥니다. 새로 시작하려면 `--overwrite`를 줍니다.
- **api 전용:**
  - API가 떠 있지 않으면 안내 메시지를 내고 종료합니다.
  - 시작할 때 API 사전 해시와 현재 사전 파일 해시를 비교해서, 다르면 경고합니다.
  - `latency_ms`는 HTTP 왕복 시간입니다(서버 내부 추론 시간이 아님).
- **qwen 전용:**
  - 타임아웃, 연결 오류, 429, 5xx는 지수 백오프(1s → 2s → 4s → 8s)로 재시도합니다.
  - 파싱 실패와 그 밖의 4xx는 다시 보내도 같은 결과라 바로 실패 처리합니다.
  - 동시 요청 수는 `QWEN_CONCURRENCY`(기본 4)로 제한하고, `--concurrency`를 주면 그쪽이 우선합니다.
  - 추론(thinking) 모델이 답 앞에 `<think>…</think>`를 붙여도 떼고 파싱합니다.
  - 질의에 글자 그대로 없는 단어는 버리고 `dropped_keywords`에 기록합니다.
  - `--mock`을 주면 서버 없이 가짜 응답으로 돕니다.

### 5.2 채점 (`python -m eval.score`)

**판정 기준은 테이블 단위 커버리지입니다.** 정답 SQL이 쓰는 대상 테이블마다, 그 테이블을 가리키는 키워드가 하나 이상 있으면 덮인 것으로 봅니다.

- **대상 테이블 8개:** person, observation_period, visit_occurrence, condition_occurrence, drug_exposure, procedure_occurrence, measurement, death. concept, concept_ancestor 같은 어휘 테이블은 뺍니다.
- **정답 SQL → 테이블:** sqlglot(PostgreSQL)의 scope 분석을 씁니다. CTE 이름, 서브쿼리, 별칭, UNION, 스키마 접두어를 처리합니다. 결과는 캐시하고, 파싱에 실패한 SQL은 별도 목록으로 냅니다.
- **키워드 → 테이블:** 표면형 → 사전 묶음(사전 파일을 읽기만 함) → 테이블(평가 전용 매핑) 순서로 판정합니다.
  - 사전에 없는 단어(GLiNER, Qwen 결과)는 단어 안에 사전 표면형이 들어 있으면 그 묶음으로 봅니다. 예: "심부전 진단" → 진단.
  - 하나도 없으면 **미매핑 단어**로 집계하고, 목록과 빈도를 출력합니다.
- **시스템별 채점 방식:**
  - gliner는 키워드 기준과 라벨 기준(`gliner_label`) 두 가지로 채점합니다.
  - `--concept`를 주면 concept 라벨까지 더한 커버리지(`api_concept`)를 따로 냅니다. 지금 API는 concept에 라벨이 없어서 경고만 내고 스키마 커버리지만 냅니다(7절, 보류).

| 지표 | 정의 |
|---|---|
| 질의 단위 커버리지 | 정답 테이블이 **모두** 덮인 질의 비율 |
| 테이블별 재현율 | 8개 테이블 각각 |
| 중복 제거 버전 | 날짜·숫자·concept를 가린 문장 기준으로 템플릿 중복을 없앤 뒤 같은 지표 |
| 잡음 (참고치) | 정답에 없는 테이블만 가리키는 키워드 수 |
| 처리 속도 | `latency_ms` 평균, p95 |

모든 지표는 데이터 파일별 값과 전체 값을 같이 냅니다.

출력 위치는 `eval/runs/<타임스탬프>/`입니다.

| 파일 | 내용 |
|---|---|
| `scores.md` | 시스템 비교 표 (커버리지 / 테이블별 재현율 / 데이터 파일별 / 잡음 / 속도 / 실행 정보 요약) |
| `scores.json` | 모든 지표 |
| `misses_<시스템>.csv` | 덮이지 않은 (질의, 테이블) 쌍, 누락 테이블별 정렬 |
| `diff_prev_<시스템>.md` | 직전 run 대비 새로 덮인 질의 / 새로 깨진 질의(회귀) |
| `unmapped_<시스템>.csv` | 미매핑 단어와 빈도 |

### 5.3 보강 후보 수집 (`python -m eval.candidates`)

- Qwen은 뽑았지만 API의 schema 키워드에는 없는 단어를 모읍니다.
- 이미 사전에 있는 표면형, API의 concept와 겹치는 단어는 뺍니다.
- `candidates.csv`의 열: 후보, 빈도, 해당 문장의 정답 테이블 분포, Qwen이 지목한 테이블, 기존 사전 묶음 포함 여부, 예시 문장 3개. 빈도 내림차순으로 정렬합니다.
- **추가 옵션 `--concept-min-score`:** API가 일반 단어를 낮은 점수의 concept로 잡으면 그 단어가 후보에서 빠집니다(3.3절). 이 옵션을 주면 지정한 점수 미만의 concept는 겹침 판정에 쓰지 않습니다. 기본값 0은 지시대로 모든 concept를 씁니다.
- 사전에 자동으로 추가하지 않습니다. 검토 후 직접 넣습니다.

### 5.4 사전 보강 루프

1. `schema_keywords.yaml`을 수정합니다. 새 묶음을 만들었다면 `eval/maps/schema_keyword_table_map.yaml`에도 추가합니다.
2. API를 **재빌드**합니다: `docker compose up -d --build keyword-extraction`
3. `make loop`를 실행합니다. API 사전 해시가 현재 파일과 다르면(재빌드를 안 했으면) 추출 단계에서 멈춥니다.
4. `scores.md`, `misses_api.csv`, `diff_prev_api.md`(회귀 확인), `candidates.csv`를 검토합니다.
5. 1번으로 돌아가 반복합니다.

## 7. concept span `label` 필드 추가 제안: 보류

API 응답의 concept span에 GLiNER 라벨을 같이 내자는 제안이었습니다. 새 라벨을 추가하는 게 아니라, 지금 쓰는 의료 라벨 4개(진단명 또는 질병명 / 약물명 / 검사명 또는 측정 항목 / 시술명 또는 수술명) 중 어느 것으로 잡혔는지를 내자는 것이었습니다. 채점기가 concept를 테이블로 바꿔 쓰려는 목적이었습니다(약물명 → drug_exposure 등).

**보류한 이유:** 라벨 4개만 쓰는 근거였던 재현율 95% 이상은 "위치를 찾았는가" 기준입니다. 라벨까지 맞췄는지는 훨씬 낮습니다. 아래는 BioMed 모델 수치입니다(`GLiNER_제로샷_키워드추출_평가보고서.md` 6절).

| 도메인 | 라벨까지 맞춘 Precision / Recall |
|---|---|
| 진단명 또는 질병명 | 0.405 / 0.973 |
| 약물명 | 0.567 / 0.953 |
| 검사명 또는 측정 항목 | 0.125 / 0.698 |
| 시술명 또는 수술명 | 0.473 / 0.929 |

- API처럼 위치마다 가장 높은 라벨 하나만 남기면, 엠파글리플로진·암로디핀 같은 약물이 진단명으로 바뀌어 약물명 재현율이 0.769로 떨어집니다.
- 그래서 라벨 → 테이블 환산이 자주 틀립니다. 예를 들어 약물이 condition_occurrence로 잡히면, drug_exposure는 놓치고 엉뚱한 테이블을 덮은 것으로 계산됩니다.

**현재 상태:**
- 서비스 코드는 수정하지 않았습니다.
- 채점은 스키마 키워드 커버리지만 봅니다.
- `--concept` 옵션은 라벨이 없으면 경고만 내고 넘어가므로 그대로 둡니다.
- 처음 제안에 넣었던 `"visit"`/`"gender"` 예약 라벨은 지웠습니다. API에 사전 기반 concept가 없는데 있다고 잘못 알고 넣은 것이었습니다(매핑 파일에서도 제거).

## 8. Qwen 호출 방식과 확인할 것

### 8.1 요청 형태

질의 하나당 아래처럼 `[system, user]` 두 메시지를 보냅니다.

```json
POST {QWEN_BASE_URL}/chat/completions
{
  "model": "Flash-Next-FP8",
  "temperature": 0,
  "max_tokens": 512,
  "messages": [
    {"role": "system", "content": "<QWEN_SYSTEM_PROMPT_FILE 내용 — 지금은 임시>"},
    {"role": "user",   "content": "<작업 지시 + 예시 1개>\n\n질의: <평가할 자연어>"}
  ]
}
```

- **시스템 프롬프트:** 레포에 이 용도로 정해진 것이 없었습니다(`.env`의 기존 시스템 프롬프트는 SQL 생성용). 그래서 지금은 **임시** 파일 `eval/prompts/qwen_system_temp.txt`를 씁니다. 실행할 때마다 임시라는 경고를 냅니다. 확정되면 파일 내용을 바꾸거나 `.env`의 `QWEN_SYSTEM_PROMPT_FILE`이 다른 파일을 가리키게 하면 됩니다. 코드 수정은 필요 없습니다.
- **작업 지시는 user 쪽에 있습니다.** 테이블 8개 설명, 추출 규칙, 출력 형식(`{"schema_keywords": [{"text", "table"}]}`), 예시가 들어 있습니다(`eval/prompts/qwen_schema_keywords.txt`, 초안). 그래서 시스템 프롬프트를 확정된 것으로 바꿔도 지시는 그대로 남습니다.
- **사전 표면형 목록은 일부러 넣지 않았습니다.** Qwen이 사전에 없는 표현을 찾게 하는 것이 목적이기 때문입니다.

### 8.2 모델이 바뀔 때

- `.env`의 `QWEN_MODEL`만 바꾸면 됩니다.
- 결과에는 모델명과 실제로 보낸 메시지 전체의 해시가 기록됩니다. 모델이나 시스템 프롬프트가 바뀐 상태로 기존 결과를 이어서 돌리려 하면, 결과가 섞이지 않도록 멈춥니다.
- 모델별로 결과 파일을 따로 두는 것을 권장합니다: `make extract-qwen QWEN_OUT=eval/outputs/qwen_<모델>.jsonl`. `make score`가 `eval/outputs/`의 파일을 모두 채점하므로 모델끼리 나란히 비교됩니다.
- 추론(thinking) 모델이 답 앞에 `<think>…</think>`를 붙여도 떼고 파싱합니다. thinking을 꺼야 하면 `QWEN_EXTRA_BODY`로 넣습니다. 예: `{"chat_template_kwargs": {"enable_thinking": false}}`

### 8.3 서버에서 확인할 것

1. 서버 IP·포트를 `.env`의 `QWEN_BASE_URL`에 넣고, API 키가 필요한지 확인합니다.
2. served model name이 정확히 `Flash-Next-FP8`인지 확인합니다. `GET {QWEN_BASE_URL}/models`로 볼 수 있습니다.
3. 확정된 시스템 프롬프트를 받아 임시 파일을 교체합니다.
4. 응답이 `choices[0].message.content` 형식인지, thinking 출력이 섞이는지 확인합니다.
5. 프롬프트 품질을 봅니다. 먼저 `make extract-qwen EXTRA="--limit 20"`으로 돌리고, `qwen.failed.jsonl`과 `dropped_keywords`를 확인합니다.
6. 서버가 감당할 수 있는 동시 요청 수를 확인합니다(`QWEN_CONCURRENCY`, 기본 4).
