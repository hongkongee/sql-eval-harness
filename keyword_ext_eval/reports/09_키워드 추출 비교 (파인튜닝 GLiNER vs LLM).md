# 키워드 추출 비교: 파인튜닝 GLiNER vs LLM

- 작성일: 2026-10-28, 파인튜닝 GLiNER 기준으로 개정 2026-11-03
- 질문: **파인튜닝 GLiNER가 지금 운영 중인 LLM 대신 쓸 수 있을 만큼 성능이 나오는가**
- 비교 대상
  - **파인튜닝 GLiNER**: GLiNER-BioMed를 엔진 형식 라벨로 파인튜닝한 모델. 사전 없이 모델 하나로 모든 키워드를 낸다. **평가 대상**
  - **LLM**: 지금 Text-to-SQL 엔진에 들어가 있는 방식. 프롬프트로 LLM에게 키워드를 뽑게 한다. **기준**
  - 참고용
    - **제로샷 GLiNER**: 파인튜닝 GLiNER와 같은 베이스 모델·라벨을 학습 없이 쓴 것. 파인튜닝 효과를 보는 기준선이다
    - **GLiNER + 사전 매칭**: 이전에 만든 방식(KE-r3). 사전 매칭은 쓰지 않기로 해서 참고로만 둔다
- 모든 방식이 엔진이 받는 같은 형식 `[{keyword, label, table}]`으로 결과를 낸다. 형식 명세는 [08 응답 인터페이스](08_키워드%20추출%20응답%20인터페이스%20(llm-compat%20·%20운영%20LLM).md)에 있다. 같은 정답셋, 같은 채점 방식으로 쟀다.

## 요약

| 항목 | 지표 | 파인튜닝 GLiNER | LLM | 제로샷 GLiNER (참고) | GLiNER + 사전 매칭 (참고) |
|---|---|---|---|---|---|
| 스키마 키워드 | F1 | **87.9** | 85.8 | 60.4 | 92.5 |
| 의료 컨셉 키워드 | F1 | 92.4 | **94.7** | 66.3 | 89.2 |
| 방문 유형·성별 키워드 | 맞힌 수 / 23 | **18** | 16 | 12 | 12 |
| 응답 속도 | 평균 응답 시간 | **0.47초** | 1.70초 | 0.50초 | 0.67초 |

- 파인튜닝·제로샷 GLiNER는 세 항목을 모두 모델 하나가 만든다. GLiNER + 사전 매칭은 스키마 키워드와 방문 유형·성별을 사전이, 의료 컨셉을 GLiNER가 만든다.
- 정답은 사람이 직접 단 키워드 정답이다. 정답 SQL에서 뽑은 것이 아니다. 자세한 내용은 2절에 있다.
- 응답 시간은 평가 도구가 문장마다 잰 HTTP 왕복 시간(출력 jsonl의 `latency_ms`)의 50건 평균이다. 중앙값은 파인튜닝 GLiNER 0.45초, LLM 1.52초다.
- 응답 시간은 실행 환경이 달라 참고용이다. 파인튜닝·제로샷 GLiNER는 사내 서버 CPU에서 순차 호출, LLM은 원격 서버에 4건씩 동시 호출, GLiNER + 사전 매칭은 로컬에서 쟀다(3.6절).
- 테이블 커버리지, 조건 항목, 형식 준수는 3절에 있다.

**결론.** 파인튜닝 GLiNER는 키워드 세 항목에서 LLM과 비슷한 수준이다.
- 스키마 키워드와 방문 유형·성별은 LLM보다 높다. 의료 컨셉은 2.3점 낮다.
- 형식 위반이 없고, 같은 입력에 같은 출력을 내고, 응답이 빠르다.

다만 바로 쓰기 전에 확인할 것이 세 가지 있다(6절).
1. **시술명을 놓친다** (5 / 9). 그래서 다운스트림 추론을 포함한 테이블 커버리지가 LLM보다 10%p 낮다(80% vs 90%).
2. **조건 항목(값·비교·시점)을 내지 않는다.** 엔진이 이 항목을 쓴다면 따로 대책이 필요하다.
3. **threshold 0.5를 검증하지 않았고, 정답셋이 50문장이다.** 더 큰 홀드아웃 셋으로 다시 확인해야 한다.

**파인튜닝 효과.** 같은 모델·라벨의 제로샷 GLiNER는 조사 조각("받", "한")과 조건 표현("이상", "30일")을 스키마로 내고 질병명을 많이 놓친다. 파인튜닝 후 스키마는 60.4 → 87.9, 의료 컨셉은 66.3 → 92.4가 됐다. 단, 두 모델은 threshold가 다르다(5절).

## 1. 테스트 조건

### 1.1 파인튜닝 GLiNER

- **방식:** 파인튜닝한 GLiNER 하나로 모든 키워드를 뽑고 엔진 형식으로 변환한다. 사전은 쓰지 않는다.
- **베이스 모델:** GLiNER `Ihor/gliner-biomed-large-v1.0`
- **체크포인트:** `./models/llm-compat-v1/`. eval_loss가 가장 낮은 지점(`load_best_model_at_end`)을 저장한 것이다.
- **학습 데이터:** 시드 질의 769건을 변환한 764건(gliner-entity-router `data/processed/llm_compat_dataset.jsonl`). train 688 / eval 76으로 나눴다(seed 42, 9:1).
  - 스키마 라벨 외에 의료 컨셉 라벨 4개(진단명 358, 약물명 281, 시술명 138, 검사명 62)와 방문 유형 21, 성별 10도 들어 있다.
- **추론 라벨:** `llm_compat_map.yaml`의 schema·concept 키 18개(중복 제거)를 GLiNER 후보 라벨로 그대로 쓴다.
- **threshold:** 0.5 (`FINETUNED_THRESHOLD` 기본값). **아직 검증하지 않은 값이다.**
- **실행 환경:** 사내 서버의 API(`POST /keyword-extraction/llm-compat`). CPU로 추론하고, 한 건씩 순차 호출했다.
- **정답셋 중복 점검:** 학습 데이터 764건과 정답셋 50문장을 대조했다.
  - 똑같은 문장은 없다.
  - 가장 비슷한 쌍은 "현재 연도 기준 연령 65세 이상이고 골다공증 진단을 받은 여성 환자."와 학습 문장 "현재 연도 기준 연령 65세 이상이고 골다공증 진단인 환자."다(4글자 단위 유사도 0.6). 그 밖에는 0.53 이하다.

### 1.2 LLM

- **방식:** 시스템 프롬프트로 LLM에게 키워드와 라벨을 JSON으로 출력하게 한다.
- **모델:** Qwen3.8-Flash-Next-FP8. vLLM으로 서빙하고 모델명은 `qwen-vl`이다.
  - temperature 0
  - thinking 끔
- **사전:** 없다. 프롬프트에 테이블 목록과 라벨 정의를 넣는다.
- **실행 환경:** 원격 서버에 프록시를 거쳐 4건씩 동시 호출했다.
- **내부 이름:** prod-llm, 운영 시스템 프롬프트 sha256 `1bb9b021…`

**⚠ 운영과 조건이 다를 수 있다.**
- 프롬프트의 테이블 목록은 운영 코드를 받지 못해 대체본을 넣었다.
- 운영에서 thinking을 켜는지는 확인이 필요하다.
- 응답 시간은 실행 환경이 달라 참고용이다.

### 1.3 참고: 제로샷 GLiNER

- **방식:** 학습하지 않은 GLiNER 하나로 모든 키워드를 뽑는다. 사전은 쓰지 않는다.
- **모델:** GLiNER `Ihor/gliner-biomed-large-v1.0` (파인튜닝 GLiNER의 베이스 모델)
- **추론 라벨:** 파인튜닝 GLiNER와 같은 18개
- **threshold:** 0.2. 파인튜닝 GLiNER(0.5)와 다르다.
- **실행 환경:** 파인튜닝 GLiNER와 같은 사내 서버의 API(`POST /keyword-extraction/llm-compat/zero-shot`). CPU, 한 건씩 순차 호출.

### 1.4 참고: GLiNER + 사전 매칭

- **방식:** 사전 매칭과 GLiNER 개체명 인식 결과를 합쳐 엔진 형식으로 변환한다. 앞으로 쓰지 않는다.
- **모델:** GLiNER `Ihor/gliner-biomed-large-v1.0`, 제로샷. 라벨 4개(진단명, 약물명, 검사명, 시술명), threshold 0.3.
- **사전:** 스키마 사전(대표 키워드 13개, 표면형 39개), 방문 유형·성별 사전
- **실행 환경:** 로컬 Docker 컨테이너, 한 건씩 순차 호출.
- **내부 이름:** KE-r3 `/keyword-extraction/llm-compat`, gliner-entity-router `5708649`

### 1.5 공통 조건

- **정답셋:** 사람이 직접 정답을 단 50문장이다. 파일은 `test_set/keyword_ext/keyword_eval_samples_50.csv`이다.
  - 정답 SQL에서 뽑은 것이 아니다. 자세한 내용은 2절에 있다.
  - 어느 방식의 개발에도 쓰지 않았다. 파인튜닝 GLiNER의 학습 데이터와도 겹치지 않는다(1.1절).
- **채점:** 모든 방식의 응답을 같은 해석기로 읽고 같은 채점기로 채점한다.

## 2. 지표 설명

### 기본 용어

| 용어 | 뜻 |
|---|---|
| TP (맞힘) | 정답에 있는 것을 냈다 |
| FP (오탐) | 정답에 없는 것을 냈다 |
| FN (놓침) | 정답에 있는 것을 안 냈다 |
| 정밀도 P | TP / (TP + FP). 낸 것 중 맞은 비율. 낮으면 엉뚱한 것을 많이 낸다 |
| 재현율 R | TP / (TP + FN). 정답 중 찾은 비율. 낮으면 많이 놓친다 |
| F1 | P와 R의 조화평균. 둘 중 낮은 쪽에 끌려간다 |

### 정답은 어디서 왔나

정답셋 CSV(50문장)는 **사람이 문장마다 직접 단 정답**이다. 정답 SQL에서 뽑은 값이 아니다. CSV에 SQL 열이 없고, 아래 정답이 모두 수작업 라벨이다.

| 정답 열 | 내용 | 쓰는 지표 |
|---|---|---|
| `gold_schema_keywords` | 테이블을 가리킨다고 본 단어 ("처방", "환자", "수치") | 스키마 단어 |
| `gold_concept_gliner` | 의료 개체 텍스트와 라벨 ("고혈압:진단명 또는 질병명") | 의료 개체 |
| `gold_concept_dict` | 방문 유형·성별 표현, 도메인, 값 ("외래:Visit:9202") | 방문 유형·성별 |
| `gold_derived_schema` | 의료 개체에서 추론되는 스키마 묶음 ("진단") | 다운스트림 추론 (가정) |
| `gold_tables` | 이 질의의 SQL에 필요한 테이블 | 테이블 커버리지 |

- **스키마 단어 정답은 짧은 단위로 달려 있다** ("수치", "측정값"). 짧게 내는 GLiNER 쪽에 유리하고, "외래 방문 기록"처럼 구로 내는 LLM에 조금 불리하다. 위치 겹침 기준으로 완화했다.
- **엔진에 실제로 필요한 것에 가장 가까운 지표는 테이블 커버리지다.** 스키마 단어 F1은 "사람이 표시한 단어를 찾았나"이고, 테이블 커버리지는 "SQL에 필요한 테이블을 다 가리켰나"다.
- 정답 SQL 기준으로 잰 평가는 따로 있다: [02 스키마 키워드 추출 평가](02_스키마%20키워드%20추출%20평가%20(schema-dict%20v1).md), test_set 2,236문장, 정답 SQL의 테이블. 테이블 단위 정답이라 이 문서의 스키마 단어 지표와 직접 대응하지는 않는다.

### 이 비교에서 쓰는 지표

| 지표 | 무엇을 보나 | 맞힘 기준 | 왜 이 기준인가 |
|---|---|---|---|
| **스키마 단어** | EVENT / ATTRIBUTE / ENTITY 항목이 테이블을 가리키는 정답 단어("처방", "환자", "측정")를 찾았나 | 정답 단어와 **위치가 겹치면** 맞힘 | 방식마다 키워드 단위가 다르다("외래 방문 기록" vs "외래 방문"). 글자가 똑같아야 맞힘으로 치면 단위가 다른 쪽이 손해를 본다 |
| └ 형식 차이 제외 정밀도 | 위와 같되, 방문 유형·성별 표현("여성", "응급실")을 스키마 항목으로 낸 오탐을 뺌 | — | 정답셋은 이 표현을 스키마 단어가 아니라 별도 정답(방문 유형·성별)으로 둔다. 엔진 형식에서는 EVENT / ATTRIBUTE로 나갈 수밖에 없다 |
| **의료 개체** | DISEASE / DRUG / MEASUREMENT / PROCEDURE 항목이 정답 개체를 찾고 라벨까지 맞혔나 | 위치가 겹치고 **라벨이 같으면** 맞힘 | 위치는 맞는데 라벨만 틀리면 "라벨 오류"로 따로 센다(놓침 1 + 오탐 1). 라벨이 틀리면 다운스트림이 엉뚱한 의료 용어 사전을 찾는다 |
| **방문 유형·성별** | 정답 방문 표현(입원·외래·응급실 등)과 성별 표현(여성·남자 등) 23개를 맞는 자리로 냈나 | 위치가 겹치고, 방문은 EVENT / visit_occurrence, 성별은 ATTRIBUTE / person | 엔진 형식에 값(입원 vs 외래)을 담을 곳이 없어 값은 못 잰다. 엔진이 받을 수 있는 최선의 형태로 나왔는지만 본다 |
| **테이블 커버리지 (응답 그대로)** | 응답에 실린 `table`만으로 정답 SQL의 테이블을 **전부** 가리킨 문장 비율 | 문장 단위. 하나라도 빠지면 실패 | 키워드 추출 결과만으로 엔진이 필요한 테이블 단서를 다 받는지 본다 |
| └ 테이블 P / R | 위를 (문장, 테이블) 쌍 단위로 센 정밀도·재현율 | — | 커버리지는 엄격해서, 얼마나 가까운지는 P/R로 본다 |
| **테이블 커버리지 (다운스트림 추론 포함, 가정)** | 응답 table에 더해, 다운스트림이 의료 개체 라벨에서 테이블을 정한다고 가정했을 때(질병 → condition_occurrence 등) | 위와 같음 | 모든 방식이 의료 개체에는 table을 붙이지 않는다(형식 규칙). 의료 개체 쪽에서 테이블이 정해진다고 보면 어떻게 되는지 보는 **참고 지표**다. 이 값은 평가 도구가 만든 것이고 어느 방식도 내지 않는다. 라벨이 틀리면 테이블도 틀린다 |
| **조건 항목 수** | VALUE(값) / OPERATOR(비교·집계) / TIME(시점·기간) 항목 개수 | 정답 없음 (채점 안 함) | 정답셋에 이 항목의 정답이 없다. 낸 개수만 센다 |
| **형식 위반** | 엔진 형식 규칙(`table` 키 항상 존재, 의료 개체·조건 항목의 table은 null) 위반 건수 | — | 엔진이 받는 계약을 지키는지 본다 |

## 3. 결과

### 3.1 스키마 단어

| | TP | FP | FN | P | R | F1 | 형식 차이 제외 P |
|---|---|---|---|---|---|---|---|
| 파인튜닝 GLiNER | 105 | 11 | 18 | 90.5 | 85.4 | **87.9** | **99.1** (FP 11개 중 10개가 형식 차이) |
| LLM | 106 | 18 | 17 | 85.5 | 86.2 | 85.8 | 93.0 (FP 18개 중 10개가 형식 차이) |
| 제로샷 GLiNER (참고) | 99 | 106 | 24 | 48.3 | 80.5 | 60.4 | 51.8 (FP 106개 중 14개가 형식 차이) |
| GLiNER + 사전 매칭 (참고) | 111 | 6 | 12 | 94.9 | 90.2 | 92.5 | 100 (FP 6개 모두 형식 차이) |

- **파인튜닝 GLiNER:** 오탐은 거의 없고 놓침이 조금 많다.
  - 형식 차이가 아닌 오탐은 "T-score" 1개다.
  - 놓친 단어(FN 18개): 검사 ×3, 수치 ×3, 대상자 ×2, 사람 ×2, 수술 ×2, 검사결과 ×2, 내원 ×2, 재원, 급사.
  - 사전 매칭이 놓친 퇴원 ×2, 진료 ×2, 남녀, 먹고는 잡았다.
- **LLM:**
  - 실제 과잉 추출 8개: 날짜, 시행, 이력, 산모, 변화 등.
  - 스키마 단어를 의료 개체에 흡수하는 경우가 많다("INR 수치"를 MEASUREMENT 하나로).
- **제로샷 GLiNER (참고):** 조사·어미 조각(받 ×8, 한 ×5, 인 ×3)과 조건 표현(이상 ×6, 30일 ×3, 65세, 날짜 문자열)을 스키마로 낸다.
- **GLiNER + 사전 매칭 (참고):** 사전에 있는 단어는 정확하지만 사전에 없는 단어(퇴원, 진료, 재원, 먹고 등)를 놓친다.

| | TP | FP | FN | P | R | F1 | 라벨 오류 |
|---|---|---|---|---|---|---|---|
| 파인튜닝 GLiNER | 73 | 4 | 8 | **94.8** | 90.1 | 92.4 | 3 |
| LLM | 80 | 8 | 1 | 90.9 | **98.8** | **94.7** | **1** |
| 제로샷 GLiNER (참고) | 59 | 38 | 22 | 60.8 | 72.8 | 66.3 | 9 |
| GLiNER + 사전 매칭 (참고) | 74 | 11 | 7 | 87.1 | 91.4 | 89.2 | 7 |

라벨별 재현율

| 라벨 | 파인튜닝 GLiNER | LLM | 제로샷 GLiNER (참고) | GLiNER + 사전 매칭 (참고) |
|---|---|---|---|---|
| 진단명 (DISEASE) | 39 / 40 | 40 / 40 | 28 / 40 | 40 / 40 |
| 약물명 (DRUG) | 14 / 15 | 14 / 15 | 13 / 15 | 14 / 15 |
| 검사명 (MEASUREMENT) | 15 / 17 | **17 / 17** | 11 / 17 | 11 / 17 |
| 시술명 (PROCEDURE) | **5 / 9** | 9 / 9 | 7 / 9 | 9 / 9 |

**파인튜닝 GLiNER와 LLM의 차이는 시술명과 놓친 개체다.**
- 아예 못 찾은 개체: 대장내시경, 제왕절개, INR, 갑상선 기능 저하증, T-score.
- "위내시경 검사", "MRI 검사"처럼 뒤의 "검사"까지 묶어 검사명으로 낸 경우는 라벨 오류로 셌다. 정답은 위내시경·MRI를 시술명으로 둔다.
- 오탐은 LLM보다 적다(4 vs 8).

**참고 방식과 비교**
- 사전 매칭 방식의 약점이던 검사명 라벨은 좋아졌다(11 → 15 / 17).
- 제로샷 GLiNER는 질병명을 12개 놓치고, 스키마 단어를 의료 개체로 낸다("투여"를 시술명으로, "이력"을 검사명으로). 후보 라벨 18개가 서로 경쟁하는 것으로 보인다. 파인튜닝으로 이 문제가 거의 사라졌다.

### 3.3 방문 유형·성별

| | 표현을 잡음 | 도메인까지 맞음 |
|---|---|---|
| 파인튜닝 GLiNER | 18 / 23 | **18 / 23 (78%)** |
| LLM | 23 / 23 | 16 / 23 (70%) |
| 제로샷 GLiNER (참고) | 21 / 23 | 12 / 23 (52%) |
| GLiNER + 사전 매칭 (참고) | 14 / 23 | 12 / 23 (52%) |

- **파인튜닝 GLiNER:** 잡은 18개는 모두 도메인까지 맞다. 놓친 것은 재원, 119로 이송, 응급실, 외래, 남아다.
- **LLM:** 23개를 모두 잡았지만 7개는 다른 라벨로 냈다. 예: "남성"을 VALUE로, "입원 기간"을 TIME으로.
- **제로샷 GLiNER (참고):** 9개 라벨 오류. 응급실·남아·여환을 ENTITY/person으로, 퇴원을 death로 냈다.
- **GLiNER + 사전 매칭 (참고):** 사전에 없는 형태 변형("응급실 내원")과 어휘(여자, 여환, male, 퇴원, 재원)를 놓쳤다.

## 4. 해석

1. **키워드를 찾는 능력은 LLM과 비슷하다.**
   - 스키마 단어와 방문 유형·성별은 LLM보다 높다. 특히 방문 유형·성별은 잡은 것을 모두 맞는 라벨로 낸다.
   - 의료 컨셉은 진단명·약물명·검사명이 LLM과 비슷하고, 시술명만 약하다.
2. **약점은 학습 데이터 쪽 문제로 보인다.**
   - 시술명 누락(대장내시경, 제왕절개)과 "위내시경 검사"의 경계 문제는 학습 데이터의 시술명 예시(138개)와 경계 기준을 확인해 볼 일이다.
   - "대상자", "사람", "검사", "수치"처럼 흔한 스키마 단어를 놓치는 것도 학습 데이터의 라벨 범위를 확인해야 한다.
3. **운영 측면은 LLM보다 낫다.** 형식 위반이 없고, 결정적이고, CPU에서도 LLM보다 빠르다.
4. **LLM만 하는 일이 남아 있다.** 조건 항목(값·비교·시점)이다. 엔진이 이것을 쓰면 파인튜닝 GLiNER만으로는 대체할 수 없다.

## 5. 이 비교의 한계

- **정답셋 크기:** 정답셋이 50문장이다. 차이가 1~2개인 항목(약물명 등)은 의미가 없다. 시술명(4개 차이)과 스키마 단어, 방문 유형·성별 정도만 볼 만한 차이다.
- **정답의 기준:** 정답은 사람이 단 키워드 정답이고 정답 SQL 기반이 아니다. 스키마 단어 정답이 짧은 단위로 달려 있어 LLM에 조금 불리하다.
- **threshold:** 파인튜닝 GLiNER의 0.5를 검증하지 않았다. 놓침이 오탐보다 많아서 threshold를 낮추면 결과가 달라질 수 있다.
- **제로샷 vs 파인튜닝:** threshold가 다르다(0.2 vs 0.5). 둘의 차이가 전부 학습 효과는 아니다.
- **LLM 조건:** 테이블 목록 대체본, thinking 끔 조건이라 운영과 다를 수 있다.
- **조건 항목:** 정답이 없어 품질을 비교하지 못했다.
- **응답 시간:** 실행 환경이 달라 참고용이다.

## 6. 사용 판단에 필요한 것

| 순서 | 할 일 | 누가 | 영향 |
|---|---|---|---|
| 1 | 엔진이 조건 항목(VALUE / OPERATOR / TIME)을 쓰는지 확인 | 엔진 담당 | 쓴다면 별도 추출(규칙 기반 또는 학습 라벨 추가)이 필요. 대체의 전제 조건 |
| 2 | threshold 조정 (예: 0.3 / 0.4 / 0.5) | 평가 | 놓침이 줄어드는지 확인. 이 정답셋으로 고르면 이 셋은 개발셋이 된다 |
| 3 | 시술명 학습 데이터 점검 (대장내시경·제왕절개 같은 예시, "OO 검사" 경계 기준) | 학습 | 의료 컨셉 격차와 테이블 커버리지 격차(80% vs 90%)의 주원인 |
| 4 | 더 큰 홀드아웃 셋으로 재평가 | 평가 | NL2SQL 테스트셋 중 패러프레이즈 573건이 학습 데이터와 겹치지 않는다. 학습셋·val·SQL 변형은 학습 데이터와 거의 같은 문장이라 쓸 수 없다 |
| 5 | 엔진이 스키마 단어 없는 질의에서 테이블을 어디서 정하는지 확인 | 엔진 담당 | "다운스트림 추론 포함" 지표가 실제와 맞는지 결정 |
| 6 | 운영 테이블 목록과 thinking 설정으로 LLM 재평가 | 평가 | 기준선 수치 확정 |

## 7. 재현

```bash
C=../test_set/keyword_ext/keyword_eval_samples_50.csv
FT=<파인튜닝 서버>   # 사내 서버 주소
# 파인튜닝 GLiNER
python -m eval.csv_keyword_eval extract --system ke-compat --url $FT/keyword-extraction/llm-compat --csv $C --out eval/outputs/kw50_ft-gliner_compat.jsonl
python -m eval.csv_keyword_eval score --csv $C --pred eval/outputs/kw50_ft-gliner_compat.jsonl --out-dir eval/runs/kw50_ft-gliner_compat
# LLM
python -m eval.csv_keyword_eval extract --system prod-llm --csv $C --out eval/outputs/kw50_prod_llm.jsonl --concurrency 4
python -m eval.csv_keyword_eval score --csv $C --pred eval/outputs/kw50_prod_llm.jsonl --out-dir eval/runs/kw50_prod_llm
# 참고: 제로샷 GLiNER
python -m eval.csv_keyword_eval extract --system ke-compat --url $FT/keyword-extraction/llm-compat/zero-shot --csv $C --out eval/outputs/kw50_zs-gliner_compat.jsonl
python -m eval.csv_keyword_eval score --csv $C --pred eval/outputs/kw50_zs-gliner_compat.jsonl --out-dir eval/runs/kw50_zs-gliner_compat
# 참고: GLiNER + 사전 매칭 (로컬 KE-r3)
python -m eval.csv_keyword_eval extract --system ke-compat --csv $C --out eval/outputs/kw50_ke-r3_compat.jsonl
python -m eval.csv_keyword_eval score --csv $C --pred eval/outputs/kw50_ke-r3_compat.jsonl --out-dir eval/runs/kw50_ke-r3_compat
```

방문 유형·성별 도메인 맞음, 라벨별 재현율, 형식 위반 건수는 채점기에 아직 없어서 출력 jsonl과 `kw50_per_query.json`으로 따로 계산했다.
