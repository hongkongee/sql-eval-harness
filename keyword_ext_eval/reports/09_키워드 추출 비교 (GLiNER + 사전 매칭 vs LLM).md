# 키워드 추출 비교: GLiNER + 사전 매칭 vs LLM

- 작성일: 2026-10-28
- 질문: **새로 만든 키워드 추출 방식(GLiNER + 사전 매칭)으로 지금 운영 중인 LLM 방식을 대체할 수 있는가**
- 비교 대상
  - **GLiNER + 사전 매칭**: 새로 만든 방식. 사전 매칭과 의료 개체명 인식 모델(GLiNER)을 함께 쓴다
  - **파인튜닝 GLiNER**: GLiNER-BioMed를 엔진 형식 라벨로 파인튜닝한 모델. 사전 없이 모델 하나로 모든 키워드를 낸다
  - **LLM**: 지금 Text-to-SQL 엔진에 들어가 있는 방식. 프롬프트로 LLM에게 키워드를 뽑게 한다
- 세 방식 모두 엔진이 받는 같은 형식 `[{keyword, label, table}]`으로 결과를 낸다. 형식 명세는 [08 응답 인터페이스](08_키워드%20추출%20응답%20인터페이스%20(llm-compat%20·%20운영%20LLM).md)에 있다. 같은 정답셋, 같은 채점 방식으로 쟀다.

## 요약

| 항목 | 지표 | GLiNER + 사전 매칭 | 파인튜닝 GLiNER | LLM |
|---|---|---|---|---|
| 스키마 키워드 | F1 | **92.5** | 87.9 | 85.8 |
| 의료 컨셉 키워드 | F1 | 89.2 | 92.4 | **94.7** |
| 방문 유형·성별 키워드 | 맞힌 수 / 23 | 12 | **18** | 16 |

- GLiNER + 사전 매칭에서는 스키마 키워드와 방문 유형·성별 키워드를 사전 매칭이 만들고, 의료 컨셉 키워드를 GLiNER가 만든다.
- 파인튜닝 GLiNER는 세 항목을 모두 모델 하나가 만든다. 학습 데이터에 의료 컨셉, 방문 유형·성별 라벨도 들어 있다(1.2절).
- 정답은 사람이 직접 단 키워드 정답이다. 정답 SQL에서 뽑은 것이 아니다. 자세한 내용은 2절에 있다.
- 테이블 커버리지, 조건 항목, 형식 준수, 응답 시간은 3절에 있다.

**결론.** 아직 그대로 대체하기는 이르다. GLiNER + 사전 매칭은 스키마 단어, 형식 안정성, 속도에서 앞선다. 하지만 엔진이 쓰는 정보 중 세 가지가 LLM보다 약하거나 없다.
1. 검사명 라벨
2. 방문·성별 어휘
3. 조건 항목(값·비교·시점). 엔진이 쓰는 경우에 한한다

이 세 가지가 대체 여부를 가른다(6절).

**파인튜닝 GLiNER는** 사전 없이도 의료 컨셉과 방문 유형·성별을 GLiNER + 사전 매칭보다 잘 낸다. 방문 유형·성별은 LLM보다도 많이 맞힌다. 대신 사전에 있는 스키마 단어를 놓친다("대상자", "사람", "검사", "수치"). 조건 항목은 내지 않는다. threshold를 검증하지 않은 첫 결과라서 결론에는 아직 넣지 않는다.

## 1. 테스트 조건

### 1.1 GLiNER + 사전 매칭

- **방식:** 사전 매칭과 GLiNER 개체명 인식 결과를 합쳐 엔진 형식으로 변환한다.
- **모델:** GLiNER `Ihor/gliner-biomed-large-v1.0`. 의료 특화 모델이고 파인튜닝 없이 제로샷으로 쓴다.
  - 라벨 4개: 진단명 또는 질병명, 약물명, 검사명 또는 측정 항목, 시술명 또는 수술명
  - threshold 0.3
- **사전:**
  - 스키마 사전: 대표 키워드 13개, 표면형 39개
  - 방문 유형·성별 사전
- **실행 환경:** 로컬 Docker 컨테이너. 한 건씩 순차 호출했다.
- **내부 이름:** KE-r3 `/keyword-extraction/llm-compat`, gliner-entity-router `5708649`

### 1.2 파인튜닝 GLiNER

- **방식:** 파인튜닝한 GLiNER 하나로 모든 키워드를 뽑고 엔진 형식으로 변환한다. 사전은 쓰지 않는다.
- **베이스 모델:** GLiNER `Ihor/gliner-biomed-large-v1.0`
- **체크포인트:** `./models/llm-compat-v1/`. eval_loss가 가장 낮은 지점(`load_best_model_at_end`)을 저장한 것이다.
- **학습 데이터:** 시드 질의 769건을 변환한 764건(gliner-entity-router `data/processed/llm_compat_dataset.jsonl`). train 688 / eval 76으로 나눴다(seed 42, 9:1).
  - 스키마 라벨만 있는 게 아니다. 의료 컨셉 라벨 4개(진단명 358, 약물명 281, 시술명 138, 검사명 62)와 방문 유형 21, 성별 10도 들어 있다.
- **추론 라벨:** `llm_compat_map.yaml`의 schema·concept 키 18개(중복 제거)를 GLiNER 후보 라벨로 그대로 쓴다.
- **threshold:** 0.5 (`FINETUNED_THRESHOLD` 기본값). **아직 검증하지 않은 값이다.**
- **실행 환경:** 사내 서버의 API(`POST /keyword-extraction/llm-compat`). CPU로 추론하고, 한 건씩 순차 호출했다.
- **정답셋 중복 점검:** 학습 데이터 764건과 정답셋 50문장을 대조했다.
  - 똑같은 문장은 없다.
  - 가장 비슷한 쌍은 "현재 연도 기준 연령 65세 이상이고 골다공증 진단을 받은 여성 환자."와 학습 문장 "현재 연도 기준 연령 65세 이상이고 골다공증 진단인 환자."다(4글자 단위 유사도 0.6). 그 밖에는 0.53 이하다.

### 1.3 LLM

- **방식:** 시스템 프롬프트로 LLM에게 키워드와 라벨을 JSON으로 출력하게 한다.
- **모델:** Qwen3.8-Flash-Next-FP8. vLLM으로 서빙하고 모델명은 `qwen-vl`이다.
  - temperature 0
  - thinking 끔
- **사전:** 없다. 프롬프트에 테이블 목록과 라벨 정의를 넣는다.
- **실행 환경:** 원격 서버에 프록시를 거쳐 4건씩 동시 호출했다.
- **내부 이름:** prod-llm, 운영 시스템 프롬프트 sha256 `1bb9b021…`

**⚠ 운영과 조건이 다를 수 있다.**
- 프롬프트의 테이블 목록은 운영 코드를 받지 못해 대체본을 넣었다.
- 운영에서 thinking을 켜는지는 확인이 필요하다.
- 응답 시간은 실행 환경이 달라 참고용이다.

### 1.4 공통 조건

- **정답셋:** 사람이 직접 정답을 단 50문장이다. 파일은 `test_set/keyword_ext/keyword_eval_samples_50.csv`이다.
  - 정답 SQL에서 뽑은 것이 아니다. 자세한 내용은 2절에 있다.
  - 어느 방식의 개발에도 쓰지 않았다. 파인튜닝 GLiNER의 학습 데이터와도 겹치지 않는다(1.2절).
- **채점:** 모든 방식의 응답을 같은 해석기로 읽고 같은 채점기로 채점한다.

## 2. 지표 설명

### 기본 용어

| 용어 | 뜻 |
|---|---|
| TP (맞힘) | 정답에 있는 것을 냈다 |
| FP (오탐) | 정답에 없는 것을 냈다 |
| FN (놓침) | 정답에 있는 것을 안 냈다 |
| 정밀도 P | TP / (TP + FP). 낸 것 중 맞은 비율. 낮으면 엉뚱한 것을 많이 낸다 |
| 재현율 R | TP / (TP + FN). 정답 중 찾은 비율. 낮으면 많이 놓친다 |
| F1 | P와 R의 조화평균. 둘 중 낮은 쪽에 끌려간다 |

### 정답은 어디서 왔나

정답셋 CSV(50문장)는 **사람이 문장마다 직접 단 정답**이다. 정답 SQL에서 뽑은 값이 아니다. CSV에 SQL 열이 없고, 아래 정답이 모두 수작업 라벨이다.

| 정답 열 | 내용 | 쓰는 지표 |
|---|---|---|
| `gold_schema_keywords` | 테이블을 가리킨다고 본 단어 ("처방", "환자", "수치") | 스키마 단어 |
| `gold_concept_gliner` | 의료 개체 텍스트와 라벨 ("고혈압:진단명 또는 질병명") | 의료 개체 |
| `gold_concept_dict` | 방문 유형·성별 표현, 도메인, 값 ("외래:Visit:9202") | 방문 유형·성별 |
| `gold_derived_schema` | 의료 개체에서 추론되는 스키마 묶음 ("진단") | 다운스트림 추론 (가정) |
| `gold_tables` | 이 질의의 SQL에 필요한 테이블 | 테이블 커버리지 |

- **스키마 단어 정답은 사전 방식에 유리하다.** 사전 표면형 단위("수치", "측정값")로 달려 있기 때문이다. 구로 묶어 내는 LLM은 위치 겹침 기준으로 완화해도 조금 불리하다.
- **엔진에 실제로 필요한 것에 가장 가까운 지표는 테이블 커버리지다.** 스키마 단어 F1은 "사람이 표시한 단어를 찾았나"이고, 테이블 커버리지는 "SQL에 필요한 테이블을 다 가리켰나"다.
- 정답 SQL 기준으로 잰 평가는 따로 있다: [02 스키마 키워드 추출 평가](02_스키마%20키워드%20추출%20평가%20(schema-dict%20v1).md), test_set 2,236문장, 정답 SQL의 테이블. 테이블 단위 정답이라 이 문서의 스키마 단어 지표와 직접 대응하지는 않는다.

### 이 비교에서 쓰는 지표

"결과를 만드는 것"은 GLiNER + 사전 매칭 쪽에서 그 지표의 결과가 어느 구성 요소에서 나오는지다. LLM은 모든 지표를 모델 하나가 만든다.

| 지표 | 무엇을 보나 | 맞힘 기준 | 결과를 만드는 것 | 왜 이 기준인가 |
|---|---|---|---|---|
| **스키마 단어** | EVENT / ATTRIBUTE / ENTITY 항목이 테이블을 가리키는 정답 단어("처방", "환자", "측정")를 찾았나 | 정답 단어와 **위치가 겹치면** 맞힘 | **스키마 사전.** 단, 형식 변환 규칙이 GLiNER 개체 안의 스키마 단어를 지워 놓침 12개 중 5개가 생겼다. 사전만의 점수는 F1 96.3 (07 보고서 3.2절) | LLM은 "외래 방문 기록"처럼 구로 내고 GLiNER + 사전 매칭은 "외래 방문"처럼 짧게 낸다. 글자가 똑같아야 맞힘으로 치면 단위가 다른 쪽이 손해를 본다 |
| └ 형식 차이 제외 정밀도 | 위와 같되, 성별 값("여성", "남성")을 ATTRIBUTE로 낸 오탐을 뺌 | — | 방문·성별 사전 | 정답셋은 성별 값을 스키마 단어가 아니라 별도 정답(방문·성별)으로 둔다. 엔진 형식에서는 이 값이 ATTRIBUTE로 나갈 수밖에 없다 |
| **의료 개체** | DISEASE / DRUG / MEASUREMENT / PROCEDURE 항목이 정답 개체를 찾고 라벨까지 맞혔나 | 위치가 겹치고 **라벨이 같으면** 맞힘 | **GLiNER** (거의 순수). 후처리는 개체 양 끝의 스키마 단어 잘라내기, 사전 결과와 같은 위치의 GLiNER 결과 버리기뿐 | 위치는 맞는데 라벨만 틀리면 "라벨 오류"로 따로 센다(놓침 1 + 오탐 1). 라벨이 틀리면 다운스트림이 엉뚱한 의료 용어 사전을 찾는다 |
| **방문 유형·성별** | 정답 방문 표현(입원·외래·응급실 등)과 성별 표현(여성·남자 등) 23개를 맞는 자리로 냈나 | 위치가 겹치고, 방문은 EVENT / visit_occurrence, 성별은 ATTRIBUTE / person | **사전** (방문·성별 사전, 일부는 스키마 사전의 "방문" 묶음. 예: "입원") | 엔진 형식에 값(입원 vs 외래)을 담을 곳이 없어 값은 못 잰다. 엔진이 받을 수 있는 최선의 형태로 나왔는지만 본다 |
| **테이블 커버리지 (응답 그대로)** | 응답에 실린 `table`만으로 정답 SQL의 테이블을 **전부** 가리킨 문장 비율 | 문장 단위. 하나라도 빠지면 실패 | **사전** (table은 스키마 사전·방문·성별 사전 항목에만 붙음) + 형식 변환 규칙 | 키워드 추출 결과만으로 엔진이 필요한 테이블 단서를 다 받는지 본다 |
| └ 테이블 P / R | 위를 (문장, 테이블) 쌍 단위로 센 정밀도·재현율 | — | 위와 같음 | 커버리지는 엄격해서, 얼마나 가까운지는 P/R로 본다 |
| **테이블 커버리지 (다운스트림 추론 포함, 가정)** | 응답 table에 더해, 다운스트림이 의료 개체 라벨에서 테이블을 정한다고 가정했을 때(질병 → condition_occurrence 등) | 위와 같음 | 사전 + **GLiNER 라벨** (라벨이 틀리면 테이블도 틀림) | 두 방식 모두 의료 개체에는 table을 붙이지 않는다(형식 규칙). 실제 엔진처럼 의료 개체 쪽에서 테이블이 정해진다고 보면 어떻게 되는지 보는 **참고 지표**다. 이 값은 평가 도구가 만든 것이고 어느 방식도 내지 않는다 |
| **조건 항목 수** | VALUE(값) / OPERATOR(비교·집계) / TIME(시점·기간) 항목 개수 | 정답 없음 (채점 안 함) | 없음 (구현 안 됨) | 정답셋에 이 항목의 정답이 없다. 낸 개수만 센다 |
| **형식 위반** | 엔진 형식 규칙(`table` 키 항상 존재, 의료 개체·조건 항목의 table은 null) 위반 건수 | — | 형식 변환 계층 (서버가 형식을 검증) | 엔진이 받는 계약을 지키는지 본다 |

## 3. 결과

### 3.1 스키마 단어

| | TP | FP | FN | P | R | F1 | 형식 차이 제외 P |
|---|---|---|---|---|---|---|---|
| GLiNER + 사전 매칭 | 111 | 6 | 12 | 94.9 | 90.2 | **92.5** | **100** (FP 6개 모두 형식 차이) |
| 파인튜닝 GLiNER | 105 | 11 | 18 | 90.5 | 85.4 | 87.9 | 99.1 (FP 11개 중 10개가 형식 차이) |
| LLM | 106 | 18 | 17 | 85.5 | 86.2 | 85.8 | 93.0 (FP 18개 중 10개가 형식 차이) |

- **GLiNER + 사전 매칭:** 사전에 있는 단어를 정확히 낸다.
  - FN 12개: 사전에 없는 단어(퇴원, 진료, 재원, 먹고 등)와, 변환 규칙이 의료 개체 안의 스키마 단어를 지운 경우("응급수술"의 "수술", "혈압 측정일"의 "측정" 등. 07 보고서 3.2절)다.
- **파인튜닝 GLiNER:** 오탐은 거의 없고 놓침이 많다.
  - 사전 방식이 놓친 단어를 잡았다: 퇴원 ×2, 진료 ×2, 남녀, 먹고, 측정, 환자.
  - 대신 사전에 있는 단어를 놓쳤다: 검사 ×3, 수치 ×3, 대상자 ×2, 사람 ×2, 수술 ×2, 검사결과 ×2, 내원 ×2, 재원, 급사(FN 18개).
  - 형식 차이가 아닌 오탐은 "T-score" 1개다.
- **LLM:**
  - 실제 과잉 추출 8개: 날짜, 시행, 이력, 산모, 변화 등.
  - 스키마 단어를 의료 개체에 흡수하는 경우가 많다("INR 수치"를 MEASUREMENT 하나로).

### 3.2 의료 개체

| | TP | FP | FN | P | R | F1 | 라벨 오류 |
|---|---|---|---|---|---|---|---|
| GLiNER + 사전 매칭 | 74 | 11 | 7 | 87.1 | 91.4 | 89.2 | 7 |
| 파인튜닝 GLiNER | 73 | 4 | 8 | 94.8 | 90.1 | 92.4 | 3 |
| LLM | 80 | 8 | 1 | 90.9 | 98.8 | **94.7** | **1** |

라벨별 재현율

| 라벨 | GLiNER + 사전 매칭 | 파인튜닝 GLiNER | LLM |
|---|---|---|---|
| 진단명 (DISEASE) | 40 / 40 | 39 / 40 | 40 / 40 |
| 약물명 (DRUG) | 14 / 15 | 14 / 15 | 14 / 15 |
| 검사명 (MEASUREMENT) | **11 / 17** | 15 / 17 | **17 / 17** |
| 시술명 (PROCEDURE) | 9 / 9 | **5 / 9** | 9 / 9 |

**GLiNER + 사전 매칭과 LLM의 차이는 거의 전부 검사명이다.** GLiNER는 검사명 6개를 진단명·약물명으로 붙인다. 개체 위치는 두 방식 모두 다 찾는다.

**파인튜닝 GLiNER는 검사명 라벨 오류가 줄었지만 시술명을 놓친다.**
- 검사명은 11개에서 15개로 늘었다. 라벨 오류는 7개에서 3개로 줄었다.
- 아예 못 찾은 개체가 생겼다: 대장내시경, 제왕절개, INR, 갑상선 기능 저하증, T-score.
- "위내시경 검사", "MRI 검사"처럼 뒤의 "검사"까지 묶어 검사명으로 낸 경우는 라벨 오류로 셌다.

### 3.3 방문 유형·성별

| | 표현을 잡음 | 도메인까지 맞음 |
|---|---|---|
| GLiNER + 사전 매칭 | 14 / 23 | 12 / 23 (52%) |
| 파인튜닝 GLiNER | 18 / 23 | **18 / 23 (78%)** |
| LLM | 23 / 23 | 16 / 23 (70%) |

- **GLiNER + 사전 매칭이 놓친 것:** 사전에 없는 형태 변형("응급실 내원", "외래에서")과 어휘(여자, 여환, male, 퇴원, 재원)다. 사전 보강으로 줄일 수 있다.
- **파인튜닝 GLiNER:** 잡은 18개는 모두 도메인까지 맞다. 사전 방식이 놓친 여자, 여환, male, 퇴원을 잡았다. 놓친 것은 재원, 119로 이송, 응급실, 외래, 남아다.
- **LLM이 틀린 것:** 23개를 모두 잡았지만 7개는 다른 라벨로 냈다. 예: "남성"을 VALUE로, "입원 기간"을 TIME으로.

### 3.4 테이블

| 지표 | GLiNER + 사전 매칭 | 파인튜닝 GLiNER | LLM |
|---|---|---|---|
| 응답 그대로: 커버리지 | **40%** | **40%** | 36% |
| 응답 그대로: P / R / F1 | 68.0 / 60.3 / 63.9 | 70.7 / 60.3 / 65.1 | 66.3 / 59.5 / 62.7 |
| 응답 그대로: person 제외 P / R | 98.3 / 57.8 | 100 / 54.9 | 98.2 / 53.9 |
| 다운스트림 추론 포함 (가정): 커버리지 | 84% | 80% | **90%** |
| 다운스트림 추론 포함 (가정): P / R / F1 | 72.5 / 93.1 / 81.5 | 76.3 / 91.4 / 83.1 | 73.0 / 95.7 / 82.8 |

테이블별 재현율 (응답 그대로 → 다운스트림 추론 포함)

| 테이블 | GLiNER + 사전 매칭 | 파인튜닝 GLiNER | LLM |
|---|---|---|---|
| person | 79 → 79 | 100 → 100 | 100 → 100 |
| observation_period | 100 → 100 | 100 → 100 | 100 → 100 |
| visit_occurrence | 77 → 77 | 69 → 69 | 77 → 77 |
| condition_occurrence | 32 → 100 | 32 → 97 | 34 → 100 |
| drug_exposure | 86 → 93 | 93 → 93 | 93 → 93 |
| procedure_occurrence | 20 → 100 | 10 → **60** | 20 → 100 |
| measurement | **73** → 93 | 60 → 100 | **40** → 100 |
| death | 100 → 100 | 100 → 100 | 88 → 88 |

- **응답만 보면 비슷하다.** 둘 다 40% 안팎이다. 질병·시술 이름만 있고 "진단"·"시술" 같은 단어가 없는 문장이 많기 때문이다.
  - GLiNER + 사전 매칭은 "측정"·"수치" 같은 단어를 남겨 measurement가 높다.
  - LLM은 "환자"를 person으로 더 많이 연결한다.
- **다운스트림 추론을 포함하면 LLM이 6%p 높다.** 3.2절의 검사명 라벨, 3.3절의 방문·성별 차이가 테이블로 이어진 결과다.
- **파인튜닝 GLiNER는 응답 그대로는 GLiNER + 사전 매칭과 같고, 다운스트림 추론을 포함하면 4%p 낮다.** 시술명을 놓쳐서 procedure_occurrence가 60%에 그친다(3.2절).

### 3.5 조건 항목

| | VALUE (값) | OPERATOR (비교·집계) | TIME (시점·기간) | 합계 |
|---|---|---|---|---|
| GLiNER + 사전 매칭 | 0 | 0 | 0 | 0 |
| 파인튜닝 GLiNER | 0 | 0 | 0 | 0 |
| LLM | 16 | 20 | 12 | 48 |

GLiNER + 사전 매칭은 1단계 구현 범위에서 이 항목을 내지 않는다. 파인튜닝 GLiNER도 학습 라벨과 추론 라벨에 이 항목이 없다. 정답이 없어 LLM의 품질은 재지 않았다. 엔진이 이 항목을 SQL 조건(WHERE, 날짜 범위, 집계)에 쓰는지가 가장 큰 미확인 사항이다.

### 3.6 형식 준수와 운영 특성

| 항목 | GLiNER + 사전 매칭 | 파인튜닝 GLiNER | LLM |
|---|---|---|---|
| JSON 파싱 실패 | 0 / 50 | 0 / 50 | 0 / 50 |
| `table` 키 누락 | 0 | 0 | 13건 (의료 개체 항목) |
| 의료 개체·조건 항목에 table 지정 | 0 | 0 | 2건 (MEASUREMENT에 measurement) |
| 원문에 없는 keyword | 0 | 0 | 0 |
| 같은 입력 → 같은 출력 | 보장 (사전 + 결정적 추론) | 결정적 추론 (반복 호출로는 확인 안 함) | 보장 안 됨 (temperature 0이라도) |
| 평균 응답 시간 | 0.67초 (로컬) | **0.47초** (사내 서버, 순차) | 1.70초 (원격, 동시 4) |
| 실패 형태 | HTTP 오류 코드 | HTTP 오류 코드 | 빈 응답, JSON 아닌 텍스트 가능 |
| 고치는 방법 | 사전·매핑 파일 수정 (결과 예측 가능) | 학습 데이터 수정 후 재학습 | 프롬프트 수정 (다른 문장에 미치는 영향 예측 어려움) |

## 4. 해석

1. **두 방식의 강점이 정확히 갈린다.**
   - GLiNER + 사전 매칭은 "사전에 있는 것"을 정확하고 빠르고 일관되게 낸다.
   - LLM은 "문맥으로 판단해야 하는 것"(검사명 라벨, 형태가 다양한 방문·성별 표현, 값·시점 표현)에 강하다.
2. **GLiNER + 사전 매칭의 약점 셋은 성격이 다르다.**
   - 방문·성별: 사전 보강이면 되는 문제
   - 검사명 라벨: 모델 쪽 문제(라벨 문구 실험, 파인튜닝)
   - 조건 항목: 새 기능(규칙 기반 추출)
3. **LLM의 약점은 형식과 예측 가능성이다.**
   - table 키 누락처럼 형식 규칙을 어기는 응답이 나온다. 엔진이 너그럽게 읽어야 한다(08 문서 7절).
   - 같은 질의에도 결과가 바뀔 수 있다.

## 5. 이 비교의 한계

- **정답셋 크기:** 정답셋이 50문장이다. 차이가 1~2개인 항목(약물명, 시술명 등)은 의미가 없다. 검사명(6개 차이)과 스키마 단어 정도만 신뢰할 만한 차이다.
- **정답의 기준:** 정답은 사람이 단 키워드 정답이고 정답 SQL 기반이 아니다. 특히 스키마 단어 정답이 사전 표면형 단위("수치", "측정값")로 달려 있다. 사전을 쓰는 GLiNER + 사전 매칭에 조금 유리하다. 위치 겹침 기준으로 완화했지만 완전히 없애지는 못했다.
- **LLM 조건:** 테이블 목록 대체본, thinking 끔 조건이라 운영과 다를 수 있다.
- **조건 항목:** 정답이 없어 품질을 비교하지 못했다.
- **파인튜닝 GLiNER:** threshold 0.5를 검증하지 않았다. 놓침이 많은 편이라 threshold를 낮추면 결과가 달라질 수 있다. 응답 시간도 실행 환경이 달라 참고용이다.

## 6. 대체 판단에 필요한 것

| 순서 | 할 일 | 누가 | 영향 |
|---|---|---|---|
| 1 | 엔진이 조건 항목(VALUE / OPERATOR / TIME)을 쓰는지 확인 | 엔진 담당 | 쓴다면 GLiNER + 사전 매칭에 규칙 기반 추출(나이·숫자·날짜·기간, 비교어 사전)이 필요. 대체의 전제 조건 |
| 2 | 엔진이 스키마 단어 없는 질의에서 테이블을 어디서 정하는지 확인 | 엔진 담당 | "다운스트림 추론 포함" 지표가 실제와 맞는지 결정 |
| 3 | 운영 테이블 목록과 thinking 설정으로 LLM 재평가 | 평가 | LLM의 테이블 수치 확정 |
| 4 | 방문·성별 사전 보강 (형태 변형, 어휘) | API | 방문·성별 격차(12 vs 16) 축소. 이 정답셋을 보고 고치면 이후 이 셋은 개발셋 |
| 5 | 검사명 라벨 오류 대응 | API (모델) | 의료 개체 격차(89 vs 95)와 테이블 격차(84 vs 90)의 주원인 |
| 6 | 변환 규칙 수정: 의료 개체 안의 스키마 단어를 지우지 않게 | API | 스키마 단어 6개, 테이블 단서 4개 회복 |
| 7 | 새 held-out 정답셋 (조건 항목 정답 포함) | 평가 | 4·5번 이후 공정한 재비교, 조건 항목 품질 비교 |

## 7. 재현

```bash
C=../test_set/keyword_ext/keyword_eval_samples_50.csv
python -m eval.csv_keyword_eval extract --system ke-compat --csv $C --out eval/outputs/kw50_ke-r3_compat.jsonl   # GLiNER + 사전 매칭
python -m eval.csv_keyword_eval extract --system prod-llm  --csv $C --out eval/outputs/kw50_prod_llm.jsonl --concurrency 4   # LLM

# 파인튜닝 GLiNER: --url에 사내 서버의 /keyword-extraction/llm-compat 주소를 넣는다
python -m eval.csv_keyword_eval extract --system ke-compat --url <파인튜닝 서버>/keyword-extraction/llm-compat --csv $C --out eval/outputs/kw50_ft-gliner_compat.jsonl
python -m eval.csv_keyword_eval score --csv $C --pred eval/outputs/kw50_ft-gliner_compat.jsonl --out-dir eval/runs/kw50_ft-gliner_compat
```

방문·성별 도메인 맞음, 라벨별 재현율, 형식 위반 건수는 채점기에 아직 없어서 출력 jsonl과 `kw50_per_query.json`으로 따로 계산했다.
