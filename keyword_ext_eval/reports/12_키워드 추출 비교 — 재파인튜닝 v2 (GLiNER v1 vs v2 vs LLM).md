# 키워드 추출 비교: 재파인튜닝 v2 (GLiNER v1 vs v2 vs LLM)

- 작성일: 2026-11-09 (2026-11-10 수정: 서비스의 라벨 순서를 고정한 뒤 v2를 다시 돌린 결과로 v2 수치를 모두 교체)
- 질문: 검증셋을 컨셉 단위로 나누고 epoch을 줄여 다시 학습한 v2가, 처음 보는 의료 컨셉(특히 시술명)을 v1보다 잘 잡는가
- 비교 대상
  - **v1** (`llm-compat-v1`): 09~11에서 평가한 기존 파인튜닝 GLiNER. 무작위 10% 검증셋, 25 epoch
  - **v2** (`llm-compat-v2`): 이번에 다시 학습한 모델. 컨셉 단위 검증셋, epoch 8 체크포인트
  - **LLM**: 09~11과 같은 결과를 그대로 썼다(다시 돌리지 않음)
- 테스트셋: 09~11에서 쓴 세 셋을 그대로 다시 돌렸다
  - **새 정답셋 100**(11): 정답 의료 컨셉 227개가 모두 학습 데이터에 없다. 이 보고서의 주 판단 기준이다
  - 50문장(09), 패러프레이즈 573(10): 보조로 확인
- 배경: 11에서 v1의 시술명 재현율이 27 / 45(60%)로, 파인튜닝 전 제로샷 모델(35 / 45)보다 낮았다. threshold를 0.3으로 낮춰도 놓친 시술명은 돌아오지 않았다(11의 3.6절). 학습 중에 원래 알던 시술명을 잃은 것으로 보고, 검증 방식과 epoch을 바꿔 다시 학습했다.

- **재현율 ②가 키워드 추출의 실제 역할에 가장 가까운 지표다.** 라벨은 뒤의 컨셉 RAG가 concept_id를 찾으며 다시 정하므로, 키워드 추출은 의료 컨셉을 빠짐없이 의료 컨셉으로 넘기면 된다.
  - 의료 라벨끼리 바뀐 것(시술명을 검사명으로 냄 등)은 맞힌 것으로 센다.
  - 의료 컨셉을 스키마 단어로 낸 것은 놓친 것으로 센다. 스키마 항목은 컨셉 RAG로 가지 않기 때문이다.
  - 전제: RAG가 키워드 추출 라벨을 검색 조건(도메인 필터 등)으로 쓰지 않아야 한다. 확인이 필요하다.
- ③은 스키마로 낸 것까지 찾은 것으로 세서 성능을 부풀린다. 제로샷은 ③ 224 / 227이지만 ② 187 / 227이다(2.1절).
- 이 기준으로 보면 v2의 시술명(37 / 45, 82%)은 11에서 목표 후보로 잡은 제로샷 수준(78%)을 넘는다. LLM과의 격차(전체 91.6% vs 100%)는 그대로다.
- 정밀도는 아직 라벨까지 일치 기준으로만 셌다. 라벨을 무시하면 오탐 기준도 바뀌므로 ②와 짝이 되는 정밀도는 따로 계산해야 한다.

**결론.** v2는 v1과 점수가 거의 같다(의료 컨셉 F1 88.0 → 87.5). 다만 속을 보면 두 가지가 반대로 움직였다.
1. **키워드를 찾는 능력은 좋아졌다.** 라벨을 따지지 않고 위치만 보면, 놓친 의료 컨셉이 25개에서 14개로 줄었다. 시술명은 34 / 45에서 40 / 45가 됐다. ECMO, CRRT, ERCP, CPR, PET-CT, 간이식, 기계환기를 새로 잡았다. 학습 방식을 바꾼 목적(처음 보는 표현을 놓치지 않기)은 이 부분에서 달성됐다.
2. **대신 라벨을 더 많이 틀린다** (12 → 21). 특히 의료 컨셉을 스키마 단어로 내는 경우가 1개에서 5개로 늘었다(요추 천자, 수혈, 유방 보존술, 섬망, 요산). 찾은 시술명 40개 중 32개만 시술명 라벨을 받았다.
3. 그래서 정답 라벨까지 맞힌 시술명은 32 / 45(71%)로, 11에서 목표 후보로 잡은 제로샷 수준(35 / 45, 78%)에 못 미친다. 다만 라벨을 RAG가 다시 정한다는 전제로 재현율 ②(의료 컨셉으로 냄, 라벨 무관)를 보면 37 / 45(82%)로 목표를 넘는다.
4. 스키마 키워드는 거의 같고(겹침 F1 83.5 → 83.0), 방문 유형·성별은 조금 나빠졌다(22 → 20).
   - 환자를 가리키는 다른 말(사람, 대상자, 소아, 아이, 피험자, 환아)을 잃었다.
   - 응급실과 외래를 하나씩 더 놓쳤다.

**다음 단계 판단.** 남은 문제는 일반화보다 **라벨 경계**, 특히 의료 컨셉과 스키마 단어의 경계다.
- **라벨을 나눠 두 번 호출하는 방안은 시험해 봤고 효과가 없었다**(5절). 재현율은 같거나 조금 낮고, 응답 시간은 두 배 가까이 늘었다.
- 같은 시험에서 **라벨 순서만 바꿔도 결과가 흔들린다**는 것도 확인했다. 의료 컨셉 ②는 205~210, 시술명 ②는 35~38 사이에서 움직였다.
  - 그래서 서비스가 라벨을 `llm_compat_map.yaml` 순서로 넘기도록 고정했다. 이 보고서의 v2 수치는 모두 고정 후 결과다.
  - 고정 후에도 v1 대비 개선은 재현율 ② +7(3.1%p), 시술명 ② +4로 작다. 추가 파인튜닝은 보류한다(6절).

## 1. 테스트 조건

- **v2 모델:** `POST <파인튜닝 서버>/keyword-extraction/llm-compat`
  - v1과 같은 서버, 같은 API다. 내부 모델만 바꿨다.
  - threshold 0.3(`FINETUNED_THRESHOLD`), 사내 서버 CPU, 순차 호출
  - 실패: 100문장 0 / 100, 50문장 0 / 50, 패러프레이즈 0 / 573
  - 라벨 순서: 서비스가 `llm_compat_map.yaml`에 적힌 순서(스키마 13개 → 컨셉, 중복 제거 18개)로 라벨을 넘기도록 고정한 뒤 돌렸다(5절). 같은 100문장을 두 번 돌려 응답이 100건 모두 같은 것을 확인했다.
  - v1과 제로샷은 순서를 고정하기 전 결과다. 그래서 v1 수치에도 순서에 따른 흔들림이 조금 섞여 있을 수 있다.
- **v1 모델:** 09~11 결과를 그대로 썼다.
  - 새 정답셋 100은 threshold 0.5와 0.3 결과가 모두 있다(11의 3.6절).
  - 50문장과 패러프레이즈 573은 0.5 결과만 있다. 그래서 이 두 셋은 threshold가 다른 비교다(v1 0.5 vs v2 0.3).
- **LLM:** 09~11 결과를 그대로 썼다.
- 채점은 09~11과 같은 채점기(`eval.csv_keyword_eval score`)다. 방문 유형·성별과 라벨별 재현율은 11과 같은 방식으로 따로 셌다.
  - 이번에 집계 스크립트를 다시 만들었다.
  - v1·제로샷·LLM의 기존 수치(22·19·27 / 30 등)가 그대로 나오는 것을 확인했다.

### 1.1 v2 학습 요약

학습 쪽 기록(`gliner-entity-router/models/llm-compat-v2-ckpts/RUN.md`)을 요약했다.

| 항목 | v1 | v2 |
|---|---|---|
| 베이스 모델 | `Ihor/gliner-biomed-large-v1.0` | 같음 |
| 학습 데이터 | 764문장 중 무작위 688 | 764문장 중 **653** (나머지 111은 검증용) |
| 검증셋 | 무작위 10% (76문장). 컨셉 대부분이 학습셋에도 있음 | **컨셉 단위 분할**: `val_unseen` 54문장(학습에 없는 컨셉만), `val_seen` 57문장 |
| epoch / batch | 30 epoch 중 eval_loss 최저(25) / 8 | 20 epoch, 2 epoch마다 저장 / **4** (메모리 부족으로 낮춤) |
| 체크포인트 선택 | 무작위 검증셋의 eval_loss | 학습 후 체크포인트 9개를 `val_unseen` F1로 비교 → **epoch 8** |

- 선택된 epoch 8 체크포인트: val_unseen F1 0.913, val_unseen 시술명 재현율 16 / 16, val_seen F1 0.870
- batch size도 8에서 4로 바뀌었다. 그래서 v1과 v2의 차이에는 검증 방식과 epoch 말고 이 차이도 섞여 있다.

  |---|---|
  | 간경변 (진단) | 약물명 |

  | 아미오다론 (약물) | 시술명 |

  - 스키마 라벨 "시술"(EVENT)이 시술명 컨셉을 끌어간 경우가 많다.
  - 테이블도 틀리는 경우가 있다: 요추 천자 → death, 섬망 → death, 수혈 → drug_exposure
- **제로샷과 비교:** 제로샷이 맞히고 v2가 못 맞힌 시술명은 CABG, 골수 검사, 수혈, 요추 천자, 유방 보존술이다. 이 중 CABG만 v2가 아예 놓쳤다. 골수 검사는 "골수"를 검사명으로 냈고, 나머지 3개는 스키마로 냈다.

### 2.2 스키마 키워드

| 지표 | v1 (0.5) | v2 (0.3) | LLM |
|---|---|---|---|
| F1 (정확히 일치) | 80.5 | 80.8 | 75.2 |
| F1 (겹침 인정) | 83.5 | 83.0 | 82.9 |
| 오탐 (겹침 인정) | 16 | 27 | 29 |

- **v2가 새로 맞힌 것:** "수치" 9개, "수술" 3개, "검사결과", "노인"
- **v2가 새로 놓친 것:** 환자를 가리키는 다른 말 7개(사람, 대상자, 소아×2, 아이, 피험자, 환아), "복용" 1개
  - 학습 데이터에서 가장 흔한 "환자"는 그대로 잡는다(v1, v2 모두 67).
  - 드문 동의어로 넓혀 쓰던 능력을 잃은 것으로 보인다. 학습 문장이 줄었고(688 → 653), 학습량(8 epoch, batch 4)도 달라진 영향일 수 있다. 원인은 확인하지 않았다.
- 오탐이 16에서 27로 늘었다. 대부분 2.1절의 "의료 컨셉을 스키마로 낸" 경우다.

### 2.3 방문 유형·성별 키워드

| | v1 (0.5) | v1 (0.3) | v2 (0.3) | LLM |
|---|---|---|---|---|

- v2가 놓친 10개: 응급실×2, 외래×2, 재원, 퇴원×2, 남아×2, 여환
- v1보다 응급실과 외래를 하나씩 더 놓쳤다. 표준 단어(입원, 여성 등)는 여전히 모두 맞힌다.

### 2.4 테이블과 응답 속도

| 지표 | v1 (0.5) | v2 (0.3) | LLM |

- 속도는 사실상 같다. 모델 구조와 크기가 같고, 0.03초 차이는 측정 시점의 서버 상태 차이로 본다.

## 4. 해석

**왜 찾는 건 늘고 라벨은 더 틀리나.** 학습을 덜 한 체크포인트(epoch 8)를 골랐기 때문으로 본다.
- 학습을 덜 하면 원래 모델의 지식(처음 보는 시술명도 개체로 인식)이 더 남는다. 놓침이 줄어든 이유다.
- 대신 "환자 vs 진단명", "스키마 '시술' vs 시술명 컨셉" 같은 라벨 경계는 덜 배운다. 19개 라벨을 한 번에 넣는 구조라 라벨끼리 경쟁하고, 그 경쟁을 정리하는 법이 학습량에 달려 있다(11의 3.7절, 제로샷의 라벨 오류 37개 참고).
- 다시 말해, 이번 재학습은 v1과 제로샷 사이의 다른 지점으로 옮겨 간 것이다. 문제가 풀린 것이 아니다. 놓침과 라벨 오류를 맞바꿨다.

**체크포인트 선택의 한계.** `val_unseen`이 이 차이를 가려내기에 작았다.
- `val_unseen`은 54문장이고, 시술명 컨셉은 6개뿐이다. 그나마 대부분 무릎·고관절 치환술이다(슬 관절 치환술, 고관절 전치환술 등).
- 그래서 9개 체크포인트 중 5개가 시술명 재현율 1.0으로 같았다. 시술명 일반화를 기준으로 고르는 데 거의 변별력이 없었다.
- 100문장 셋의 시술명은 영문 약어, 중환자 처치, 이식, 영상·내시경처럼 종류가 훨씬 넓다.

**v1(0.3)과 비교해도 같은 결론이다.** 같은 threshold(0.3)로 비교해도 시술명 28 → 32, 놓침 25 → 14, 스키마로 낸 것 1 → 5다. threshold 차이로 설명되지 않는다.

## 5. 추가 테스트: 라벨 나눠 호출 (효과 없음)

같은 v2 모델(threshold 0.3)에 라벨 목록을 요청마다 넘길 수 있는 `/extract`로 직접 호출했다. 결과는 서비스의 겹침 처리와 라벨 매핑(`spans_to_llm_compat`)을 그대로 거쳤다.
- **한 번 호출**: 운영과 같은 18개 라벨을 한 번에 넣는다.
- **나눠서 두 번 호출**: 의료 4라벨로 한 번, 스키마 13개와 방문 유형·성별로 한 번 호출한 뒤 결과를 합친다.
- 라벨 순서에 따라 결과가 흔들려서, 라벨 순서를 세 가지로 섞어 각각 돌렸다. 표의 범위가 그 세 번의 결과다.

| 셋 | 방식 | 의료 컨셉 ② | 시술명 ② | 스키마 F1 | 방문·성별 | 응답 시간 평균 |
|---|---|---|---|---|---|---|
| 100문장 | 한 번 호출 | 205 ~ 210 / 227 | 35 ~ 38 / 45 | 81.4 ~ 82.9 | 20 ~ 21 / 30 | 0.45초 |
| 100문장 | 나눠서 두 번 | 200 ~ 202 / 227 | 33 ~ 36 / 45 | 80.4 ~ 82.0 | 21 ~ 22 / 30 | 0.80 ~ 0.86초 |
| 50문장 | 한 번 호출 | 80 / 81 | 9 / 9 | 85.8 ~ 86.3 | 16 / 23 | 0.47 ~ 0.51초 |
| 50문장 | 나눠서 두 번 | 79 / 81 | 9 / 9 | 85.5 ~ 86.4 | 15 ~ 16 / 23 | 0.80 ~ 0.83초 |

- **나눠도 좋아지지 않았다.** 재현율은 같거나 조금 낮고, 응답 시간은 두 배 가까이 늘었다.
- 이유: 의료 4라벨만 넣어도 v2는 수혈, 요추 천자, 간이식, 유방 보존술을 의료 컨셉으로 내지 않는다. 다른 라벨과 경쟁해서 밀린 것이 아니라, 학습에서 이 단어들을 스키마 "시술"로 배운 것이다. 기계환기와 섬망은 진단명으로 나왔다.
- **라벨 순서만으로도 결과가 흔들린다.** 한 번 호출에서도 의료 컨셉 ②가 205~210, 시술명 ②가 35~38 사이에서 움직였다.
  - 운영 서비스는 라벨 목록을 집합(set)으로 합쳐서, 프로세스를 다시 띄울 때마다 순서가 바뀔 수 있다.
  - 11의 3.6절에서 재시작 뒤 일부 키워드가 사라진 현상도 이것으로 설명된다.
  - 이에 따라 서비스가 라벨을 `llm_compat_map.yaml` 순서로 넘기도록 고정했다. 이 순서는 결과를 보고 고른 것이 아니다. 고정 후 v2 결과(② 208, 시술명 ② 37)는 위 범위 안에 있다.

## 6. 다음에 할 것

| 순서 | 할 일 | 근거 |
|---|---|---|
| 1 | 컨셉 RAG가 키워드 추출 라벨을 검색 조건으로 쓰는지 확인 | 재현율 ②를 기준으로 삼으려면 라벨을 쓰지 않아야 한다 |
| 2 | 스키마 "시술"로 나온 span도 컨셉 RAG에 넘기는 후처리 검토 | v2는 시술명을 위치로는 40 / 45 찾지만, 의료 컨셉으로 내는 것은 37 / 45다. RAG가 맞는 컨셉을 못 찾으면 버리는 식이면 사전 없이 시험할 수 있다 |

- 라벨 나눠 호출은 5절 결과로 제외한다.
- 서비스의 라벨 순서 고정은 반영했다(5절).
- 추가 파인튜닝(`val_unseen` 보강 등)은 보류한다. 라벨 순서를 고정한 뒤에도 v1 → v2의 재현율 ② 개선이 +7(3.1%p), 시술명 +4로 작았다.

```bash
T=../test_set/keyword_ext
FT=<파인튜닝 서버>   # 사내 서버 주소, v2 모델 + FINETUNED_THRESHOLD=0.3
# 추출
python -m eval.csv_keyword_eval extract --system ke-compat --url $FT/keyword-extraction/llm-compat --csv $T/kw100/keyword_eval_samples_100_new.csv --out eval/outputs/kw100/kw100_ft-gliner-v2_compat.jsonl
python -m eval.csv_keyword_eval extract --system ke-compat --url $FT/keyword-extraction/llm-compat --csv $T/kw50/keyword_eval_samples_50.csv --out eval/outputs/kw50/kw50_ft-gliner-v2_compat.jsonl
```
