# GLiNER 방문·성별 라벨 제로샷 평가

- 날짜: 2026-10-27
- 모델: `Ihor/gliner-biomed-large-v1.0` (gliner-entity-router `entity-router-biomed`, :8002 `/extract`), 파인튜닝 없음
- 라벨 6개(`multi_label=True`): 진단명 또는 질병명 / 약물명 / 검사명 또는 측정 항목 / 시술명 또는 수술명 / **방문 유형** / **성별**
- 평가 대상: **방문 유형, 성별** 두 라벨 (의료 4개 라벨은 검증 완료 상태라 대상 아님. 다만 라벨 2개를 추가했을 때 4개 라벨이 영향을 받는지는 따로 확인함 → 4절)
- 데이터: `test_set/proposed_input_train.jsonl` + `proposed_input_val.jsonl` 680문장

## 1. 결론

| | 방문 유형 | 성별 |
|---|---|---|
| 정답을 찾는가 (재현율) | ❌ 약함. threshold를 0.05까지 내려도 72% | ✅ 100% (정답 점수 0.91~1.00) |
| 엉뚱한 것을 잡는가 (오탐) | "신규 사용자", "환자", "노출군" | ❌ 심각. "환자", "노출군"을 성별로 잡음 |
| threshold 0.5 | P 34.6 / R 50.0 / F1 40.9 | P 11.6 / R 100 / F1 20.8 |
| threshold 0.3 | P 26.1 / R 66.7 / F1 37.5 | P 4.2 / R 100 / F1 8.0 |
| 가장 나은 threshold | 0.8: P 88.9 / R 44.4 / F1 59.3 | 0.9: P 88.9 / R 100 / F1 94.1 |
| 판단 | **제로샷 GLiNER로는 부적합** | **높은 threshold(0.9)에서만 쓸 만하지만 근거가 약함** |

- **방문 유형**은 어떤 threshold에서도 실용 수준이 안 나온다. 맨 앞에 있는 "입원" 한 단어는 거의 못 잡고, threshold를 낮추면 오탐만 늘어난다.
- **성별**은 "여성"/"남성"은 다 찾지만, 라벨 문구 "성별"이 사람을 가리키는 말("환자", "노출군", "성인")까지 끌어온다. threshold 0.3에서는 정답 없는 문장 672개 중 136개(20%)에 성별 오탐이 생긴다. 0.9에서 깨끗해지지만, 정답이 8개뿐이고 남성(0.91)이 경계에 걸려 있어 이 숫자만 믿고 0.9로 정하기는 이르다.
- **라벨 2개를 추가하면 기존 4개 라벨의 정밀도가 떨어진다** (4절). "진단", "처방", "이력" 같은 일반어를 의료 라벨로 잡는 경우가 늘어난다.
- 두 개념 모두 표현이 거의 닫혀 있다(입원·외래·응급실 / 여성·남성·여자·남자). **GLiNER 라벨에 넣기보다 사전 매칭으로 처리하는 쪽을 권한다.** 지금 4개 라벨만 GLiNER에 둔 구성을 그대로 유지하는 게 맞다.

## 2. 평가 방법

### 정답 만드는 방법

정답 SQL이 방문 유형이나 성별로 거르는 문장만 양성으로 본다. SQL의 `visit_concept_id`/`gender_concept_id`에 있는 개념을 문장 속 표현과 연결해 정답 span으로 삼았다.

| 개념 | 문장 속 표현 (정규식) | train/val 정답 수 |
|---|---|---|
| 9201 입원 | `입원( 방문)?` | 입원 9, 입원 방문 3 |
| 9202 외래 | `외래( 방문)?` | 외래 방문 5 |
| 9203 응급실 | `응급실?( 방문)?` | 응급실 방문 1 |
| 262 응급실+입원 | `응급실 입원( 방문)?` | 0 |
| 8532 여성 | `여성\|여자` | 여성 7 |
| 8507 남성 | `남성\|남자` | 남성 1 |

- 양성: 방문 17문장(span 18개), 성별 8문장(span 8개). SQL에는 있는데 문장에서 표현을 못 찾은 경우는 0건.
- 나머지 문장은 모두 음성이다. 거기서 나온 방문·성별 예측은 전부 오탐으로 센다.
- SQL이 거르지 않는데 "외래"가 나오는 문장(예: "만성 외래 복막투석")은 방문이 아니므로 정답에서 빠진다. train/val에는 이런 문장이 없었다.

### 채점

- **span 단위, 겹침(overlap) 기준.** 같은 라벨의 정답과 한 글자라도 겹치면 맞힌 것으로 본다. 정답이 "입원 기록"이 아니라 "입원"이어도, 예측이 "입원 기록"이면 인정한다. 경계까지 정확히 맞는지(exact)는 따로 계산해 `visit_gender_scores.json`에 넣었다.
- 정밀도(P) = 정답과 겹친 예측 / 전체 예측, 재현율(R) = 예측과 겹친 정답 / 전체 정답.
- 문장 단위로는 "정답 있는 문장에서 정답을 전부 맞혔나", "정답 없는 문장에 오탐이 있나"를 같이 본다.

### threshold

요청마다 `threshold: 0.05`를 직접 보내 0.05 이상인 예측을 점수와 함께 모두 받았다. 채점할 때 threshold별로 걸렀다. GLiNER는 점수가 높은 span부터 남기고 겹치는 span을 지우기 때문에, 0.05 결과를 t 이상만 남기면 threshold=t로 직접 돌린 결과와 같다. 그래서 0.3과 0.5를 따로 돌리지 않아도 이 표 안에 포함된다. 컨테이너의 `GLINER_THRESHOLD=0.5`는 요청에 threshold가 없을 때만 쓰는 기본값이라 이번 결과와 관계없다.

## 4. 라벨 2개를 추가하면 기존 4개 라벨이 흔들리나

GLiNER는 라벨 목록을 문장과 함께 모델에 넣기 때문에, 라벨을 추가하면 다른 라벨의 점수도 바뀐다. 같은 680문장을 의료 4라벨만으로 한 번 더 돌려 비교했다.

**예측이 얼마나 바뀌나 (의료 4라벨, threshold 0.2 = 키워드 추출 API 설정값).** 4라벨과 6라벨이 같은 예측 2,493개, 4라벨에만 있는 예측 204개, 6라벨에만 있는 예측 666개. 6라벨에서 새로 생긴 예측은 대부분 일반어다: 진단명 "진단" 36·"이력" 29·"처방" 19·"처방일" 19, 약물명 "처방" 32, 시술명 "진단" 31·"처방" 24, 검사명 "진단" 21·"measurement" 14·"비교군" 13.

**정확도 변화.** 예전 제로샷 평가 정답(`gliner-entity-router/eval/gold/gliner_gold.json`)과 문장이 같은 555개로 쟀다. 그 정답은 구조 단어("환자", "처방" 등)를 일부러 뺐기 때문에 정밀도 절대값은 낮게 나온다. 4라벨과 6라벨의 **차이**만 보면 된다.

| 라벨 (threshold 0.2) | 4라벨 P / R | 6라벨 P / R |
|---|---|---|
| 진단명 또는 질병명 | 38 / 99.0 | 34 / 99.7 |
| 약물명 | 50 / 96.3 | 48 / 96.3 |
| 검사명 또는 측정 항목 | 10 / 89.8 | 9 / 93.2 |
| 시술명 또는 수술명 | 30 / 96.9 | 25 / 96.9 |

threshold 0.3, 0.5에서도 방향은 같다. 정밀도는 2~9포인트 떨어지고, 재현율은 그대로이거나 조금 오른다(검사명 0.3에서 71→83). 검증된 4개 라벨 설정을 그대로 두려면 두 라벨을 같은 요청에 넣지 않는 편이 낫다. 지연은 요청당 평균 0.96초 → 1.03초로 늘었다(동시 2개 요청 기준).

## 5. 제안

1. **방문 유형·성별은 GLiNER 라벨에 넣지 않는다.** 키워드 추출 API의 concept 라벨은 지금처럼 4개를 유지한다.
2. **사전 매칭으로 처리한다.** 표현이 닫혀 있어 사전이 훨씬 정확하고 싸다.
   - 방문: 입원 → 9201, 외래 → 9202, 응급실 → 9203, 응급실 입원 → 262 (긴 표현 우선). "방문"이 뒤에 붙는 형태 포함.
   - 성별: 여성/여자 → 8532, 남성/남자 → 8507.
   - 주의: "만성 외래 복막투석"처럼 시술명 안에 "외래"가 들어가는 경우가 변형 테스트셋에 3건 있다. GLiNER 시술명 span과 겹치면 방문으로 보지 않는 규칙이 필요하다.
   - 사전 추가는 직접 검토 후 진행 (자동 반영하지 않음).
3. 그래도 GLiNER로 해야 한다면 라벨별 threshold가 필요하다. 지금 서비스는 threshold를 하나만 쓴다. 성별은 0.9 이상, 방문은 0.8 이상이어야 오탐이 잡히고, 그래도 방문 재현율은 44%다. 라벨 문구를 바꿔 보는 실험("성별(남성/여성)", "입원·외래·응급실 같은 방문 유형")은 아직 안 했다.

## 6. 한계

- **양성 표본이 작다.** 방문 18개, 성별 8개(남성 1개). 재현율은 한 건에 5~12포인트씩 움직인다. 음성 문장(660여 개)은 충분해서 오탐 경향은 믿을 만하다.
- 정답은 SQL 개념 → 표현 규칙으로 만들었다. 문장에 방문·성별이 나오지만 SQL이 그 조건을 안 쓰는 경우가 있다면 그 예측은 오탐으로 잡힌다. train/val에서는 그런 문장을 못 찾았다.
- train/val 문장은 임상시험 프로토콜 문체다. 실제 사용자 질의("여자 환자 중에…")에서는 결과가 다를 수 있다.
- 변형 테스트셋(paraphrase/restructure/concept/slot)은 이번에 돌리지 않았다. 변형 테스트셋까지 합친 2,236문장에는 방문·성별 정답 문장이 102개(span 106개)로 train/val의 4배다. 재현율 표본을 늘리려면 그쪽까지 돌리면 된다(약 15분 추가).

## 7. 재현

`keyword_ext_eval/`에서:

```bash
D="--data ../test_set/proposed_input_train.jsonl --data ../test_set/proposed_input_val.jsonl"
# 추출 (이어하기 지원, 설정이 바뀌면 --overwrite)
python -m eval.visit_gender_eval extract $D --out eval/outputs/vg_6labels.jsonl --concurrency 2
python -m eval.visit_gender_eval extract $D --out eval/outputs/vg_4labels.jsonl --concurrency 2 \
  --labels "진단명 또는 질병명,약물명,검사명 또는 측정 항목,시술명 또는 수술명"
# 채점 (--threshold는 오탐/미탐 CSV를 뽑을 기준, 점수표는 0.05~0.9 전부)
python -m eval.visit_gender_eval score $D --pred eval/outputs/vg_6labels.jsonl --out-dir eval/runs/vg_trainval_th0.3 --threshold 0.3
```

결과 파일(`eval/runs/vg_trainval_th0.3`, `vg_trainval_th0.5`):
- `visit_gender_scores.json`: threshold별 P/R/F1 (overlap, exact)
- `visit_gender_fp.csv`: 오탐 목록
- `visit_gender_fn.csv`: 놓친 정답, 같은 라벨 최고 점수, 대신 잡힌 라벨
- `visit_gender_gold_issues.csv`: SQL에는 있는데 문장에서 표현을 못 찾은 경우 (이번엔 0건)
