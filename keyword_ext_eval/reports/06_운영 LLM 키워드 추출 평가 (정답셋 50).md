# 운영 LLM 키워드 추출 평가 (정답셋 50)

- 평가일: 2026-10-28
- 대상: 운영 중인 프롬프트 기반 LLM (기준선). API v1/v2와 같은 정답셋, 같은 채점기
- 원자료: `eval/outputs/kw50_prod_llm.jsonl` (응답 원문 `raw` 포함), 채점 결과 `eval/runs/kw50_prod_llm/`

## 요약

| 항목 | 운영 LLM | API v2 | 비교 |
|---|---|---|---|
| 스키마 키워드 (겹침) P / R / F1 | 85.5 / 86.2 / 85.8 | **98.3 / 94.3 / 96.3** | API 우세 |
| └ 성별·방문 값 FP 10개를 형식 차이로 보고 뺐을 때 P | 93.0 | 98.3 | API 우세 |
| concept (GLiNER 4라벨) P / R / F1 | **90.9 / 98.8 / 94.7** | 87.1 / 91.4 / 89.2 | LLM 우세 |
| └ 라벨 오류 | **1** | 7 | LLM 우세 (검사명) |
| 방문·성별 표현 포착 (형식 무관) | **23 / 23** | 14 / 23 | LLM 우세 |
| └ 도메인까지 맞음 | **16 / 23 (70%)** | 12 / 23 (52%) | LLM 우세 |
| 테이블 커버리지 (자기 출력 그대로) | 36% | 42% | 비슷 (둘 다 낮음) |
| 테이블 커버리지 (+ 대체 스키마 모의) | **90%** | 84% | LLM 약간 우세 |
| 평균 응답 시간 | 1.70초 | **0.56초** | API 3배 빠름 |

한 줄로 요약하면 **스키마 단어는 API가, 의료 개체 라벨과 방문·성별은 LLM이 낫다.** 테이블 커버리지는 두 시스템 모두 concept을 테이블로 넘기는 단계 없이는 40% 안팎이다.

## 1. 실행 조건

| 항목 | 값 |
|---|---|
| 엔드포인트 | 운영 프록시 (`.env`의 `PROD_LLM_BASE_URL`), served model `qwen-vl` (실제 모델은 Qwen 계열 Flash, FP8) |
| 시스템 프롬프트 | `eval/prompts/prod_llm_system.local.txt` (sha256 `1bb9b021…`). 운영 `_system()` 원문을 그대로 옮김 |
| 디코딩 | temperature 0, max_tokens 1024, `enable_thinking: false`, 1회 실행 |
| 동시 요청 | 4 |
| 실패 / 파싱 실패 | 0 / 0 (50건 모두 JSON 배열) |

**⚠ 운영과 다를 수 있는 점**
1. **테이블 카탈로그는 대체본이다.** 프롬프트의 `_catalog()` 부분은 운영 코드를 받지 못해 10개 테이블 이름과 설명을 직접 써 넣었다. LLM이 붙이는 `table` 값에 영향이 있다. 키워드와 라벨에는 영향이 작을 것으로 본다.
2. **thinking을 껐다.** 켜면 1024 토큰 안에 답이 나오지 않는다. 운영에서 어떻게 쓰는지 확인이 필요하다.
3. **응답 시간은 직접 비교하기 어렵다.** 원격 프록시를 거쳤고 동시 요청이 4개였다. API는 로컬 컨테이너에서 쟀다.

## 2. 형식 차이를 어떻게 채점했나

운영 LLM은 `[{"keyword","label","table"}]`를 내고, API는 `schema`와 `concept` span을 낸다. 채점기는 LLM 응답을 다음처럼 API 형식으로 바꿔 같은 기준으로 잰다.

| LLM label | 채점에서 | 비고 |
|---|---|---|
| EVENT / ATTRIBUTE / ENTITY | schema span | `table` 값은 따로 "LLM 테이블" 지표로 씀 |
| DISEASE / DRUG / MEASUREMENT / PROCEDURE | concept span (진단명·약물명·검사명·시술명) | `eval/maps/llm_category_map.yaml` |
| VALUE / OPERATOR / TIME | 채점 제외 | API에 해당 경로가 없음. 48개 나옴 |

**공정성 보정이 필요한 세 곳**
- **키워드 단위.** LLM은 "응급실 방문 기록"처럼 구로 낸다. 표면형 일치 지표(스키마 키워드)에서는 불리하므로 **위치가 겹치면 맞힘**으로 보는 "스키마 키워드 (겹침)"를 주 지표로 쓴다. 정확 일치로 보면 P 68.8 / R 69.9다.
- **방문·성별.** LLM 형식에는 방문 유형·성별 값을 담을 라벨이 없다. "여성"은 ATTRIBUTE/person, "외래"는 EVENT/visit_occurrence로 나온다. 그래서 채점기의 concept (Visit/Gender) 지표는 구조상 0이다. 대신 형식과 무관한 지표 두 개를 따로 쟀다.
  - 포착: 정답 표현과 위치가 겹치는 출력이 있는가
  - 도메인 맞음: API는 category가 방문 유형·성별(또는 schema 방문·성별 묶음), LLM은 EVENT/visit_occurrence 또는 ATTRIBUTE/person
- **정답셋의 기준.** 정답 스키마 키워드는 사전 표면형 단위("수치", "측정값", "검사결과")로 달려 있다. 사전 기반 API에 조금 유리하다.

## 3. 결과

### 3.1 스키마 키워드

| 지표 | TP | FP | FN | P | R | F1 |
|---|---|---|---|---|---|---|
| 겹침 기준 (주 지표) | 106 | 18 | 17 | 85.5 | 86.2 | 85.8 |
| 정확 일치 | 86 | 39 | 37 | 68.8 | 69.9 | 69.4 |

**FP 18개**
- **10개는 형식 차이다.** 성별·방문 값(남성, 여자, 여성×4, 여환, 남아, 외래, 응급실)을 ATTRIBUTE/EVENT로 냈다. API v2라면 concept (Visit/Gender)로 나가는 값이라 정답 스키마 키워드에 없다. 이를 빼면 P 93.0이다.
- 8개는 실제 과잉 추출이다: 날짜×2, 시행, 이력, 산모, 생긴, 변화, 시작일.

**FN 17개**
- 수치·측정값·검사결과·측정 (9개): "LDL 콜레스테롤 측정값", "INR 수치"를 통째로 MEASUREMENT로 내거나, 스키마 단어를 아예 내지 않았다.
- 수술 (2개): "응급수술", "백내장 수술"을 PROCEDURE 하나로 냈다.
- 내원·입원·재원 (3개): "응급실 내원 당일", "입원 기간"을 TIME으로 내거나 "재원 기간"을 MEASUREMENT로 냈다.
- 검사 (1개, K022 위내시경 검사), 급사·사망 (2개, K048)

LLM은 "의료 개체 + 스키마 단어"를 한 덩어리로 묶는 경향이 있다. 그러면 스키마 단어가 concept 쪽으로 흡수된다.

### 3.2 concept (의료 4라벨)

| | TP | FP | FN | P | R | F1 | 라벨 오류 |
|---|---|---|---|---|---|---|---|
| 운영 LLM | 80 | 8 | 1 | 90.9 | 98.8 | 94.7 | 1 |
| API v1/v2 | 74 | 11 | 7 | 87.1 | 91.4 | 89.2 | 7 |

- **API의 약점인 검사명 라벨 오류가 LLM에는 거의 없다.** 유일한 라벨 오류는 K044 "항암화학요법"(정답 약물명, LLM 시술명)이다.
- FP 7개 (라벨 오류 제외): 측정값, 유병률, 응급수술, 재원 기간, 119, 이송, 급사
  - 재원 기간, 119, 이송은 정답상 방문 표현이다.
  - 측정값, 응급수술은 3.1절의 "스키마 단어 흡수"와 같은 현상이다.

### 3.3 방문·성별 (형식 무관 비교)

| | 포착 | 도메인 맞음 |
|---|---|---|
| API v1 | 6 / 23 | 4 / 23 |
| API v2 | 14 / 23 | 12 / 23 (52%) |
| 운영 LLM | **23 / 23** | **16 / 23 (70%)** |

LLM은 23개를 모두 어떤 형태로든 잡았다. 도메인이 틀린 7개는 아래와 같다.

| id | 정답 | LLM 출력 |
|---|---|---|
| K013 | 여환 (Gender) | 여환 / ENTITY / person (테이블은 맞음) |
| K014 | male (Gender) | male / VALUE |
| K031 | 남성 (Gender) | 남성 / VALUE |
| K019 | 재원 (Visit) | 재원 기간 / MEASUREMENT |
| K020 | 119로 이송 (Visit) | 119, 이송 / PROCEDURE |
| K028 | 응급실 (Visit) | 응급실 내원 당일 / TIME |
| K034 | 입원 (Visit) | 입원 기간 / TIME |

입원·외래·응급실 구분(값)은 LLM 형식에도 없다. 그래서 다운스트림이 값을 알려면 결국 키워드 텍스트를 다시 해석해야 한다. 이 점은 API v2(category만 있고 값은 없음)와 같다.

### 3.4 테이블

| 지표 | 운영 LLM (LLM이 붙인 table) | API v2 (스키마 사전) |
|---|---|---|
| P / R / F1 | 66.3 / 59.5 / 62.7 | 67.6 / 62.9 / 65.2 |
| 커버리지 | 36% | 42% |
| person 제외 P / R | 98.2 / 53.9 | 96.9 / 61.8 |
| + 대체 스키마(모의) P / R / F1 | 73.0 / 95.7 / 82.8 | 71.5 / 93.1 / 80.9 |
| + 대체 스키마(모의) 커버리지 | **90%** | 84% |

테이블별 재현율 (LLM table → + 대체 모의): person 100 → 100, observation_period 100 → 100, visit 77 → 77, condition **34** → 100, drug 93 → 93, procedure **20** → 100, measurement **40** → 100, death 88 → 88

- **LLM도 concept에는 table을 붙이지 않는다** (프롬프트 규칙). 그래서 "고혈압 환자"처럼 질병명만 있는 문장은 condition_occurrence를 못 가리킨다. 이 점은 API와 똑같다.
- 대체 스키마(concept 라벨 → 테이블)를 더하면 LLM이 90%로 API보다 6%p 높다. LLM이 방문·성별을 더 많이 잡고 검사명 라벨을 덜 틀린 영향이다.
- 운영 엔진이 concept에서 테이블을 따로 추론하는지는 확인이 필요하다. 추론하지 않는다면 운영 LLM의 실제 커버리지는 36% 쪽에 가깝다.

## 4. 결론

1. **두 방식의 강점이 다르다.** 스키마 단어는 API(사전)가 정확하고(F1 96 vs 86), 의료 개체 라벨과 방문·성별은 LLM이 낫다(concept F1 95 vs 89, 방문·성별 도메인 70% vs 52%).
2. **API로 LLM을 대체할 때 가장 큰 격차는 검사명 라벨과 방문·성별 어휘다.** 둘 다 이미 개선 후보에 있다. 반대로 스키마 단어, 응답 시간(3배), 결정론적 출력은 API가 낫다.
3. **테이블 커버리지는 두 시스템 모두 concept → 테이블 단계가 결정한다.** 자기 출력만으로는 36~42%이고, 대체 스키마를 더하면 84~90%다. 운영 엔진이 이 단계를 어떻게 처리하는지가 비교의 마지막 변수다.
4. **이 결과는 운영 그대로가 아니다.** 테이블 카탈로그가 대체본이고 thinking을 껐다. 운영 `_catalog()`와 운영 설정을 받으면 다시 돌려 이 보고서의 숫자를 갱신한다(table 관련 지표가 주로 바뀔 것으로 본다).

## 5. 재현

```bash
C=../test_set/keyword_ext/keyword_eval_samples_50.csv
python -m eval.csv_keyword_eval extract --system prod-llm --csv $C --out eval/outputs/kw50_prod_llm.jsonl --concurrency 4
python -m eval.csv_keyword_eval score --csv $C --pred eval/outputs/kw50_prod_llm.jsonl --out-dir eval/runs/kw50_prod_llm
```
방문·성별 형식 무관 지표(3.3절)는 채점기에 아직 넣지 않았다. 이번에는 `kw50_per_query.json`과 출력 jsonl로 따로 계산했다.
