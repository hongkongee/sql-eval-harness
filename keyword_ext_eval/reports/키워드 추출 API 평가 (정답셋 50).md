# 키워드 추출 API 평가 (정답셋 50문장) — API v1

- 날짜: 2026-10-27
- 대상: **API v1** (구성은 [API 리비전](API%20리비전.md) 참고) — 키워드 추출 API `POST http://localhost:8001/keyword-extraction` (gliner-entity-router `app/`)
  - schema: 사전 최장 일치 (`schema_keywords.yaml`, sha256 `b1630690…`, 컨테이너와 로컬 파일 일치 확인)
  - concept: GLiNER `Ihor/gliner-biomed-large-v1.0`, 라벨 4개, threshold **0.3** (컨테이너 `GLINER_THRESHOLD=0.3`)
- 정답셋: `test_set/keyword_ext/keyword_eval_samples_50.csv` (50문장, 사람이 직접 만든 정답, `case_type`으로 유형 구분)
- 응답 시간: 평균 0.56초, 최대 1.15초

## 요약

| 경로 | 정밀도(P) | 재현율(R) | F1 | TP / FP / FN | 한 줄 평 |
|---|---|---|---|---|---|
| **스키마 키워드** (사전) | 98.3 | 94.3 | 96.3 | 116 / 2 / 7 | 사전에 있는 단어는 다 잡는다. FN 7개는 전부 사전에 없는 단어 |
| **concept** (GLiNER) | 87.1 | 91.4 | 89.2 | 74 / 11 / 7 | 진단명·시술명은 완벽. FN 7개는 전부 **라벨 오류**(위치는 맞음), 그중 6개가 검사명 |
| **concept** (Visit/Gender 사전) | — | **0** | — | 0 / 0 / 23 | API에 이 경로가 아직 없음 |
| 대체 스키마 (concept 라벨 → 묶음, 모의) | 90.0 | 72.7 | 80.4 | 72 / 8 / 27 | API는 안 냄. API의 concept 라벨로 만들어 본 값 |

테이블 단위 (정답 SQL이 쓰는 테이블을 키워드가 가리키는가):

| 무엇으로 테이블을 찾나 | P | R | F1 | 커버리지 | person 빼고 P / R |
|---|---|---|---|---|---|
| 스키마 키워드만 (지금 API 출력 그대로) | 67.6 | 62.9 | 65.2 | **42%** (21/50) | 96.9 / 61.8 |
| 스키마 + 대체 스키마(모의) | 71.3 | 92.2 | 80.5 | **82%** (41/50) | 90.7 / 95.1 |

- 커버리지 = 정답 테이블을 **전부** 가리킨 문장의 비율
- person 정밀도가 낮은 건 정답셋 설계 때문이다. "환자"는 거의 모든 문장에 나오지만, SQL에 person 조인이 필요 없는 문장이 많다(K003 note 참고).

**정리하면**

1. **사전 매칭은 사전에 있는 단어에 대해서는 거의 완벽하다** (R 94.3, P 98.3). 놓친 7개는 모두 사전에 없는 단어(퇴원 2, 진료 2, 남녀, 재원, 먹고)라서 매칭 문제가 아니라 사전 범위 문제다.
2. **GLiNER concept는 개체를 찾는 능력은 충분하다.** 정답 81개 중 위치를 놓친 것은 0개다. 다만 **검사명을 진단명으로 붙이는 라벨 오류**가 약점이다 (검사명 재현율 11/17 = 65%).
3. **스키마 키워드만으로는 테이블을 절반도 못 찾는다** (커버리지 42%). 진단(condition 34%)과 시술(procedure 30%)을 가리키는 단어가 문장에 없는 경우가 많기 때문이다. **concept 라벨을 대체 스키마 단어로 바꿔 붙이면 82%까지 오른다.**
4. **방문·성별 값(응급실/외래/입원, 여성/남성 등 23개)은 지금 API가 concept로 내지 않는다.** 남은 미커버 9문장 중 6문장이 이 경로가 있으면 풀린다.

## 1. 용어

| 용어 | 뜻 |
|---|---|
| TP (맞힘) | 정답에 있는 것을 API가 냈다 |
| FP (오탐) | 정답에 없는 것을 API가 냈다 |
| FN (놓침) | 정답에 있는 것을 API가 안 냈다 |
| 정밀도(P) | TP / (TP + FP). API가 낸 것 중 맞은 비율 |
| 재현율(R) | TP / (TP + FN). 정답 중 API가 찾은 비율 |
| F1 | P와 R의 조화평균 |
| 라벨 오류 | concept 위치는 정답과 겹치는데 라벨이 다름 (예: 헤모글로빈 → 진단명). 채점상 FN 1 + FP 1 |

## 2. 채점 방법

정답 CSV의 열마다 따로 채점했다.

| 정답 열 | API 출력 | 맞힘 기준 |
|---|---|---|
| `gold_schema_keywords` | `type=schema` span의 텍스트 | 표면형이 같으면 TP (문장 단위 집합 비교) |
| `gold_concept_gliner` | `type=concept` span (위치, `category`) | 위치가 겹치고 **라벨이 같으면** TP. 경계가 다른 것("흉통 환자" vs "흉통")도 TP로 보되 따로 셈 |
| `gold_concept_dict` | 없음 | API에 경로가 없어 전부 FN |
| `gold_derived_schema` | 없음 → **모의** | API concept 라벨을 묶음으로 바꿔 비교: 약물명→처방, 진단명→진단, 검사명→측정, 시술명→시술 |
| `gold_tables` | 스키마 키워드(+대체 스키마) → 테이블 | 평가 도구의 묶음→테이블 표(`eval/maps/schema_keyword_table_map.yaml`)로 환산 |

concept 점수 하한을 0.5로 올린 결과도 같이 쟀다(3-2).

## 4. 결론

1. **사전 매칭(스키마)은 지금 수준으로 유지해도 된다.** 재현율을 더 올리려면 사전을 넓혀야 한다. 후보는 퇴원·진료(방문), 재원(방문), 먹고(처방)다. "질환" 오탐은 테이블에 해가 없어 급하지 않다.
2. **GLiNER concept는 "찾기"는 되고 "라벨 붙이기"가 약하다.** 특히 검사명이 진단명으로 잘못 붙는다. 라벨이 테이블 선택에 쓰이는 순간(대체 스키마), 이 오류가 바로 테이블 오류가 된다(K009, K044). 우선순위는 threshold 조정이 아니라 검사명 라벨 문구 실험이나 파인튜닝이다.
3. **가장 효과가 큰 개선은 대체 스키마(concept 라벨 → 묶음)다.** 테이블 커버리지가 42% → 82%로 오른다. API 출력에 넣을지는 API 계약 변경이라 승인이 필요하다. 지금은 평가 도구에서 모의로만 계산했다.
4. **그다음은 Visit/Gender 사전 경로다.** 정답 23개가 전부 FN이고, 미커버 문장의 2/3가 이것 때문이다. 표현이 닫혀 있어 사전으로 처리하는 게 맞다(GLiNER 제로샷은 앞선 평가에서 부적합).

## 5. 한계와 주의

- **50문장, 정답 수십 개 규모다.** 라벨별 재현율(검사명 17개, 시술명 9개)은 한두 건에 6~11포인트씩 움직인다. 방향을 보는 용도로 쓰고 절대값은 신중히 본다.
- 대체 스키마와 그로 인한 테이블 결과는 **API가 내지 않는 값을 평가 도구가 만들어 본 것**이다. 실제로 구현하면 규칙에 따라 달라질 수 있다.
- 정답셋 확인이 필요한 곳:
  - K016: 정답 테이블에는 procedure_occurrence가 있지만 concept·대체 스키마 정답에는 시술이 없다. API의 "응급수술 → 시술명"은 오탐으로 계산됐다.
  - K025: 정답셋이 표시한 대로 폐암 → 진단 → condition_occurrence가 FP가 되는 경계사례다.
- **짧은 구어체 질의는 이 정답셋에 거의 없다.** 예로 주신 "치매 걸린 환자 수"는 "걸린"(0.36)·"린"(0.49)을 진단명으로, "수"(0.55)를 시술명으로 낸다. 한 글자 span이나 서로 겹치는 span이 threshold 0.3을 넘는다. 이 50문장에서는 그런 출력이 없었으니, 구어체 문장을 몇 개 추가하면 이 약점이 숫자로 잡힐 것이다.

## 6. 재현

`keyword_ext_eval/`에서:

```bash
C=../test_set/keyword_ext/keyword_eval_samples_50.csv

```
