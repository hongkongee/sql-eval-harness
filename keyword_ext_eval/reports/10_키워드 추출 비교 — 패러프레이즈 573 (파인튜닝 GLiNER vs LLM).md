# 키워드 추출 비교: 패러프레이즈 573 (파인튜닝 GLiNER vs LLM)

- 작성일: 2026-11-03
- 질문: [09 문서](09_키워드%20추출%20비교%20(파인튜닝%20GLiNER%20vs%20LLM).md)의 결론(파인튜닝 GLiNER가 LLM과 비슷하다)이 **더 큰 셋에서도 유지되는가**. 단, 이 셋은 학습 데이터와 같은 시드에서 나와 완전한 홀드아웃이 아니다(1절, 3.5절)
- 비교 대상: 09와 같은 파인튜닝 GLiNER(threshold 0.5)와 LLM. 제로샷 GLiNER와 사전 매칭은 뺐다.
- 테스트셋: NL2SQL 평가용 패러프레이즈 셋 573문장(`test_set/paraphrase.jsonl`). 키워드 정답이 없어서 **재료(input)와 정답 SQL에서 정답을 끌어냈다**(2절). 그래서 일부 지표만 잴 수 있다.

## 요약

| 항목 | 지표 | 파인튜닝 GLiNER | LLM |
|---|---|---|---|
| 의료 컨셉 키워드 | 재현율 (647개) | 95.4 | **99.2** |
| 의료 컨셉 키워드 | 정밀도 (참고) | **99.2** | 89.8 |
| 방문 유형·성별 키워드 | 맞힌 수 / 25 | **25** | 23 |
| 스키마 키워드 | 테이블 재현율 (SQL 기준, person 제외) | 75.3 | **88.1** |
| 스키마 키워드 | LLM과 위치 일치 (참고) | LLM 키워드의 76.6%를 같이 냄 | 기준 |
| 테이블 | 다운스트림 추론 포함 커버리지 | 94.6% | **98.8%** |
| 응답 속도 | 평균 / 중앙값 | **0.55초 / 0.57초** | 1.34초 / 0.91초 |

- 두 모델 모두 한 건씩 순차로, 같은 시간대에 호출했다. 09와 달리 LLM도 순차 호출이라 속도 비교 조건이 더 가깝다. 다만 서버는 다르다(파인튜닝 GLiNER는 사내 CPU, LLM은 원격 GPU).
- 정밀도는 참고용이다. 정답에는 SQL 조건에 쓰인 컨셉만 들어 있어서, 문장에 있지만 조건이 아닌 컨셉(예: 비교약 이름)을 뽑으면 맞아도 오탐으로 잡힌다(3.1절).
- 스키마 키워드 F1은 정답이 없어 재지 않았다(2절).

**결론.** 50문장 셋의 결론이 대체로 유지된다. 파인튜닝 GLiNER는 의료 컨셉과 방문 유형·성별에서 LLM과 비슷한 수준이고, 정밀도가 높고, 빠르다. 다만 두 가지가 50문장 셋보다 분명해졌다.
1. **스키마 키워드를 LLM보다 적게 낸다.** 날짜·이력 표현("최초 발생일", "시행일", "기준일", "추적 종료일")과 대상 표현("대상자", "코호트")을 주로 놓친다. 그래서 스키마 키워드만으로 정한 테이블 재현율이 13%p 낮다(75.3 vs 88.1). procedure_occurrence는 29% vs 69%다.
2. **의료 컨셉을 놓치는 것이 LLM보다 많다** (30개 vs 5개). 유방암, 뇌졸중, 말기신부전 같은 질병명과 "DPP-4 억제제", "SGLT2 억제제" 같은 약물 계열명이다. 09에서 약점이던 시술명은 이 셋에서는 96 / 99로 괜찮다.

**⚠ 이 셋은 완전한 홀드아웃이 아니다. 파인튜닝 GLiNER 점수는 부풀려져 있다.** 573문장이 모두 학습 데이터를 만든 시드에서 나왔다. 문장은 다르지만 정답 컨셉의 94%를 학습 때 정답으로 본 적이 있다. 50문장 셋은 42%다. 파인튜닝 GLiNER의 의료 컨셉 재현율은 학습 때 본 컨셉에서 96.5%, 처음 보는 컨셉(40개)에서 77.5%다(3.5절). 그래서 이 셋은 "표현이 바뀌어도 학습한 키워드를 잡는가"를 보는 셋이다. 처음 보는 질의에서의 성능은 50문장 셋(09)으로 판단해야 한다.

## 1. 테스트 조건

- **파인튜닝 GLiNER:** 09 1.1절과 같다. `POST /keyword-extraction/llm-compat`, threshold 0.5, 사내 서버 CPU, 순차 호출.
- **LLM:** 09 1.2절과 같은 모델·프롬프트(sha256 `1bb9b021…`). 이번에는 **순차 호출**(동시 1)했다.
- **테스트셋:** NL2SQL 패러프레이즈 셋 573문장. 시드 질의를 표현만 바꿔 쓴 문장이다.
- **학습 데이터와의 겹침:** 파인튜닝 학습 데이터 764건과 대조했다.
  - 573문장이 각각 다른 시드 573개에서 나왔고, 모두 학습 데이터를 만든 시드다. 표현만 바뀌었고 시나리오와 질병·약물 이름은 같다.
  - 똑같은 문장은 없다.
  - 학습 문장과의 최대 4글자 단위 유사도로 나누면 다음과 같다. 다만 문장 유사도가 낮아도 키워드는 겹친다(3.5절).

| 학습 문장과 유사도 | 문장 수 | 의미 |
|---|---|---|
| 0.5 이상 | 101 | 거의 같은 문장 |
| 0.3 ~ 0.5 | 118 | 꽤 비슷함 |
| 0.3 미만 | 354 | 사실상 새 문장 |

## 2. 정답을 만든 방법

이 셋은 Text-to-SQL 평가용이라 키워드 정답이 없다. 문항마다 있는 재료(input)와 정답 SQL에서 아래처럼 결정론적으로 끌어냈다(`eval/paraphrase_gold.py`).

| 정답 | 출처 | 개수 |
|---|---|---|
| 의료 컨셉 + 라벨 | 재료의 개념 값 조건 중 진단·약물·시술·검사 컬럼 | 647개 (진단명 283, 약물명 210, 시술명 99, 검사명 55) |
| 방문 유형·성별 | 같은 조건 중 `visit_concept_id`, `gender_concept_id` | 25개 (입원 13, 외래 방문 4, 응급실 방문 1, 여성 6, 남성 1) |
| 테이블 | 정답 SQL이 쓰는 테이블. `observation_period`는 구조용이라 뺐다. person은 성별·나이 컬럼을 쓸 때만 넣었다 | 573문항 |
| 스키마 키워드 | **만들 수 없다** | — |

- 개념 값 조건의 키워드는 99.4%가 질문 문장에 그대로 있어서 위치까지 맞춰 채점할 수 있다. 문장에 없는 4개는 뺐다.
- **재료 오류 25개를 뺐다.** 개념 값 조건 중 일부가 잘못 연결되어 있었다. 예: "측정값" → 진단, "PCI"·"TKA"·"EVT" → 진단, "사쿠비트릴" → 진단, "pH"·"젖산" → 약물, "HbA1c" → 시술. 두 모델이 모두 놓친 항목을 하나씩 검토해 찾았고, 전부 이런 재료 오류였다. 목록은 `paraphrase_gold.py`의 `KNOWN_BAD`에 있다.
  - 이것은 **NL2SQL 데이터셋 자체의 오류**다. Text-to-SQL 학습·평가에도 영향이 있을 수 있어 따로 확인이 필요하다.
- 스키마 키워드는 정답 대신 두 가지로 봤다.
  - 정답 SQL 기준 테이블 재현율: SQL이 쓰는 테이블마다, 그 테이블로 매핑된 스키마 키워드를 하나라도 냈는지 본다.
  - LLM과의 일치도: 정확도가 아니라 두 모델이 얼마나 같은 단어를 내는지다.

## 3. 결과

### 3.1 의료 컨셉 키워드

| 지표 | 파인튜닝 GLiNER | LLM |
|---|---|---|
| TP / FP / FN | 617 / 5 / 30 | 642 / 73 / 5 |
| 정밀도 (참고) / 재현율 / F1 | 99.2 / 95.4 / 97.2 | 89.8 / 99.2 / 94.3 |
| 라벨 오류 (위치는 맞고 라벨이 다름) | 1 | 5 |

라벨별 재현율

| 라벨 | 파인튜닝 GLiNER | LLM |
|---|---|---|
| 진단명 | 265 / 283 (93.6) | **283 / 283** |
| 약물명 | 201 / 210 (95.7) | **210 / 210** |
| 시술명 | **96 / 99** (97.0) | 94 / 99 (94.9) |
| 검사명 | 55 / 55 | 55 / 55 |

- **파인튜닝 GLiNER가 놓친 것 (30개):** 유방암 3, 뇌졸중 2, 말기신부전 2, 관상동맥경화증, 골다공증, 골관절염, 본태성 고혈압, 만성 신부전, 신염, 신증후군 같은 질병명과, DPP-4 억제제 3, SGLT2 억제제 2, ACEi, 이소판 인슐린(NPH) 같은 약물 계열명이다. "시술" 3, "위약" 2, "사망"·"생존"처럼 정답 자체가 애매한 것도 일부 있다.
- **LLM이 놓친 것 (5개):** 전부 "항암화학요법"이다. 정답은 시술명인데 LLM은 약물명으로 낸다.
- **LLM의 오탐 73개는 대부분 오류가 아니다.**
  - 61개는 문장에 있지만 SQL 조건이 아니라서 정답에 없는 컨셉이다. 예: 유방절제술, 시타글립틴, 졸레드론산, 혈액투석. 앞에서 뺀 재료 오류 위치(PCI, TKA, PJI 등)를 LLM이 맞는 라벨로 낸 것도 여기에 들어간다.
  - 실제 오류는 "측정값"·"검사값"을 검사명으로 낸 것(8), "OMOP CDM"(3), EXCLUDE 라벨 항목(7) 정도다.
  - 그래서 정밀도 차이(99.2 vs 89.8)는 그대로 믿으면 안 된다. 파인튜닝 GLiNER가 보수적으로 낸다는 정도로 읽어야 한다.

### 3.2 방문 유형·성별 키워드

| 지표 | 파인튜닝 GLiNER | LLM |
|---|---|---|
| 잡음 / 25 | 25 | 25 |
| 맞는 라벨로 냄 / 25 | **25** | 23 |

- LLM이 틀린 2개는 둘 다 "여성"을 성별이 아니라 VALUE(값)로 낸 것이다. 50문장 셋(09 3.3절)과 같은 경향이다.
- 25개 중 입원이 13개, 남성이 1개라 표본이 작고 치우쳐 있다. 정밀도는 정답이 SQL 조건에만 있어서 재지 않았다.

### 3.3 스키마 키워드

**(1) 정답 SQL 기준 테이블 재현율.** 스키마 키워드의 `table`만으로 정답 SQL의 테이블을 얼마나 잡는지 본다.

| 지표 | 파인튜닝 GLiNER | LLM |
|---|---|---|
| 응답 그대로: 커버리지 | 71.0% | **86.6%** |
| 응답 그대로: person 제외 P / R | 80.5 / 75.3 | 81.9 / **88.1** |
| 다운스트림 추론 포함 (가정): 커버리지 | 94.6% | **98.8%** |
| 다운스트림 추론 포함 (가정): person 제외 P / R | 83.8 / 95.7 | 83.1 / **99.0** |

테이블별 재현율 (응답 그대로 → 다운스트림 추론 포함)

| 테이블 | 정답 수 | 파인튜닝 GLiNER | LLM |
|---|---|---|---|
| person | 39 | 100 → 100 | 100 → 100 |
| visit_occurrence | 17 | 100 → 100 | 100 → 100 |
| condition_occurrence | 247 | 74 → 95 | 86 → 100 |
| drug_exposure | 204 | 87 → 95 | 99 → 100 |
| procedure_occurrence | 105 | **29** → 98 | 69 → 95 |
| measurement | 69 | 83 → 91 | 78 → 99 |
| death | 80 | 99 → 99 | 99 → 99 |

- person은 정답 기준상 성별·나이를 쓸 때만 정답이라, 두 모델 모두 정밀도가 낮다(8%). 그래서 P/R은 person을 빼고 봤다.
- 차이는 procedure_occurrence에서 가장 크다(29% vs 69%). 시술 문장에서 "시행일", "기록" 같은 스키마 단어를 파인튜닝 GLiNER가 내지 않는다.

**(2) LLM과의 일치도 (참고).** LLM의 스키마 키워드를 기준으로 봤다(`eval/schema_agreement.py`).

| 지표 | 값 |
|---|---|
| 스키마 키워드 수 | 파인튜닝 GLiNER 1,364 / LLM 1,674 |
| LLM 키워드 중 파인튜닝 GLiNER도 낸 비율 (위치 기준) | 76.6% |
| 파인튜닝 GLiNER 키워드 중 LLM도 낸 비율 (위치 기준) | 94.1% |
| 위 두 값, 테이블까지 같을 때 | 75.4% / 92.6% |
| 두 모델의 스키마 키워드가 완전히 같은 문장 | 279 / 573 (48.7%) |

파인튜닝 GLiNER는 LLM이 내는 스키마 키워드의 부분집합에 가깝다. 다르게 낸 것 중 많은 것은 다음과 같다.

| LLM만 냄 (412개 중 상위) | 파인튜닝 GLiNER만 냄 (101개 중 상위) |
|---|---|
| 대상자→person 38, 코호트→person 13, 개인별→person 8, 사람→person 7 | 환자→person 16, 환자별→person 4 |
| 추적 종료일→observation_period 23, 종료 사유 8, 추적 종료 시점 7 | 추적 종료일·추적기간·추적 종료 → table 없음 25 |
| 최초 발생일→condition 16, 이력→condition 8, 발생한 날짜 7 | 진단→condition 6 |
| 시행일→procedure 15, 기준일→procedure 8, 이력→procedure 7 | 시술→procedure 5 |
| 노출 이력→drug 11, 기준일→drug 10, 시작일→drug 6 | 처방→drug 10, 처방일→drug 6 |

- 파인튜닝 GLiNER는 "추적 종료일" 같은 관찰 기간 표현을 잡기는 하지만 `table`을 비워 둔다. observation_period가 매핑에 없는 것으로 보인다.
- "대상자", "사람"을 놓치는 것은 50문장 셋(09 4절)과 같다. 학습 데이터의 라벨 범위를 확인해야 한다.

|---|---|---|
| 평균 | **0.55초** | 1.34초 |

- 파인튜닝 GLiNER는 응답 시간이 고르다. LLM은 출력 길이에 따라 크게 흔들린다.

### 3.5 학습 데이터와의 겹침

**(1) 키워드 단위.** 정답 컨셉이 학습 데이터에서 정답 span으로 나온 적이 있는지 봤다(공백 무시).

| 셋 | 정답 컨셉 | 학습 정답 span에 있음 | 학습 문장에 등장 |
|---|---|---|---|
| 50문장 셋 (09) | 81 | 34 (42%) | 40 (49%) |
| 패러프레이즈 전체 | 647 | 607 (**94%**) | 627 (97%) |
| 패러프레이즈 중 새 문장 354 | 454 | 426 (**94%**) | 438 (96%) |

| 파인튜닝 GLiNER 의료 컨셉 재현율 | 값 |
|---|---|
| 학습 때 본 컨셉 | 96.5% (586 / 607) |
| 처음 보는 컨셉 | **77.5%** (31 / 40) |

- 처음 보는 컨셉은 40개뿐이라 대략적인 수치지만, 차이가 크다. 이 셋의 높은 재현율은 상당 부분 학습한 키워드를 다시 본 결과다.
- LLM은 이 데이터로 학습하지 않았으므로 이 겹침의 영향을 받지 않는다. 그래서 이 셋에서도 의료 컨셉 재현율이 LLM보다 낮다는 점은 오히려 약점을 보여 준다.

**(2) 문장 단위.** 학습 문장과 비슷한 정도로 나눠 같은 채점기로 쟀다.

| 지표 | 파인튜닝 GLiNER: 새 문장 354 | 파인튜닝 GLiNER: 비슷한 문장 219 | LLM: 새 문장 354 | LLM: 비슷한 문장 219 |
|---|---|---|---|---|
| 의료 컨셉 재현율 | **96.5** | 92.7 | 99.3 | 99.0 |
| 의료 컨셉 정밀도 (참고) | 99.5 | 98.4 | 90.7 | 87.6 |
| 방문 유형·성별 | 23 / 23 | 2 / 2 | 21 / 23 | 2 / 2 |
| 테이블 재현율, 응답 그대로 (person 제외) | 74.7 | 76.9 | 87.2 | 90.0 |
| 테이블 커버리지, 다운스트림 추론 포함 | 97.5% | 90.0% | 99.2% | 98.2% |

- 새 문장(유사도 0.3 미만)에서도 점수가 떨어지지 않는다. 문장 전체를 외운 효과는 아니라는 뜻이다. 하지만 (1)처럼 새 문장도 키워드는 학습 때 본 것이라, **이 비교로는 오염을 가려낼 수 없다.**
- 비슷한 문장 쪽이 낮은 것은 그쪽에 질병명 누락(유방암, 뇌졸중 등)이 몰려 있기 때문이다.

## 4. 해석

1. **의료 컨셉은 학습한 키워드에서는 LLM과 비슷하다.** 재현율이 4점 낮지만 정밀도가 높다. 다만 처음 보는 컨셉의 재현율은 77.5%로 떨어진다(3.5절). 운영 질의에는 학습에 없는 질병·약물이 계속 나오므로, 이 셋의 95.4보다 50문장 셋의 결과(09)가 실제에 가깝다.
2. **스키마 키워드는 50문장 셋보다 차이가 크다.** 50문장 셋에서는 F1로 LLM보다 높았지만, 이 셋에서는 날짜·이력·대상 표현을 덜 낸다. 이 셋의 문장이 50문장 셋보다 길고(평균 50자 vs 32자) 연구 설계 문장("노출 코호트로 정의한다", "추적 종료일")이 많기 때문으로 보인다. 이 단어들이 엔진에 꼭 필요한지(6절 3항)에 따라 영향이 달라진다.
3. **다운스트림 추론을 포함하면 차이가 4%p로 줄어든다** (94.6% vs 98.8%). 엔진이 의료 컨셉 라벨로 테이블을 정할 수 있다면 스키마 단어 누락의 영향은 작다.
4. **운영 측면은 LLM보다 낫다는 결론이 그대로다.** 실패 0건, 응답 시간이 짧고 고르다.

## 5. 이 비교의 한계

- **완전한 홀드아웃이 아니다.** 학습 데이터와 같은 시드에서 나와 정답 컨셉의 94%가 학습 데이터에 있다. 파인튜닝 GLiNER에 유리하다(3.5절).
- **정답이 사람이 단 것이 아니다.** 재료와 SQL에서 끌어낸 정답이라, SQL 조건에 쓰인 컨셉만 있다. 정밀도는 참고용이고, 스키마 키워드 F1은 잴 수 없다.
- **재료 오류를 사람이 걸러냈다.** 두 모델이 모두 놓친 항목만 검토했다. 한 모델만 놓친 항목에도 재료 오류가 남아 있을 수 있다(예: "시술", "사망", "생존").
- **방문 유형·성별 표본이 작다** (25개, 입원 13개).
- **threshold:** 파인튜닝 GLiNER 0.5는 여전히 검증하지 않은 값이다.
- **LLM 조건:** 09와 같다(테이블 목록 대체본, thinking 끔).
- **조건 항목:** 정답이 없어 보지 않았다. GLiNER는 여전히 내지 않는다.
