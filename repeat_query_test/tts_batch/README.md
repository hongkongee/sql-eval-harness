# TTS 프롬프트 고정, temperature 0으로 10개 질의 반복 (2026-11-12)

TTS 코드 기준(temperature 0.0)으로도 SQL이 매번 달라지는지, 동시 요청이 영향을 주는지 확인했습니다.

## 방법

- **질의 10개:** `test_set/eval_ready/`에서 골랐습니다. paraphrase 3, concept 3, slot 2, restructure 2개이고 모두 MEDIUM/HARD입니다.
- **프롬프트 고정:** TTS `/rag`(`http://10.1.1.69:8080`)를 질의당 1번 호출해 user 프롬프트를 저장했습니다(`rag/<id>.json`).
  - `seed_263`은 '인슐린'을 못 찾아서(`concept_unmapped`), 테스트셋 input의 concept_id를 확정 개념으로 넣어 1번 더 호출했습니다.
  - 외부 노출 서버라 `/rag` 호출은 모두 11번이었고, 그 뒤로는 저장한 프롬프트만 썼습니다.
- **요청 형태:** TTS `prompt_builder.build_messages`, `ChatClient.complete`와 같습니다. system은 TTS system 프롬프트(개념 후보가 있으면 자리표시자 규칙을 덧붙임), user는 `/rag` 프롬프트입니다. 설정은 `model=by-loss`, `temperature=0.0`, `max_tokens=4096`이고, 요청 본문은 `requests.json`에 있습니다.

| 조건 | 내용 | 요청 수 |
|---|---|---|
| `seq` | 질의마다 5번을 하나씩 순서대로 | 50 |
| `par_same` | 질의마다 같은 요청 5개를 동시에 | 50 |
| `par_mixed` | 10개 질의 × 5번 = 50개를 한꺼번에 동시에 (섞어서) | 50 |

### seed_103 추가 확인 (같은 요청을 순서대로 10번 더)

처음엔 "첫 요청만 A, 나머지는 B"라서 vLLM 프롬프트 캐시(prefix caching, 서버에서 켜져 있음)에 맞았는지가 원인으로 보였습니다. 그래서 `cache_salt`로 캐시를 못 쓰게 한 요청 5번과, 새 salt 하나로 순서대로 보낸 요청 5번을 다시 보냈습니다(`cache_test.py`, `cache_test.jsonl`).

| 조건 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 요청마다 다른 salt (캐시 사용 안 함) | B | **C** | A | **C** | B |
| 같은 새 salt로 순서대로 | B | A | A | **C** | **C** |

캐시 사용 여부와 상관없이, 하나씩 순서대로 보내도 A·B·C가 섞여 나왔습니다. **prefix caching 하나로는 설명되지 않았습니다.**

### seed_103의 세 답은 뜻이 다릅니다

| 답 | 다른 점 | 샌드박스 실행 결과 |
|---|---|---|
| A | 기준 답. 시술 개념 `4006788`(경피적관상동맥확장술), `INTERVAL '14' DAY` | 1행, 추적 종료일 2015-04-26 |
| B | A에서 `INTERVAL '14' DAY`가 **`INTERVAL '14'`**로 바뀜. PostgreSQL에서 단위가 없으면 **14초**로 해석됨 | 1행, 추적 종료일 **2015-04-12 00:00:14** (틀림) |
| C | 시술 개념을 **`4216130`(Percutaneous coronary intervention)**으로 고름. 정답 SQL과 같은 개념 | 0행, **정답과 결과 같음** (EX pass) |

- 토큰 하나만 달라져도 결과가 달라집니다. B는 틀린 결과를 내고, C는 오히려 정답입니다.
- C의 개념은 RAG가 `"경피관상동맥중재술"`과 `"PCI"` 두 표면어로 후보를 따로 줬기 때문에 생긴 갈림입니다. 첫 번째 표면어의 1순위(`4006788`)와 두 번째 표면어의 1순위(`4216130`)가 모두 그럴듯해서, 모델이 거의 반반으로 고민하는 지점입니다.

## 해석

1. **temperature 0이어도 항상 같은 답이 나온다는 보장은 없습니다.** vLLM은 GPU 연산 순서(요청을 묶는 크기, 캐시 사용 여부, 실행 시점의 커널 선택 등)에 따라 아주 작은 소수점 오차가 생깁니다. 다음 토큰 후보 두 개의 점수가 거의 같은 곳에서는 이 오차로 선택이 뒤집힙니다. temperature 0은 "가장 높은 점수의 토큰 선택"일 뿐, 점수 자체가 매번 비트 단위로 같다는 뜻이 아닙니다.
2. **다만 대부분의 질의에서는 드뭅니다.** 이번에는 10개 중 1개에서만 일어났습니다. 그 1개는 갈림길(개념 후보 두 그룹, `INTERVAL` 단위)이 있어서 모델이 확신이 낮은 질의였습니다. "계속 다르게 나온다"면 확신이 낮은 질의가 많거나, 아래 4번 원인이 섞였을 수 있습니다.
3. **동시 요청이 영향을 줄 수는 있지만, 이번 시험에서 주된 원인으로 보이지는 않았습니다.** 50개를 섞어 동시에 보냈을 때 새로 갈린 질의는 없었고, seed_103은 하나씩 순서대로 보내도 갈렸습니다. 동시 요청이 이 오차를 더 자주 일으킬 수는 있습니다(묶는 크기가 계속 바뀌므로).
4. **이번 시험 범위 밖의 원인:** 프롬프트를 고정했으므로 `/rag` 재료(개념 후보 순서, 테이블)가 요청마다 바뀌는 영향은 보지 않았습니다. 실제 TTS에서는 이것도 SQL을 바꿀 수 있습니다. 서버 부하 때문에 `/rag`는 반복 호출하지 않았습니다.

## 줄이는 방법 (적용해 보지는 않음)

- **애매한 재료 줄이기:** 같은 개념이 표면어 두 개(예: "경피관상동맥중재술", "PCI")로 나뉘어 후보가 겹치지 않게 합니다. 정답 개념이 1순위로 오게 하면 모델이 고민할 여지가 줄어듭니다.
- **생성 후 검사:** `INTERVAL 'n'`처럼 단위가 없는 구문은 결정적으로 고칠 수 있습니다.
- **서버 설정:** vLLM 최근 버전에는 묶는 크기와 상관없이 같은 결과를 내는 batch-invariant 모드가 있지만 속도가 떨어집니다. 지금 서버 버전에서 쓸 수 있는지는 확인하지 않았습니다.
