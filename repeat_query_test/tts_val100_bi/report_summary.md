# batch-invariant 모드로 3차 시험 반복 (4차, 2026-11-19)

vLLM batch-invariant 모드(`VLLM_BATCH_INVARIANT=1`)를 켠 서버에 3차(`../tts_val100`)와 같은 시험을 다시 했습니다. 세 설정을 함께 비교한 표는 `../settings_compare.md`에 있습니다.

## 결론

- **답 갈림이 완전히 사라졌습니다.** 1,400건 모두 질의마다 답이 하나였습니다. 순차, mixed, same 어느 조건에서도 갈리지 않았습니다(3차는 100개 중 10개 질의가 갈림).
- **대신 약 1.5~1.6배 느려졌습니다.** 요청당 평균 시간은 순차 5.87초 → 9.41초, mixed 6.71초 → 10.21초입니다.
- **답 자체는 대부분 그대로입니다.**
  - 93개 질의는 3차 순차에서 가장 많이 나온 답과 같은 답이 나왔습니다.
  - 바뀐 7개 중 실행 결과까지 달라진 것은 val_441 하나이고, 정답으로 바뀌었습니다. 나머지 6개는 쓰는 방식만 다르고 결과는 같습니다.
- **갈림이 사라졌다고 답이 맞아진 것은 아닙니다.** 3차에서 갈렸던 질의는 그때 나온 답 중 하나로 굳었을 뿐입니다. 틀린 답으로 굳은 질의(val_445, val_261, val_420, val_468, seed_598)는 계속 틀립니다.

## 방법

| 항목 | 내용 |
|---|---|
| 서버 | vLLM v0.26.0, L40S 1장, 런타임 LoRA(`by-loss`), **`VLLM_BATCH_INVARIANT=1`**. 나머지 설정은 3차와 같음 |
| 질의·프롬프트 | 3차의 `requests.json`을 그대로 씀. `/rag`를 다시 부르지 않았으므로 프롬프트가 글자까지 같음 |
| 반복 | 질의마다 순차 5번, mixed 5번(동시 4개, 3차와 같은 묶음), same 4번(같은 질의 동시 4개). 모두 1,400건 |
| 실행 | 2026-11-19 09:17~11:30 (순차 78.9분, 병렬 53.7분) |
| 오류 | 0건. 재시도 0건, 모든 응답이 정상 종료(`stop`) |
| 동시 처리 확인 | 순차는 500건 모두 혼자 처리됨. 병렬은 900건 모두 서버에서 4개가 동시에 처리됨 |
| 외부 요청 | mixed 500건 중 368건이 외부 요청과 겹침. same은 겹친 응답 없음 |

### 3차에서 갈린 10개는 어느 답으로 굳었나

답 이름은 3차의 이름을 그대로 씁니다(3차 순차 1회차 답 = A). 실행 결과와 정답 일치는 샌드박스 DB에서 확인했습니다.

| 질의 | 3차 (순차 / mixed / same) | 4차 | 4차 답 실행 결과 | 정답 일치 |
|---|---|---|---|---|
| val_441 | ABCCC / BBCAA / CCCC | 모두 A | 1,120행 | **pass** (3차 다수 답 C는 fail) |
| val_445 | ABBAB / BBBAB / AAAA | 모두 A | 18,573행 (B와 같음) | fail |
| val_261 | AAAAB / BAABA / BBBA | 모두 A | 9,103행 (B는 문법 오류였음) | fail |
| val_420 | AAAAA / ABBAA / AAAA | 모두 A | 시간 초과 (3차와 같음) | fail |
| val_720 | AAAAA / BBBBB / BBBA | 모두 B | 6,421행 (A와 같음) | pass |
| val_468 | AAAAA / ABAAB / AAAA | 모두 A | 1,278,608행 | fail |
| seed_598 | AAAAA / AABAA / BAAA | 모두 A | 53,832행 (합병증 동반 당뇨 제외) | fail |
| seed_747 | AAAAA / BAABB / BAAA | 모두 A | 79,941행 | pass |
| seed_690 | AAAAA / BCAAB / BBBB | 모두 B | 66,454행 (A와 같음) | pass |
| seed_547 | AAABB / BBBAB / BBBB | 모두 B | 0행 (A와 같음) | pass |

- **3차 답 중 하나로 굳었습니다.** 10개 모두 3차에서 나왔던 답 중 하나가 되었고, 3차에 없던 새 답은 없었습니다.
- **틀린 답이 다수였던 val_441:** 4차에서는 맞는 답 A로 굳었습니다. 하지만 batch-invariant가 정답을 고르는 기능은 아닙니다. 계산 경로가 하나로 고정되면서 그 경로의 답이 우연히 A였던 것으로 봐야 합니다.

## 결과: 3차와 답이 달라진 질의

3차 순차에서 가장 많이 나온 답과 4차 답을 비교했습니다. 100개 중 93개가 같고, 7개가 달랐습니다.

| 질의 | 3차에서 갈렸나 | 달라진 내용 | 실행 결과 | 정답 일치 |
|---|---|---|---|---|
| val_441 | 예 | 3차 다수 답 C(발사르탄 `1308842` 추가) → A(추가 안 함) | 13,041행 → **1,120행** | fail → **pass** |
| val_445 | 예 | 3차 다수 답 B → A (심부전 조건을 거르는 위치만 다름) | 같음 | fail 그대로 |
| val_720 | 예 | A → B (CTE로 씀) | 같음 | pass 그대로 |
| seed_690 | 예 | A → B (`EXISTS`로 씀) | 같음 | pass 그대로 |
| seed_547 | 예 | A → B (첫 CTE 키워드가 대문자) | 같음 | pass 그대로 |
| val_446 | 아니오 | 3차에 없던 새 답: `MIN(CASE …)` + `HAVING`, 기준일 조건 추가 | 같음 (18,573행) | fail 그대로 |
| val_464 | 아니오 | 3차에 없던 새 답: `person`에서 `EXISTS`로 고름 | 같음 (6,292행) | pass 그대로 |

- **계산 경로가 바뀐 결과입니다.** batch-invariant 모드는 계산 커널 자체를 바꿉니다. 그래서 3차에서 한 번도 갈리지 않던 질의(val_446, val_464)도 다른 답으로 굳을 수 있습니다. 두 질의 모두 쓰는 방식만 다르고 결과는 같았습니다.
- **정확도:** 7개 기준으로 좋아진 질의 1개(val_441), 나빠진 질의 0개입니다.

- **생성 토큰 수:** 거의 같으므로, 느려진 것은 답이 길어져서가 아니라 토큰 하나를 만드는 속도가 느려졌기 때문입니다.
- **동시 처리:** same(같은 질의 4개 동시) 요청당 시간이 순차와 거의 같습니다(9.53초, 9.41초). 동시 처리 능력은 유지됩니다.
- **측정 방식:** 시간은 Mac에서 잰 값이라 네트워크 시간이 포함됩니다. 3차와 같은 방식이므로 비교에는 문제가 없습니다.

## 해석

1. **원인:** 3차의 갈림은 대부분 batch-invariant 모드가 막는 종류의 계산 오차였습니다. 동시에 처리되는 요청 수나 묶음 구성에 따라 계산 순서가 바뀌는 것이 원인이었다고 볼 수 있습니다.
2. **순차 갈림도 사라졌습니다.** 3차 순차는 500건 모두 혼자 처리됐는데도 4개 질의가 갈렸습니다. 4차에서는 이것도 사라졌습니다.
   - 추정: 같은 프롬프트를 두 번째 보낼 때부터 prefix cache를 써서 처리 범위가 달라지는 것이 원인이었을 수 있습니다. batch-invariant 모드는 이런 차이에도 결과가 같도록 만듭니다.
   - 근거: 3차 순차 갈림 중 val_441(ABCCC)은 앞 1·2회차만 다르고 3회차부터 같은 답이었습니다. 하지만 seed_547(AAABB)처럼 뒤에서 바뀐 경우도 있어서, 이 추정은 검증되지 않았습니다.
3. **런타임 LoRA:** "런타임 LoRA 경로 때문에 갈린다"는 NeurIPS 2026 논문의 주장은 적어도 이 환경에서는 나타나지 않았습니다. batch-invariant 모드를 켜자 LoRA를 그대로 둔 채로 갈림이 0이 되었습니다. LoRA 병합 시험(`../tts_val100_merge`)은 병합만으로도 줄어드는지 보는 비교로 의미가 있습니다.
4. **남는 문제는 모델의 답 품질입니다.** 일관성은 해결됐지만, 굳은 답이 틀린 질의는 그대로 틀립니다. concept_id 선택(seed_598), 후보 5개 모두 넣기(val_261, val_420) 같은 문제는 `/rag` 후보 정리, 생성 후 검사, 재학습으로 풀어야 합니다(`../tts_val100/report_summary.md`의 "줄이는 방법").
5. **운영에 쓸지는 속도와 맞바꿀 문제입니다.** 요청당 약 3.5초가 더 걸립니다. TTS 응답 시간 요구와 사용자 수를 보고 정해야 합니다.
