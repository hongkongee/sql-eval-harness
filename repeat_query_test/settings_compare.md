# 서버 설정별 답 갈림·속도 비교

같은 질의 100개를 서버 설정만 바꿔 세 번 시험하고, **답이 얼마나 갈리는지**와 **속도**를 한눈에 비교합니다. 시험별 세부 결과는 각 폴더의 md에 있습니다.

| 시험 | 서버 설정 | 폴더 | 세부 결과 | 날짜 |
|---|---|---|---|---|
| 기준 (3차) | 설정 변경 없음 (런타임 LoRA) | `tts_val100/` | `tts_val100/report_summary.md` | 2026-11-18 |
| batch-invariant | `VLLM_BATCH_INVARIANT=1` (런타임 LoRA) | `tts_val100_bi/` | `tts_val100_bi/report_summary.md` | 2026-11-19 |
| LoRA 병합 | LoRA를 베이스에 병합해 단독 서빙, batch-invariant 꺼짐 | `tts_val100_merge/` | `tts_val100_merge/report_summary.md` | 2026-11-19 |

## 공통 조건

- **질의:** 100개, 3차와 같은 `requests.json`. `/rag`는 다시 부르지 않았으므로 프롬프트가 글자까지 같습니다.
- **반복:** 질의마다 14번(순차 5번, mixed 5번, same 4번). 시험마다 1,400건입니다.
  - mixed: 서로 다른 질의 4개를 동시에 보냄. 묶음 구성은 세 시험이 같습니다.
  - same: 같은 질의 4개를 동시에 보냄.
- **생성 설정:** temperature 0, max_tokens는 TTS 설정과 같습니다.
- **서버:** vLLM v0.26.0, NVIDIA L40S 1장, bf16, prefix caching 켜짐, CUDA graph 켜짐. 표에 적은 설정만 다릅니다.
- **모델 이름:** 기준과 batch-invariant는 `by-loss`(런타임 LoRA)입니다. 병합 시험도 같은 IP·포트·모델 이름(`by-loss`)으로 띄웠습니다. `by-loss` 체크포인트를 베이스에 병합한 모델(`…/merged`)이며 LoRA는 붙어 있지 않습니다.

- 바라는 결과: 다른 답 비율이 0에 가깝고, 시간은 크게 늘지 않는 것.

## 5. 결론 (시험 후 작성)

- **batch-invariant:** 1,400건 모두 질의마다 답이 하나로 같았습니다. 순차·mixed·same 어느 조건에서도 갈림이 없었습니다. 대신 요청당 시간이 약 1.5~1.6배 늘었습니다. 답이 바뀐 7개 중 실행 결과가 달라진 것은 val_441 하나뿐이고, 이 질의는 정답으로 바뀌었습니다. 다만 이것은 어느 답으로 굳느냐의 문제라 우연에 가깝습니다. 자세한 내용은 `tts_val100_bi/report_summary.md`를 보세요.
- **LoRA 병합:** 갈림이 줄었지만(갈린 질의 10 → 5개, 순차 1.4% → 0.2%, mixed 3.4% → 1.6%) 없어지지는 않았습니다. 속도는 오히려 7~9% 빨라졌습니다(런타임 LoRA 계산이 빠지므로). concept_id 갈림 중 seed_598은 그대로 남았습니다. 자세한 내용은 `tts_val100_merge/report_summary.md`를 보세요.
- **원인 판단:** batch-invariant 하나로 갈림이 모두 사라졌고, 병합은 일부만 줄였습니다. 따라서 **주 원인은 배치 구성에 따른 계산 순서 차이**입니다. 런타임 LoRA 경로는 갈림을 늘리는 요인이기는 하지만(병합하면 절반으로 줄어듦), 그것만으로 설명되지 않습니다. 병합해도 같은 계산 순서 문제가 남기 때문입니다. 아래는 시험 전에 정해 둔 판단 기준입니다.

| 결과 | 해석 |
|---|---|
| batch-invariant에서 갈림이 사라짐 | 배치 구성에 따른 계산 순서 차이가 원인 |
| batch-invariant로는 남고, 병합하면 사라짐 | 런타임 LoRA 경로가 원인 |
| 둘 다 일부만 줄어듦 | 두 원인이 겹침. 둘 다 켠 시험이 추가로 필요 |
| 둘 다 그대로 | 다른 원인(prefix caching, CUDA graph 등)을 더 봐야 함 |

#### LoRA 병합

| 구분 | 내용 | 근거 |
|---|---|---|
| 장점 | 갈림이 절반으로 줄어듦 (갈린 질의 10 → 5개, mixed 3.4% → 1.6%) | 시험 확인 |
| 장점 | 약 7~9% 빨라짐 (순차 5.87초 → 5.34초) | 시험 확인 |
| 장점 | SQL 품질 유지 (정답 일치 64 → 65) | 시험 확인 |
| 단점 | **갈림이 남음.** 5/100 질의가 여전히 갈리고, concept_id가 갈리는 seed_598도 그대로임. "늘 같은 답"이 요구사항이면 이것만으로는 부족함 | 시험 확인 |
| 단점 | **병합하면 답이 바뀜.** 9/100 질의의 답이 기준과 달라졌고, 그중 val_261은 문법 오류 답으로 굳음. 병합본을 만들 때마다 정확도를 다시 검증해야 함 | 시험 확인 |
| 단점 | **어댑터 여러 개를 한 서버에 못 올림.** 지금은 베이스 하나에 `by-loss`·`final-step`을 같이 올려 비교함. 병합하면 어댑터 하나가 14B 모델 하나가 되는데, L40S 1장(46GB)에는 하나만 들어감 | 구성 확인 (`serve_vllm.sh`, GPU 사양) |
| 단점 | **체크포인트를 바꿀 때마다 병합과 재시작이 필요함.** 재시작하는 몇 분 동안 서비스가 멈춤. 런타임 LoRA는 베이스를 그대로 두고 어댑터만 바꿈 | 구성 확인 (이번 시험에서도 재배포함) |
| 단점 | **디스크.** 어댑터는 수백 MB인데 병합본은 체크포인트마다 약 28~30GB(14B bf16). 되돌리려면 베이스·어댑터·병합본을 모두 보관해야 함 | 추정 (모델 크기로 계산, 실제 파일 크기는 확인 안 함) |
| 단점 | **파이프라인에 단계가 늘어남.** 학습 → 병합 → 검증 → 서빙. 지금 `serve_vllm.sh`는 런타임 LoRA 방식만 지원함 | 구성 확인 |
| 단점 | **어느 체크포인트인지 추적하기 어려움.** 이번 병합본 경로도 `…/merged`뿐이라 어느 체크포인트인지 따로 확인해야 했음. 이름 규칙이나 메타 파일이 필요함 | 구성 확인 |
| 단점 | 병합할 때 가중치를 bf16으로 다시 반올림하면서 생기는 미세한 차이 | 추정 (이번 시험에서 품질 차이는 없었음) |

#### batch-invariant

| 구분 | 내용 | 근거 |
|---|---|---|
| 장점 | 갈림이 완전히 사라짐 (1,400건 모두 질의마다 같은 답, 외부 요청이 섞여도 같음) | 시험 확인 |
| 장점 | SQL 품질 유지 (정답 일치 64 → 65) | 시험 확인 |
| 장점 | 런타임 LoRA를 그대로 쓸 수 있음 (어댑터 여러 개 서빙, 교체 방식 유지) | 시험 확인 |
| 단점 | **약 1.5~1.6배 느려짐.** 토큰 생성 속도 0.64배, 순차 5.87초 → 9.41초 | 시험 확인 |
| 단점 | **사용자가 몰리면 더 느려질 수 있음.** 이번 시험은 동시 4개까지였음. 처리량이 줄어 대기열이 길어지면 1.6배보다 더 느려질 수 있음 | 추정 (동시 5개 이상은 시험 안 함) |
| 단점 | **비교적 새 기능.** 버전마다 지원 조건이 바뀜(v0.20 문서는 CC 9.0 이상, v0.26 문서는 8.0 이상). vLLM을 업그레이드할 때마다 동작을 다시 확인해야 함 | 문서 |
| 단점 | 지원하는 어텐션 백엔드에서만 동작하므로 선택지가 줄어듦 | 문서 |
| 단점 | **같은 환경 안에서만 같음.** vLLM 버전, GPU, 모델이 바뀌면 답이 다시 바뀜. 바뀐 뒤에도 일관되지만 기존 답과 같다는 보장은 없음 | 추정 (원리상, 시험 안 함) |
| 단점 | 기동할 때 경고나 제약이 있었는지 로그를 확인하지 않음 | 확인 안 함 |

#### 두 방법 공통

| 구분 | 내용 | 근거 |
|---|---|---|
| 단점 | **재시도가 소용없어짐.** 갈릴 때는 다시 보내면 다른 답이 나올 수 있었음(예: 3차 val_261은 순차 5번 중 1번만 문법 오류). 일관되게 바뀌면 같은 오류가 반복됨. TTS에 SQL 오류 시 재시도하는 로직이 있다면, 오류 메시지를 넣는 등 입력을 바꿔야 의미가 있음 | 시험 확인 (val_261 사례) + 추정 (TTS 재시도 로직은 확인 안 함) |
| 단점 | **현재 답이 바뀜.** 기준과 다른 답이 나온 질의가 7~9개. 기존 결과를 저장해 비교하는 곳이 있으면 영향을 받음 | 시험 확인 |
| 단점 | **시험 범위가 좁음.** 질의 100개, 동시 4개, 설정마다 한 번씩만 실행함. 속도는 그날 외부 요청의 영향도 받음. 운영 부하와 전체 평가 세트에서는 확인하지 않음 | 시험 조건 |
| 공통 | 어느 설정도 답을 맞게 만들지는 않음. 틀린 답은 틀린 채로 굳음 | 시험 확인 |

#### 상황별 선택

| 상황 | 권하는 설정 |
|---|---|
| 운영에서 어댑터 하나만 쓰고 자주 바꾸지 않음 | **LoRA 병합.** 단점이 대부분 관리 비용이라 거의 이득임 |
| 운영 서버에서 어댑터를 자주 바꾸거나 여러 개를 비교함 (개발 중인 지금) | **현재 방식(런타임 LoRA) 유지** |
| "같은 질문에 늘 같은 답"이 꼭 필요함 | **batch-invariant 필수.** 속도 손해를 줄이려면 병합과 함께 쓰는 조합이 후보 (추가 시험 필요) |

- **운영 권고:**
  - 답이 갈리지 않아야 한다면 batch-invariant 모드가 유일하게 확실한 방법입니다. 대가는 요청당 약 1.5~1.6배의 시간입니다.
  - 병합은 속도에 손해가 없고 갈림을 절반으로 줄이므로, batch-invariant를 쓰지 않더라도 해 둘 만합니다.
  - **병합 + batch-invariant**를 함께 쓰면, 병합으로 빨라진 만큼 batch-invariant의 느려짐을 일부 상쇄할 수 있을 것으로 보입니다(미검증). 운영 적용 전에 이 조합을 한 번 더 시험하는 것을 권합니다.
  - 어떤 설정도 답을 맞게 만들지는 않습니다. 틀린 답으로 굳은 질의는 `/rag` 후보 정리, 생성 후 검사, 재학습으로 따로 풀어야 합니다.
