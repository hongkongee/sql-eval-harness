# LoRA를 베이스에 병합해 3차 시험 반복 (5차, 2026-11-19)

`by-loss` LoRA 어댑터를 베이스 모델에 병합해 단독으로 서빙하고, 3차(`../tts_val100`)와 같은 시험을 다시 했습니다. batch-invariant 모드는 껐습니다. 세 설정을 함께 비교한 표는 `../settings_compare.md`에 있습니다.

## 결론

- **갈림이 절반으로 줄었지만 없어지지는 않았습니다.**
  - 갈린 질의: 100개 중 10개 → 5개
  - 다른 답 비율: 순차 1.4% → 0.2%, mixed 3.4% → 1.6%, same 1.0% → 0.2%
- **속도는 오히려 7~9% 빨라졌습니다.** 요청당 평균 시간이 순차 5.87초 → 5.34초, mixed 6.71초 → 6.24초입니다. 요청마다 LoRA를 따로 계산하던 부분이 빠졌기 때문입니다.
- **concept_id 갈림:**
  - val_441: 틀린 답 C(발사르탄 단일제 추가)가 사라졌습니다. 남은 두 답 A, B는 모두 정답입니다.
  - seed_598: 합병증 동반 당뇨를 빼느냐 마느냐로 여전히 갈립니다.
- **답 자체가 바뀐 질의:** 3차 순차에서 가장 많이 나온 답과 다른 답이 나온 질의가 9개입니다. 이 중 4개는 실행 결과도 달라졌습니다.
  - 좋아진 것: val_441 (fail → pass)
  - 나빠진 것: val_261. 정답 일치는 fail 그대로지만, 3차에서 가끔 나오던 문법 오류 답으로 굳었습니다.
- **batch-invariant 모드와 비교:** batch-invariant 모드는 갈림을 0으로 만들었습니다. 따라서 주 원인은 런타임 LoRA가 아니라 배치 구성에 따른 계산 순서 차이로 보입니다. 병합은 그 원인 중 일부를 줄인 것입니다.

답 이름은 3차의 이름을 그대로 씁니다(3차 순차 1회차 답 = A). N은 3차에 없던 새 답입니다. 실행 결과와 정답 일치는 샌드박스 DB에서 확인했습니다.

|---|---|---|---|---|
| val_441 | ABCCC / BBCAA / CCCC | BBBBB / AAABB / ABAA | 쓰는 방식 (B는 A 끝에 `HAVING COUNT(*) >= 1`만 붙임) | A·B 모두 1,120행 pass. 틀린 C는 사라짐 |

## 해석

1. **런타임 LoRA는 갈림을 늘리는 요인이지만 주 원인은 아닙니다.** 병합하면 갈림이 절반으로 줄지만, batch-invariant 모드 없이는 계산 순서 차이가 남습니다. batch-invariant 모드는 LoRA를 그대로 둔 채로 갈림을 0으로 만들었습니다.
2. **병합은 손해가 없는 개선입니다.** 갈림이 줄고 속도도 빨라집니다. 다만 어댑터를 바꿀 때마다 병합본을 새로 만들어야 하고, 한 서버에 여러 어댑터(`by-loss`, `final-step`)를 함께 올려 비교하는 방식은 쓸 수 없습니다.
3. **병합하면 답이 바뀝니다.** 계산 경로가 달라져 91개만 3차와 같은 답이 나왔습니다. 결과가 달라진 4개 중 좋아진 것은 val_441, 나빠진 것은 val_261(문법 오류로 굳음)입니다. 병합 전후로 정확도를 평가 세트에서 다시 확인해야 합니다.
4. **다음 시험 후보: 병합 + batch-invariant.** 병합으로 빨라진 만큼 batch-invariant의 느려짐을 일부 상쇄할 수 있을 것으로 보입니다. 운영에 batch-invariant를 쓴다면 이 조합이 가장 현실적인 후보입니다(미검증).
