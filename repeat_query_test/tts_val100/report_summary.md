# 다양한 유형 질의 100개 반복 요청: 순차·병렬 요약 (3차, 2026-11-18)

NL2SQL 모델(`by-loss`)에 TTS와 같은 요청을 같은 프롬프트로 반복해 보냈습니다. temperature 0.0에서도 답이 갈리는지, 하나씩 보낼 때와 동시에 보낼 때 각각 얼마나 갈리는지 봤습니다.

**순차와 병렬은 서로 따로 셌습니다.** 각 조건 안의 응답끼리만 비교했고, 병렬을 볼 때 순차 답을 기준으로 삼거나 순차에서 갈린 질의를 빼지 않았습니다. 그래서 `report_par.md`(순차 답 기준)와 숫자가 다릅니다.

## 해석

1. **temperature 0이어도 순차에서 1.4%, 병렬에서 3.0%의 응답이 다른 답으로 나왔습니다.** 서버가 요청을 묶어 처리하는 방식에 따라 GPU 계산에 아주 작은 소수점 오차가 생기고, 다음 토큰 후보 두 개의 점수가 거의 같은 곳에서 선택이 뒤집히기 때문입니다. 동시에 처리하는 요청이 많고 매번 바뀔수록(mixed) 더 자주 생깁니다.
2. **갈림은 모델이 원래 애매하게 판단하는 지점에서만 생깁니다.** 90개 질의는 14번 모두 같은 답이었습니다. 갈린 곳은 아래와 같습니다.
   - **애매한 개념 후보:** val_441(한글명이 복합제인 단일 성분), seed_598(반대 뜻의 개념이 후보에 섞임)
   - **덧붙이는 컬럼·조건:** val_468(단위·범위 컬럼), val_420·seed_747(날짜 조건)
   - **표기만 다름:** 대소문자, CTE, EXISTS, CASE 위치. 결과는 같습니다.
3. **"개념 후보 중 1개만 고르라"는 지시를 따르지 않는 문제가 갈림을 키웁니다.** val_261, val_420, val_445, seed_598은 후보 5개를 모두 IN에 넣었습니다. 이것 자체는 매번 같았지만, SQL이 길고 복잡해지면서 괄호나 조건 누락 같은 갈림이 생길 여지가 커집니다.
4. **"결과" 섹션이 가장 많이 갈렸습니다(병렬 4/16).** 측정값·최초 발생일 조회처럼 질의가 출력 형태(컬럼, 집계 방식)를 정하지 않는 유형입니다. HARD는 16개 중 1개(대소문자 차이)만 갈려 난이도와는 관계가 약했습니다.
5. **여러 번 요청해 많이 나온 답을 고르는 방법으로는 막을 수 없습니다.** val_441은 틀린 답이 다수였습니다. 애매한 개념 후보를 줄이고(`/rag` 재료 정리) 후보 1개만 고르게 하는 쪽이 효과가 있을 것입니다.

## 줄이는 방법 (제안, 아직 적용·검증하지 않음)

서버 설정으로 계산 오차를 없애도 **답이 매번 같아질 뿐 맞게 고쳐지지는 않습니다.** val_441은 틀린 답(C)이 다수였으므로, 결정적으로 만들면 틀린 답으로 고정될 수도 있습니다. 그래서 갈림의 원인인 "모델이 애매하게 판단하는 지점"을 줄이는 쪽을 먼저 권합니다.

### concept_id 갈림 줄이기 (val_441, seed_598)

두 질의 모두 `/rag` 개념 후보에 헷갈리는 개념이 섞여 있어서, 모델이 두 선택지 사이에서 거의 반반으로 고민하는 상태였습니다.

**① `/rag` 후보 정리 (효과가 가장 클 것으로 예상)**

| 방법 | 해당 사례 |
|---|---|
| **이름이 정확히 같은 후보가 있으면 그 하나만 확정 개념으로 넣기** | seed_598 1순위 `4008576` "합병증을 동반하지 않은 당뇨병 NOS", val_420 `4066543` "유방절제술" |
| **뜻이 반대인 후보 빼기** ("동반하지 않은 ↔ 동반한", "없는 ↔ 있는" 등) | seed_598 5순위 `442793` 합병증을 **동반한** 당뇨 → EXCEPT로 쓸지 말지가 갈림 |

| **한글명 대신 표준 영문명으로 맞춰 보기** | val_441 `1308842`, seed_598 `201254`(영문명 Type 1 diabetes mellitus인데 한글명은 "합병증을 동반하지 않은 1형 당뇨병") |
| **후보 수 줄이기** (`top_k` 5 → 더 적게, 또는 1순위와 점수 차가 큰 후보 제외) | 모든 질의 |

근거: 이번 시험에서 `/rag`에 확정 개념을 넣어 다시 부른 5개 질의(val_421, val_466, val_471, seed_408, seed_361)는 14번 모두 같은 답이었습니다. 다만 5개뿐이라 충분한 근거는 아닙니다.

**② 개념 고르기와 SQL 생성 나누기 (구조 변경)**

- 지금은 모델이 SQL을 쓰면서 개념도 고르는데, "후보 1개만 고르라"는 지시를 자주 따르지 않습니다. val_261, val_420, val_445, seed_598은 후보 5개를 모두 IN에 넣었습니다.
- 개념을 SQL 생성 전에 따로 정합니다.
  - 이름이 정확히 같으면 규칙으로 바로 정합니다.
  - 애매하면 후보 중 하나만 고르는 짧은 질문으로 정하거나 사용자에게 확인합니다.
- 그다음 확정 개념만 넣어 SQL을 만듭니다. 확정 개념 형식은 모델이 학습 때 본 형식에 가깝습니다.

**③ 생성 후 검사 (빨리 넣을 수 있음)**

- SQL에서 concept_id를 뽑아 아래 경우를 확인합니다.
  - 후보 목록에 없는 ID를 썼는지
  - 표면어 하나에 ID를 2개 이상 썼는지 (val_441 C)
- 걸리면 다시 생성하거나 사용자에게 경고합니다.

**④ 재학습 (다음 버전)**

- 후보 목록 형식에, 반대 뜻 후보나 복합제의 단일 성분 후보처럼 헷갈리는 후보를 섞은 학습 데이터를 넣습니다. 이렇게 해서 "1개만 고르기"를 학습시킵니다. 다른 재학습 방법과 함께 아래 "모델 쪽에서 줄이기"에 정리했습니다.

### 모델 쪽에서 줄이기 (재학습)

갈림에는 두 가지 원인이 겹쳐 있습니다.
- **계산 오차:** 서버가 요청을 묶어 처리하는 방식에서 생깁니다. 모델로는 없앨 수 없고, 서버 설정으로 다뤄야 합니다.
- **후보 점수가 비슷함:** 오차가 있어도 다음 토큰 후보 두 개의 점수가 거의 같을 때만 답이 뒤집힙니다. 90개 질의가 14번 모두 같았던 것도 그 지점들에서는 점수 차가 커서입니다.

모델이 할 일은 두 번째를 줄이는 것, 즉 **애매한 지점에서도 한쪽을 확실히 고르게 만드는 것**입니다. 학습 데이터가 같은 상황에 늘 같은 답을 주면, 모델이 그 답에 큰 점수를 주게 되어 작은 오차로는 뒤집히지 않습니다.

| 방법 | 내용 | 줄어들 갈림 (이번 사례) |
|---|---|---|
| **정답 SQL 쓰는 방식 통일** | 학습 데이터의 정답 SQL을 한 가지 방식으로 맞춥니다. 예: 키워드는 대문자, CTE는 정해진 경우에만, "있는 환자"는 `person` + `EXISTS`처럼 한 패턴, 불필요한 `GROUP BY`·`HAVING COUNT(*) >= 1` 없음, 끝 세미콜론 항상 붙임. SQL 포매터와 규칙 검사로 자동으로 맞출 수 있습니다 | 갈린 10개 중 결과는 같고 쓰는 방식만 다른 5개: seed_547(대소문자), val_720(CTE), seed_690(`FROM procedure_occurrence` ↔ `EXISTS`), val_445(CASE 위치), val_441 A↔B(`HAVING`) |
| **헷갈리는 후보로 학습** (위 ④) | 후보 목록 형식에 반대 뜻 후보, 복합제의 단일 성분 후보, 상위·하위 개념을 섞고, 정답은 늘 1개만 고르게 합니다 | val_441, seed_598(개념 갈림). 후보 5개를 모두 넣는 습관(val_261, val_420, val_445)도 줄어듦 |
| **학습 프롬프트를 서비스 형식에 맞추기** | 지금 모델은 학습용 system 프롬프트와 `[질의]`+`[재료]` 형식으로 학습됐습니다. TTS는 다른 system 프롬프트, 개념 후보 목록, 자리표시자 규칙을 씁니다. TTS 형식으로 만든 학습 데이터를 넣어 처음 보는 형식에서 망설이지 않게 합니다 | 지시를 따르지 않는 문제 전반(후보 1개 고르기, 재료의 조건 그대로 쓰기) |
| **조건을 쓰는 방식 통일** | "기준일 이전 진단 이력", "기준일까지의 사망"처럼 날짜 조건이 있는 문항은 정답 SQL에 늘 같은 자리, 같은 모양으로 조건을 넣습니다. 정답에 조건이 들어갔다 빠졌다 하지 않게 합니다 | val_420(진단 날짜 조건 누락), seed_747(사망일 조건 누락) |
| **출력 컬럼 기본값 통일** | "측정값 조회"처럼 질의가 컬럼을 다 정하지 않는 유형은 정답 SQL의 반환 컬럼을 하나로 정합니다(예: person_id, concept, 측정일, 값, `unit_concept_id`) | val_468(범위 ↔ 단위 컬럼), 1·2차의 q118 |

- **효과 확인:** 재학습한 모델로 이번과 같은 100개 질의를 같은 방식으로 다시 돌려 소수 답 비율(순차 1.4%, 병렬 3.0%)과 갈린 질의 수(10개)를 비교합니다. 갈림 지점의 1·2위 토큰 점수 차(logprobs)를 재 보면 모델이 더 확실해졌는지 직접 볼 수 있습니다. 서버 요청이 들어가므로 실행 전에 확인을 받습니다.
- **한계:**
  - 계산 오차 자체는 남으므로, 아슬아슬한 지점이 새로 생기면 여전히 갈릴 수 있습니다.
  - 입력이 틀린 경우(val_441의 잘못된 한글명 후보)는 모델이 확실해져도 틀린 쪽으로 확실해질 수 있습니다. 그래서 `/rag` 후보 정리(①)와 생성 후 검사(③)는 재학습과 함께 필요합니다.
  - 재학습은 다음 버전의 일이라 지금 모델에는 바로 적용할 수 없습니다.
- **역할 나누기:**
  - 쓰는 방식 차이 → 모델(정답 SQL 쓰는 방식 통일)
  - 개념 갈림 → `/rag` 입력 정리와 모델(헷갈리는 후보로 학습)
  - 계산 오차 → 서버 설정
  - 그래도 남는 의미 차이 → 생성 후 검사

### 설정으로 줄이기 (재학습 없이)

**① 생성 옵션 (요청에 넣는 값): 더 줄일 여지가 거의 없음**

| 설정 | 효과 |
|---|---|
| temperature 0 | 이미 적용함. 항상 점수 1등 토큰만 고름 |
| top_k=1, top_p, seed | temperature 0이면 이미 1등만 고르므로 **추가 효과 없음** |
| repetition_penalty 등 | 관계없음. 오히려 답을 바꿀 수 있음 |

이번 갈림은 1등을 고르는 방식 때문이 아닙니다. **계산 오차로 1등 자체가 바뀌어서** 생긴 것이라, 생성 옵션으로는 더 줄이기 어렵습니다.

**② 서버 실행 설정: 계산 오차 자체를 줄임**

| 설정 | 기대 효과 | 비용·불확실성 |
|---|---|---|
| **batch-invariant 모드** (최근 vLLM) | 묶음 크기와 관계없이 같은 결과를 내도록 만든 모드. 순차·병렬 사이 갈림을 없애는 데 가장 직접적 | 지금 서버 버전에서 되는지 확인 안 함. 느려짐 |
| **LoRA를 베이스에 합쳐 단독 서빙** | 지금은 한 서버가 `by-loss`, `final-step`, 베이스를 같이 띄우고 LoRA를 요청마다 따로 계산합니다. 다른 어댑터 요청과 함께 묶이면 계산 경로가 바뀔 수 있는데, 합치면 이 경로가 사라짐 | 모델마다 서버를 따로 띄워야 함. 효과는 추정 |
| **정밀도 올리기** (bf16 → fp16 또는 fp32) | bf16은 소수점 정밀도가 낮아 비슷한 점수가 오차로 뒤집히기 쉬움 | fp32는 메모리 2배이고 느려짐. fp16은 수치가 넘칠 위험이 있음. 결과가 미세하게 바뀌므로 정확도를 다시 봐야 함 |
| **텐서 병렬 끄기** (GPU 1장으로 서빙) | 여러 GPU로 나눠 계산한 값을 합치는 순서에서 생기는 오차가 없어짐. 14B는 GPU 1장(80GB)에 들어감 | 지금 서버 설정은 확인 안 함. 처리량이 줄어듦 |
| **prefix caching·CUDA graph 끄기** (`--enforce-eager`) | 캐시 사용 여부나 커널 선택에 따라 계산 경로가 달라지는 것을 줄임 | 1차 시험(seed_103)에서는 캐시를 꺼도 갈렸음. 효과가 작을 수 있고 느려짐 |
| **동시 처리 수 1** (`max_num_seqs=1`) | 병렬 갈림을 순차 수준(1.4%)으로 낮춤 | 순차에서도 갈림. 처리량이 크게 떨어짐 |

**③ 생성 방식 제한: 1·2등 점수가 비슷해도 틀린 쪽으로 못 가게 함**

| 설정 | 기대 효과 | 한계 |
|---|---|---|
| **guided decoding으로 개념 선택 제한** (vLLM structured output, `guided_choice`) | 개념을 고를 때 후보 ID 중 하나만 출력하게 강제합니다. 위 "개념 고르기와 SQL 생성 나누기"와 함께 쓰면 val_441 C처럼 ID 2개를 OR로 넣는 답이 나올 수 없음 | 어떤 후보를 고를지가 오차로 바뀌는 것은 남음 |
| **SQL 문법(grammar)으로 생성 제한** | val_261 같은 괄호 불일치·문법 오류를 생성 단계에서 막음 | 문법을 직접 정의해야 함. 의미 차이는 못 막음 |
| **logprobs로 아슬아슬한 답 표시** | 1·2등 점수 차가 작은 토큰이 있으면 "불안정한 답"으로 표시해 검사나 사용자 확인으로 넘김. 갈림을 줄이지는 않지만 위험한 답을 미리 알 수 있음 | 점수 차 기준을 정해야 함 |
| beam search | 한 토큰이 아니라 문장 전체 점수로 고르므로, 한 지점의 근소한 차이에 덜 흔들릴 수 있음 | 느림. 오차가 사라지지는 않음. 효과 불확실 |

- **서버 설정만으로 "항상 같은 답"에 가장 가까운 방법:** batch-invariant 모드와 LoRA를 합쳐서 단독 서빙하는 것입니다. 다만 val_441처럼 틀린 답이 다수인 질의는 **틀린 답으로 고정될 수 있습니다.**
- **재학습 없이 결과를 바로잡는 방법:** guided decoding으로 개념 선택을 제한하고 문법 검사를 하는 쪽이 실용적입니다.
- **진행 조건:** 서버 설정 변경은 서버 관리 쪽과 정해야 합니다. 효과를 보려면 같은 100개 시험을 다시 돌려야 하므로, 실행 전에 확인을 받습니다.

### 권하는 순서

1. **바로:** 생성 후 concept_id·문법 검사(③)와 같은 프롬프트 캐시
2. **효과가 큰 것:** `/rag` 후보 정리(①). 이름이 정확히 같으면 확정하고, 반대 뜻 후보와 복합제의 단일 성분 후보를 뺌
3. **구조 개선:** 개념 고르기 분리(②)와 guided decoding으로 후보 ID 중 하나만 고르게 제한
4. **서버 설정 (서버 관리 쪽과 협의):** batch-invariant 모드, LoRA 합쳐서 단독 서빙
5. **다음 버전 재학습:** 정답 SQL 쓰는 방식 통일, 헷갈리는 후보 학습, TTS 프롬프트 형식 반영 ("모델 쪽에서 줄이기")

**①의 효과를 확인하는 방법:** val_441과 seed_598 프롬프트에서 문제 후보(`1308842`, `442793`)만 빼고, 같은 방식(순차 5번 + 병렬 9번, 질의 2개에 28건)으로 다시 보내 갈림이 사라지는지 봅니다. 아직 하지 않았습니다.
