# TTS 프롬프트 고정, 50개 질의 × 5번 반복: 순차 vs 병렬 (2026-11-17 실행)

TTS(`/Users/seo/Developer/mpx-cdm-tts`)가 `POST /nl2sql`에서 NL2SQL 모델에 보내는 것과 같은 요청을, 같은 프롬프트로 반복해 보냈습니다. 먼저 하나씩 순서대로 보내 병렬 영향 없이 temperature 0에서 답이 갈리는지 보고, 이어서 4개씩 동시에 보내 순차 답과 비교했습니다.

## 결과 요약

> **1·2차 합산 결과(질의 100개)는 `../tts_seq_100_report.md`에 있습니다.** 아래는 1차 50개만 본 결과입니다.

- **실행:** 2026-11-17 17:52~18:21 (약 30분). TTS 서버는 `http://10.1.1.106:8080`, 모델 서버는 `http://10.1.1.69:8007`이었습니다. 요청은 `by-loss`, temperature 0.0, max_tokens 4096입니다.
- **질의:** TTS `tests/test_queries_100.txt`에서 섞어 뽑은 50개입니다. `/rag`는 53번 불렀고, 3개는 `concept_unmapped`로 실패해 뺐습니다(q113·q115·q116, 모두 "~의 최고 측정값을 조회").
- **오류:** 순차 250건, 병렬 450건 모두 오류 없이 응답했습니다.

| 시험 | 요청 수 | 다른 요청과 겹침 | 답이 갈린 질의 | 기준(순차 답)에 없던 새 답 |
|---|---|---|---|---|
| 순차 (하나씩) | 50 × 5 = 250 | 없음 (250건 모두 서버에서 혼자 처리) | **1/50** (q081) | — |
| 병렬 mixed (다른 질의 4개 동시) | 50 × 5 = 250 | 108건은 외부 요청과도 겹침 | **2/50** (q026, q094) | 3건 (우리 요청만 돈 묶음에서 2건) |
| 병렬 same (같은 질의 4개 동시) | 50 × 4 = 200 | 없음 | **1/50** (q026) | 1건 |

**50개 중 47개는 순차 5번, mixed 5번, same 4번, 모두 14번 같은 답**이었습니다. 갈린 질의는 3개입니다.

| 질의 | 순차 | mixed | same | 무엇이 달라졌나 | 실행 결과 |
|---|---|---|---|---|---|
| q081 여성이고 알츠하이머병 진단인 환자 | AAA**BB** | AAAAA | AAAA | 성별을 `gender_concept_id IN (SELECT descendant … 8532)`로 쓰다가 `= 8532`로 씀 | **같음** (1,911행) |
| q026 2014-01-01부터 2018-12-31까지 메트포르민 처방 이력 | AAAAA | A**BB**AA | **B**AAA | 기간 끝 조건을 `drug_exposure_start_date <= '2018-12-31'`로 쓰다가 **`drug_exposure_end_date`**로 씀 | **다름** (15,539 → 15,416행) |
| q094 현재 연도 기준 55세 이상 75세 미만, 이상지질혈증 진단 | AAAAA | **B**AAAA | AAAA | `EXTRACT(YEAR FROM p.birth_datetime')`처럼 **따옴표 하나가 끼어듦** | **문법 오류** (`unterminated quoted string`) |

갈린 회차는 모두 다른 사용자 요청 없이 우리 요청만 처리되던 때였습니다. 예외는 q026 mixed 2회차 하나로, 외부 요청이 섞였습니다.

### 해석

1. **temperature 0이면 대부분 같은 답이 나옵니다.** 순차로 하나씩 보낸 250건 중 답이 갈린 질의는 q081 하나였습니다. 그것도 두 답의 실행 결과가 같았습니다. 지난번 10개 시험(`../tts_batch`)의 seed_103처럼, 순차로 보내도 아주 드물게 갈리는 질의가 있다는 점이 다시 확인됐습니다.
2. **병렬로 보내면 결과가 바뀌는 답이 조금 더 나왔습니다.** 순차에선 5번 다 같았던 q026, q094가 병렬에서만 갈렸고, 두 경우 모두 실행 결과가 달라졌습니다(q026은 행 수가 다르고, q094는 실행이 안 됨). 동시에 처리되는 요청 수가 바뀌면 GPU 연산 순서가 달라져 소수점 오차가 생기고, 이 오차가 점수가 비슷한 토큰 사이의 선택을 뒤집은 것으로 보입니다. 다만 빈도는 낮습니다. 병렬 450건 중 순차에 없던 답은 4건(약 0.9%)이고, 질의 기준으로 50개 중 2개입니다.
3. **실제 TTS는 병렬 상황입니다.** TTS는 LLM 요청을 최대 4개까지 동시에 보내므로(`LLM_CONCURRENCY=4`), 사용자가 많을 때는 이번 병렬 시험과 비슷한 상황이 됩니다. "같은 질의인데 SQL이 다르게 나온다"는 현상은, temperature 0이어도 드물게 생길 수 있습니다. 특히 모델이 두 표현 사이에서 확신이 낮은 질의(q026의 start/end 날짜 컬럼 같은 경우)에서 생깁니다.
4. **이번 시험 범위 밖:** 프롬프트를 고정했기 때문에 `/rag` 재료가 요청마다 달라지는 영향은 보지 않았습니다. 실제 서비스에서 SQL이 자주 달라진다면, 모델보다 재료 쪽 원인이 더 클 수도 있습니다.

### 답과 상관없이 보인 문제 (참고)

- **q026 재료 이상:** `/rag` 재료의 조건이 `[TIME] "2014-01-01부터 2018-12-31까지" → 2014-01-01 이전`으로 잘못 나왔습니다. 기간이 "이전" 하나로 줄었습니다. 모델은 이를 따르지 않고 질의 문장대로 기간을 걸었지만, 재료가 애매해서 끝 날짜 컬럼 선택이 흔들렸을 가능성이 있습니다.
- **[나이] 조건 무시:** q092, q094는 재료가 `person.birth_datetime <= DATE '1971-11-17'`처럼 "그대로 WHERE 에 쓴다"고 줬습니다. 그런데도 모델은 14번 모두 `EXTRACT(YEAR …) - EXTRACT(YEAR …)`로 바꿨습니다. `../tts_style`의 seed_240과 같은 문제입니다.
- **샌드박스 0행:** q094 A의 0행은 샌드박스 DB의 출생 정보가 비어 있어서일 수 있습니다(보안상 비워 둠). 정답 여부 판단에는 쓰지 않았습니다.

## 순서

1. **프롬프트 고정 (`prepare.py`):** 질의마다 TTS `/rag`를 **한 번만** 불러 user 프롬프트를 받습니다(`rag/<qid>.json`). 실패한 질의(개념 못 찾음 등)는 버리고 다음 후보로 50개를 채웁니다. 호출 사이에 3초 쉽니다.
2. **LLM 순차 반복 (`run_seq.py`):** 고정한 요청을 질의마다 5번, 한 번에 하나씩 모델 서버에 보냅니다. `/rag`는 다시 부르지 않습니다.
3. **정리 (`analyze.py`):** `report.md`, `summary.json`을 만듭니다.

## TTS와 같은 요청을 만드는 방법

따라 만든 사본이 아니라 TTS 프로젝트 코드를 직접 import 해서 씁니다(`common.py`).

| 항목 | 출처 (TTS 코드) |
|---|---|
| system + user 메시지 | `app/services/text2sql/prompt_builder.build_messages(materials, dialect=NL2SQL_SQL_DIALECT, mask=True)` — `/nl2sql`의 `generator.generate_sql`과 같은 호출 |
| user 내용 | `/rag` 응답의 `prompt` (TTS 안에서 `_render_materials`로 만든 것) |
| 요청 본문 | `client.ChatClient.complete`와 같은 `{model, messages, max_tokens, temperature}` |
| 설정값 | `app/core/config.py`: `NL2SQL_BASE_URL`, `NL2SQL_MODEL`, `NL2SQL_TEMPERATURE`, `NL2SQL_MAX_TOKENS` (지금 값: `http://10.1.1.69:8007/v1`, `by-loss`, `0.0`, `4096`) |
| 긴 concept_id 목록 | `mask=True`로 `:CONCEPT_IDS_N`으로 가려 보내고, 응답 뒤 원래 id로 되돌림 (TTS와 같음) |

검증: 지난번 `tts_batch`의 `/rag` 응답 10개로 요청을 만들어 보니, 지난번 요청과 10개 모두 같았습니다.

## 병렬 영향을 빼는 방법

- 제 쪽에서는 한 번에 하나씩만 보냅니다.
- 다른 사용자나 TTS 요청이 모델 서버에 들어와 있으면 같이 묶여 처리될 수 있습니다. 그래서 보내기 전에 서버 `/metrics`의 처리 중·대기 요청이 0이 될 때까지 기다립니다(최대 120초).
- 처리되는 동안 0.5초마다 `/metrics`를 읽어 동시에 돈 요청 수의 최댓값을 기록합니다. 다른 요청과 겹친 회차는 `alone=False`로 표시되고, `report.md`에서 "혼자 처리된 요청만 봐도 갈렸는지"를 따로 셉니다.

## 병렬 시험 (순차 시험이 끝난 뒤)

같은 고정 프롬프트(`requests.json`)로 4개씩 동시에 보내고, 순차 답과 비교합니다. `/rag`는 다시 부르지 않습니다.

```bash
nohup caffeinate -i ./run_par_all.sh > run_par.log 2>&1 &
tail -f run_par.log
```

- **동시 4개로 정한 이유:** TTS의 LLM 동시 실행 상한이 기본 4입니다(`config.py`의 `LLM_CONCURRENCY=4`). 실제 서비스에서 모델 서버로 동시에 갈 수 있는 최대치와 같습니다.
- **mixed:** 라운드마다 질의 순서를 섞어 4개씩 묶어 동시에 보냅니다. 같은 질의가 라운드마다 다른 질의들과 함께 처리됩니다(여러 사용자가 동시에 쓰는 상황). 5라운드라 질의당 답이 5개 나옵니다. 50개를 4개씩 묶으면 라운드마다 마지막 묶음은 2개입니다.
- **same:** 같은 질의 요청 4개를 동시에 보냅니다. 질의당 답이 4개 나옵니다.
- 묶음을 보내기 전에 서버가 빌 때까지 기다리고, 묶음 안의 4개는 같은 순간에 출발시킵니다. 처리 중 동시 요청 수가 4를 넘거나 대기가 생기면 외부 요청이 섞인 것으로 표시합니다(`only_ours`).
- **결과 (`report_par.md`):**
  - 순차 답에 없던 "새 답"이 몇 건 나왔는지
  - 순차에선 5번 다 같았는데 병렬에서 달라진 질의가 몇 개인지
  - 갈린 답의 첫 차이와 샌드박스 실행 결과
- **예상 시간:** mixed 65묶음 + same 50묶음, 묶음당 약 10~15초 → **약 25~30분**.
- 옵션(환경변수): `CONC=4`, `REPS=5`, `MODE=both|mixed|same`, `IDLE_WAIT=120`
- 순차와 병렬을 이어서 돌리려면: `nohup caffeinate -i sh -c './run_all.sh && ./run_par_all.sh' > run_both.log 2>&1 &`
