# NL2SQL 모델 평가 — 핵심 요약

> 학습셋과 validation 셋 결과만 추려 정리한 문서입니다. 변형 테스트셋을 포함한 전체 결과와 지표 정의는 [00_overview.md](00_overview.md)에 있습니다.

## 목적

이 테스트의 목적은 두 가지입니다.

1. **베이스 모델과 파인튜닝 모델 비교:** 파인튜닝이 베이스 모델(프롬프트만 설계한 경우 포함) 대비 얼마나 나은지 확인합니다.
2. **파인튜닝 모델 간 데이터셋 구조 비교:** 학습 데이터의 구조(RAG 제공 프롬프트 포함 여부, concept_id 랜덤화 여부)에 따라 어떤 성능 지표에서 우위가 생기는지 확인합니다.

학습 데이터 구조 외의 조건(epoch, AutoML trials, 체크포인트 선택 기준, 평가 시 시스템 프롬프트·재료·생성 설정)은 모두 동일하게 맞췄습니다.

## 테스트 대상 모델

모든 모델은 동일한 자연어 질의와 프롬프트 **재료**를 받습니다. 재료는 질의에 필요한 concept_id 후보, 사용할 수 있는 테이블·컬럼, 조인 방법을 정리한 텍스트입니다. 모델간 다른 점은 학습 데이터셋의 구조입니다.

| 모델 | 설명 |
|---|---|
| 프롬프트 미반영 학습 모델 | 자연어 질의와 정답 SQL만으로 파인튜닝한 모델입니다. 학습 때 재료(concept_id, 테이블 정보 등)를 보지 못했고, 평가 시에만 재료를 받습니다. 재료를 넣어 학습하는 방식의 효과를 측정하기 위한 기준선입니다 |
| 프롬프트 반영 학습 모델 | '질문 + 재료 → 정답 SQL' 로 파인튜닝한 모델입니다. 학습 데이터 612건으로, 위 모델과 건수·정답 SQL·학습 조건이 같고 재료 유무만 다릅니다 |
| 프롬프트 반영 + 코드 랜덤화 학습 모델 | 위 학습 데이터에 concept_id만 무작위 코드로 바꾼 사본 3벌을 더해(총 2,202건) 파인튜닝한 모델입니다. 코드를 외우지 않고 재료에 적힌 코드를 옮겨 쓰도록 하려는 방식입니다 |
| 베이스 모델 | 파인튜닝하지 않은 원본 모델(XiYanSQL-QwenCoder-14B-2504)입니다 |
| 베이스 모델 + 규칙·예시 프롬프트 | 베이스 모델에 직접 설계한 긴 시스템 프롬프트를 붙인 것입니다. 하위 전개 규칙, PostgreSQL 문법 규칙, 정답 SQL 스타일 규칙과 예시 SQL 5개(few-shot)가 들어 있습니다. 파인튜닝 없이 프롬프트만으로 사용 가능한지 확인하는 비교 대상입니다 |

- 파인튜닝 모델은 모두 1 epoch, 같은 AutoML HPO 조건(trials 5)으로 학습했고 eval_loss가 가장 낮은 체크포인트를 썼습니다.
- 파인튜닝 모델 3종과 프롬프트를 설계하지 않은 베이스 모델은 학습 때 쓴 시스템 프롬프트("OMOP-CDM SQL 생성 전문가…, SQL만 출력")를 똑같이 받습니다.

**지표 설명** 
| 지표 | 의미 |
|---|---|
| 문법 유효성 | SQL 문법이 올바르고 샌드박스 DB에서 오류 없이 실행되는 문항 비율 |
| 하위 전개 | 대표 개념 코드(예: 고혈압)를 하위 코드까지 포함하도록 답변 쿼리문에 `concept_ancestor`로 펼쳐 조회한 비율 |
| 프롬프트 반영도 | 정답 SQL에 필요한 concept_id를 모두 조건에 넣었고, 재료에 없는 테이블·컬럼을 쓰지 않은 문항 비율. 코드를 넣은 형식(하위 전개 여부)은 보지 않습니다 |
| EM | 정답 SQL과 문장이 글자 그대로 같은 비율. 결과가 같아도 작성 방식이 다르면 실패이므로 참고용입니다 |
| EX | 정답 SQL과 실행 결과가 같은 비율. |


## 결론

1. **"프롬프트 반영 + 코드 랜덤화 학습 모델"이 성능이 가장 좋습니다.** EX가 학습셋 94.1%, validation 셋 92.1%로 다른 모델보다 17%p 이상 높습니다. 학습하지 않은 데이터에서도 점수가 거의 떨어지지 않았습니다. 변형 테스트셋 4종에서도 EX 90~97%로 가장 높았습니다.
2. **학습할 때 재료(concept_id, 스키마 정보)를 같이 보여주면 정확도가 오릅니다.** 학습 데이터 건수가 동일한 두 모델을 비교하면, 재료를 넣어 학습한 모델의 EX가 9~11%p 높습니다(학습셋 62.6% → 71.6%, validation 셋 63.5% → 74.6%).
3. **차이는 "코드를 찾는 능력"이 아니라 "코드를 정답 형식으로 옮기는 능력"에서 납니다.** 프롬프트 미반영 학습 모델도 필요한 코드는 비슷하게 넣지만(프롬프트 반영도 86~89%), 재료에 적힌 `IN (9202)` 형식을 그대로 베껴서 하위 전개를 26%가량 빠뜨리고 실행되지 않는 SQL도 많습니다(문법 유효성 83~87%).
4. **베이스 모델은 프롬프트의 코드는 잘 반영하지만 하위 전개의 쿼리 구조로 답변하지 않습니다.** 프롬프트 반영도는 가장 높지만(96~98%), 하위 전개를 전혀 하지 않아(0%) EX가 24~26%에 그칩니다.
5. **규칙·예시 프롬프트만으로도 베이스 모델이 크게 좋아지지만, 파인튜닝 모델에는 못 미칩니다.** EX가 베이스 모델 대비 약 40%p 올라 63~66%가 되지만, 프롬프트 반영 학습 모델(72~75%)과 랜덤화 학습 모델(92~94%)보다 낮습니다. 정답 SQL의 작성 방식은 따라 하지 못해 EM이 10% 안팎입니다.
6. **concept_id 랜덤화를 하면 프롬프트 반영도가 좋아집니다.** 프롬프트 반영 학습 모델 대비 프롬프트 반영도가 학습셋 88.2% → 96.4%(+8.2%p), validation 셋 85.7% → 93.7%(+8.0%p)로 올랐습니다. 정답에 필요 없는 코드를 넣는 비율도 학습셋 48.9% → 17.4%로 줄어, 재료의 코드 중 필요한 것만 골라 쓰는 능력이 함께 좋아졌습니다. 학습 때 보지 못한 코드로 바꾼 변형 테스트에서도 EX 89.3%로, 랜덤화하지 않은 모델(67.9%)보다 높았습니다.
7. **주의할 점:** concept_id 랜덤화 학습 모델은 데이터가 3.6배이므로 학습량도 그만큼 많았습니다. 향상이 랜덤화 영향인지, 절대적 학습량 영향인지 아직 구분할 수 없어서 랜덤화로 인한 향상이라고 확정하기 어렵습니다.
