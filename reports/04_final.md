## 1. 핵심 요약

1. **독립 테스트셋 EX는 42.6%(235/552)로, 같은 모델의 val EX 94.1%보다 크게 낮습니다.** 같은 서버·프롬프트·설정으로 val 68건을 다시 돌린 대조 실행이 94.1%(few-shot 5건 제외 시 93.7%, FT3 기존 값과 같음)라서, 서빙이나 프롬프트 설정 문제는 아닙니다.
2. **42.6%도 실제보다 높게 나온 값입니다.** 맞힌 235건 중 195건은 정답이 빈 결과인 문항입니다. 정답이 빈 결과이거나 나이 조건이 있는 문항을 빼면 **EX는 13.6%(38/280)**입니다(→ 3절).
3. **틀린 문항의 가장 큰 원인은 정답 SQL의 출력 컬럼 규칙이 학습 데이터와 다른 것입니다.** 판단용 280건 중 113건은 환자 집합은 정답과 같고 컬럼만 다릅니다. 이 중 87건이 관찰기간 질의입니다. 학습 정답은 `person_id, 시작일, 종료일`(49건 중 47건)을 쓰는데 테스트 정답은 `DISTINCT person_id`만 씁니다(98건). 모델은 배운 대로 답했습니다. 이 87건을 정답으로 세면 판단용 EX는 44.6%(125/280)입니다(→ 4절).
4. **concept_id 선택은 표면어 기준 61.8%만 정답과 같습니다.** 정답이 쓰는 표면어 1,260개 중 779개만 정확히 골랐고, 253개(20.1%)는 아무것도 고르지 않았습니다. 163개(12.9%)는 다른 후보를 골랐습니다. 문항 단위로 concept_id 집합이 정답과 완전히 같은 비율은 41.9%(179/427)입니다(→ 5절).
5. **SQL 문법 오류는 적습니다.** sqlglot 문법 96.4%, 샌드박스 EXPLAIN 92.8%입니다. 실행 불가 40건 중 절반은 4.결과 섹션의 긴 집계 SQL입니다.
6. **응답시간은 평균 7.52초, 중앙값 4.82초입니다.** 난이도가 올라갈수록 출력이 길어져 HARD는 평균 18.1초입니다.
7. **하락 원인 추정:** ① 재료 형식이 다릅니다. 테스트 재료는 `개념 후보`(표면어마다 여러 후보 중 고르기) 형식인데, 로컬의 원본 학습 데이터 612건은 개념이 있는 532건이 모두 `개념 값 조건`(코드가 정해진) 형식입니다. v2 증강 학습 데이터는 로컬에 없어 형식을 확인하지 못했습니다. ② 정답 SQL 작성 규칙(출력 컬럼)이 다릅니다. ③ 시나리오가 모두 새것입니다. 어느 쪽이 얼마나 영향을 주는지는 8절의 추가 실험으로 나눠 봐야 합니다.
8. **점수가 낮은 이유는 대부분 정답 작성 기준과 재료 구성이 학습 때와 다르기 때문이고, 모델 실력 부족은 그다음입니다(→ 7절).**
   - 정답을 하위 전개로 바꾼 것은 학습 데이터와 같은 방식이라 영향이 거의 없습니다.
   - 반면 EX는 정답 SQL이 어떤 concept_id를 정답으로 정했는지, 재료를 어떻게 구성했는지에 따라 크게 달라집니다. 판단용 문항에서 개념을 정답과 똑같이 고르면 EX 43.1%, 틀리면 7.7%입니다.
   - 재료에서 점수를 깎은 부분은 두 가지입니다. 질의에 없는 표면어로 개념을 넣으면 그 개념을 고르지 않은 비율이 59.6%입니다. `[상위개념]` 표시가 정답과 어긋나면 다른 후보를 고른 비율이 27.6%입니다.

## 4. 틀린 원인

### 4.1 컬럼 구성만 다름 — 정답 작성 규칙 차이 (113건)

| 항목 | 건수 | 모델 컬럼 | 정답 컬럼 |
|---|---:|---|---|
| 데이터 기간 [필수] | 87 | `person_id, observation_period_start_date, observation_period_end_date` | `person_id` |
| 1차·2차 결과 | 24 | `person_id, death_status(survival_status), death_date` 등 | `person_id, death_yn(survival_yn), death_date` 등 |
| 기타 | 2 | | |

- **관찰기간 질의는 같은 문장 틀인데 학습과 테스트의 정답 규칙이 반대입니다.**
  - 학습: "관찰기간이 2003-10-01부터 2008-03-31까지의 기간과 겹치는 환자." → `SELECT op.person_id, op.observation_period_start_date, op.observation_period_end_date FROM observation_period op …`
  - 테스트: "관찰기간이 2020-11-18부터 2027-12-31까지의 기간과 겹치는 환자." → `SELECT DISTINCT op.person_id FROM observation_period op …`
  - 조건(WHERE)은 모델과 정답이 같고 환자 집합도 같습니다. 데이터 기간 항목 99건 중 87건이 이 이유로만 틀렸습니다.
- **결과 항목 24건은 컬럼 이름과 값 표기가 다릅니다**(예: `death_status` vs `death_yn`). 환자 집합은 같지만 값 표기(Y/N 등)까지 같은지는 확인하지 않았습니다.
- 이 차이는 모델의 SQL 능력 문제라기보다 정답 규칙 문제입니다. 어느 쪽을 표준으로 삼을지 정한 뒤 다시 채점해야 합니다. 응답을 다시 받을 필요는 없습니다.

### 4.2 concept_id 선택 오류 (판단용 80건)

- 4.결과 섹션이 가장 많습니다. concept_id가 맞는데 EX가 틀린 판단용 문항 37건 중 23건도 4.결과 섹션입니다.

  - id 42 (도자절제술): 정답 `Cardiac ablation for atrial fibrillation` 대신 `Craniectomy`를 고름
  - id 8: 표면어 하나의 개념(432867)을 빠뜨림

## 5. concept_id 선택 기록

재료의 `개념 후보`를 표면어 단위로 파싱해, 모델 SQL과 정답 SQL이 각각 어떤 후보를 썼는지 비교했습니다. 문항별 결과는 `final_concept_choices.csv`에 있습니다(표면어, 후보 수, 모델 선택 id·이름, 정답 id·이름, 판정).

### 5.1 표면어 단위

| 판정 | 정답이 쓰는 표면어 (1,260) | 비율 |
|---|---:|---:|
| 정답 선택 | 779 | 61.8% |
| 선택 안 함 | 253 | 20.1% |
| 다른 후보 선택 | 163 | 12.9% |
| 정답+다른 후보 | 48 | 3.8% |
| 일부만 선택 / 일부+다른 후보 | 17 | 1.3% |

| 판정 | 정답이 쓰지 않는 표면어 (319) | 비율 |
|---|---:|---:|
| 모델도 안 씀 | 193 | 60.5% |
| 모델은 씀 | 126 | 39.5% |

- `{{표면어}}`(미해결)로 남긴 문항은 0건입니다. 맞는 후보가 없을 때도 미해결로 남기지 않습니다.
- 재료에 없는 concept_id를 쓴 문항은 4건입니다(id 174·252·385·457).

### 5.2 문항 단위

| 그룹 | concept_id 일치 |
|---|---:|
| 전체 | 41.92% (179/427) |
| EASY | 58.39% (87/149) |
| MEDIUM | 40.98% (84/205) |
| HARD | 10.96% (8/73) |
| 재료 보정 없음 | 64.75% (79/122) |
| 재료에 후보·개념이 추가된 문항 | 29.12% (76/261) |

- 정답에 필요한 concept_id 1,371개 중 567개를 놓쳤고, 정답에 없는 concept_id를 382개 썼습니다.
- **재료가 보정된 문항에서 낮지만, 원인은 질의에 없는 표면어를 새로 추가한 경우에 몰려 있습니다(→ 7.3절).** 기존 후보 목록에 정답 후보만 끼워 넣은 경우(`candidate_added`)는 정답 선택률이 65.5%로 큰 차이가 없습니다. 반면 질의 문장에 없는 표면어 항목을 새로 만든 경우(`concept_added`)는 "선택 안 함"이 59.6%입니다.

### 5.3 판정 방법

- 모델·정답 SQL에서 `*_concept_id` 컬럼과 비교(`=`, `IN`)되는 정수를 모으고, 재료에 있는 id가 SQL에 나타나면 함께 셉니다. 정답 SQL 552건에 적용하면 테스트셋의 `anchor_concept_ids`를 하나도 빠뜨리지 않습니다.
- 정답 집합 = 정답 SQL에서 뽑은 id ∪ `anchor_concept_ids`. 재료의 허용값(성별·방문유형 등)도 포함합니다.
- 같은 id가 여러 표면어의 후보에 있으면 각 표면어에서 모두 선택한 것으로 봅니다.

## 7. 점수가 낮은 이유 — 테스트셋 구성과 모델

테스트셋은 협력업체 원본 NL-SQL을 그대로 쓰지 않고, 모델 단독 평가를 위해 두 가지를 바꿨습니다.
- 재료(input, RAG가 만드는 부분)는 직접 만들었습니다.
- 정답 SQL은 앵커 concept_id 기반 하위 전개 서브쿼리로 바꿨습니다.

이 절은 그 변형과 모델 자체가 각각 점수에 얼마나 영향을 주는지 정리합니다.

### 7.1 정답 SQL 하위 전개 — 영향 적음

- **학습 데이터도 같은 방식입니다.** 원본 학습 데이터 612건 중 530건(87%)이 `concept_ancestor` 하위 전개를 씁니다.
- **모델도 그대로 씁니다.** 정답이 하위 전개를 쓰는 427건 중 424건에서 모델도 하위 전개를 썼습니다. 정답이 쓰지 않는 125건에서는 모델도 0건입니다.
- **EX는 결과 집합만 비교하므로** SQL 구조가 달라도 결과가 같으면 통과합니다.
- **다만 개념 선택이 정확해야 합니다.** 앵커 하나만 달라도 하위 개념 집합이 달라져 결과가 바뀝니다. 그래서 EX가 개념 선택 결과에 강하게 묶입니다(→ 7.4절).
- **한계:** 협력업체 원본 정답 SQL이 저장소에 없어, 원본으로 채점했을 때와 직접 비교하지는 못했습니다.

### 7.2 재료 형식 — 학습 때와 다름

| | `개념 값 조건` (앵커가 정해진 형식) | `개념 후보` (후보 중 고르는 형식) | 개념 없음 |
|---|---:|---:|---:|
| 원본 학습 데이터 (612) | 532 | **0** | 80 |
| 독립 테스트셋 (552) | 0 | 426 | 126 |

가장 큰 요인으로 보지만, 크기는 같은 문항을 `개념 값 조건` 형식으로 다시 돌려 봐야 따로 잴 수 있습니다(→ 8절 다음 단계 2). v2 증강 학습 데이터는 로컬에 없어 형식을 확인하지 못했습니다.

### 7.3 재료 구성 — 점수를 깎는 두 가지

**(1) 질의에 없는 표면어를 새로 추가한 경우**

정답이 쓰는 표면어 1,260개를 재료 보정 방식에 따라 나눴습니다.

| 표면어 | 개수 | 정답 선택 | 선택 안 함 | 다른 후보 선택 |
|---|---:|---:|---:|---:|
| RAG가 만든 표면어 (보정 없음) | 752 | 71.4% | 9.7% | 16.6% |
| 기존 목록에 정답 후보를 끼워 넣음 (`candidate_added`) | 249 | 65.5% | 19.3% | 15.3% |
| 표면어를 새로 추가, 질의에 있음 (`concept_added`) | 66 | 74.2% | 25.8% | 0% |
| **표면어를 새로 추가, 질의에 없음 (`concept_added`)** | **193** | **40.4%** | **59.6%** | 0% |

- **예시 (id 12):** 질의는 "HCTZ"라고 쓰는데, 재료에 `"히드로클로로티아지드": 974166` 항목을 따로 추가했고 정답은 974166입니다. "HCTZ" 후보 목록에는 성분 수준 개념이 없습니다. 모델은 질의에 나온 표면어의 후보 목록에서 고르므로, 질의에 없는 항목은 쓰지 않는 경우가 많습니다.
- 전체 "선택 안 함" 253건 중 115건(45%)이 이 경우입니다.
- 이런 표면어가 있는 문항은 판단용 EX가 7.4%(54건)입니다. 개념이 있으면서 이런 표면어가 없는 문항은 27.8%(115건)입니다.

**(2) 재료의 지시문과 `[상위개념]` 표시가 정답과 어긋나는 경우**

재료에는 "질의에 수식어가 없으면 [상위개념](하위 포함)을 고른다"는 지시가 있습니다. 그런데 정답 후보에 `[상위개념]` 표시가 없는 표면어가 많습니다. 아래 표는 정답 id가 하나이고 후보 목록에 있는 표면어 1,205개를 집계했습니다.

| 경우 | 개수 | 정답 선택 | 선택 안 함 | 다른 후보 선택 |
|---|---:|---:|---:|---:|
| 정답이 상위개념, 다른 상위 후보 없음 | 198 | 86.9% | 8.1% | 5.1% |
| 정답이 상위개념, 다른 상위 후보도 있음 | 124 | 68.5% | 12.1% | 19.4% |
| 정답은 상위개념 아님, 다른 상위 후보 없음 | 611 | 61.7% | 30.1% | 8.2% |
| **정답은 상위개념 아님, 다른 후보가 상위개념** | **272** | **59.9%** | 12.5% | **27.6%** |

- **예시 (id 1, "관상동맥질환"):** `[상위개념]` 표시는 4187067(Disorder of coronary artery)에 붙어 있는데 정답은 4185932(Ischemic heart disease)입니다. 이 문항은 모델이 맞혔지만, 지시대로 고르면 틀리게 되어 있습니다.

### 7.4 EX는 concept_id 선택에 좌우됨

| 개념 선택 (정답이 concept_id를 쓰는 427건) | 전체 EX | 판단용 EX |
|---|---:|---:|
| 정답과 완전히 같음 | 69.3% (124/179) | 43.1% (28/65) |
| 다름 | 39.5% (98/248) | 7.7% (8/104) |

- EX는 모델의 질의 이해 능력뿐 아니라, **정답 SQL이 어떤 concept_id를 정답으로 정했는지**와 **재료에 후보를 어떻게 넣었는지**에 따라 크게 달라집니다. 예를 들어 상위 개념으로 볼지 세부 개념으로 볼지, 성분으로 볼지 계열로 볼지가 정답 기준에 따라 갈립니다.
- 개념과 무관한 정답 기준도 점수를 크게 바꿉니다. 개념이 없는 125건은 EX가 10.4%인데, 대부분 관찰기간 출력 컬럼 규칙 때문입니다(→ 4.1절).
- **EM은 concept_id보다 SQL 문자열 차이 때문에 낮습니다.** 날짜 표기(`CURRENT_DATE` 대신 날짜 값), 별칭, 조건 순서가 조금만 달라도 틀립니다. val에서도 69.1%였습니다.

### 7.5 모델 쪽 원인 — 복잡한 질의

테스트셋은 학습 데이터보다 질의가 길고 개념이 많습니다.

| | 원본 학습 (612) | val (68) | 독립 테스트셋 (552) |
|---|---:|---:|---:|
| 질문 길이 평균 | 41자 | 40자 | 55자 |
| 정답 SQL 길이 평균 | 514자 | 535자 | 693자 |
| 앵커 개념 수 평균 | 1.19 | 1.25 | 2.36 |
| **앵커 4개 이상 문항** | **0%** | **0%** | **23.4%** |
| 시나리오 수 | 64 | 7 | 114 |

| 앵커 개념 수 | 문항 | EX | concept_id 문항 일치 |
|---|---:|---:|---:|
| 0개 | 125 | 10.4% | — |
| 1개 | 149 | 67.8% | 71.1% |
| 2~3개 | 149 | 54.4% | 39.6% |
| 4개 이상 | 129 | 31.0% | 10.9% |

- 개념이 많아질수록 조건을 통째로 빠뜨리거나 다른 후보를 고르는 경우가 늘어납니다.
- val 94.1%는 val 68건 중 61건이 학습 데이터와 같은 SQL 틀이라 낙관적인 값입니다(`02_val.md`). 이번 테스트셋은 학습 분포 밖에서 처음 잰 점수입니다.

### 7.6 정리

- **테스트셋 몫:** 정답 작성 기준(concept_id 선택, 출력 컬럼)과 재료 구성(형식, 질의에 없는 표면어, `[상위개념]` 표시)이 학습 때와 달라 점수가 크게 낮아졌습니다. 빈 결과와 나이 조건 문항은 반대로 점수를 부풀립니다.
- **모델 몫:** 개념이 여러 개인 긴 질의와 후보 고르기 형식을 학습 때 거의 보지 못해 생기는 실패입니다. 학습 데이터를 보강해야 할 부분입니다.
- **최종 점수로 쓰려면 먼저 기준을 정해야 합니다.** 앵커 원칙, 질의에 없는 개념의 처리, `[상위개념]` 표시, 출력 컬럼 규칙을 정하고 테스트셋을 맞춘 뒤 다시 채점해야 모델 실력을 공정하게 비교할 수 있습니다.

## 8. 주의 사항과 다음 단계

### 주의 사항

- **재채점 날짜:** `CURRENT_DATE` 정답 111건은 재료 기준일(2026-11-25)과 같은 날에만 맞게 채점됩니다. 이 보고서의 값은 2026-11-25에 채점한 것입니다. 다른 날 `score`를 다시 돌리면 스크립트가 날짜 불일치로 멈춥니다(`--allow-date-mismatch`로 무시 가능하지만 해당 문항 EX가 달라집니다).
- **모델 단독 점수:** 재료가 보정된 문항이 309건이라(후보 추가 249, 개념 추가 256, 컬럼 139, 조인 97, 테이블 43 — 한 문항에 여러 개), RAG 검색 성능은 빠진 점수입니다.
- **학습 데이터 중복:** 로컬 원본 학습 데이터(`nl_sql_train.jsonl`, 612건)와 비교하면 시나리오 0건, 질문 1건(id 431, 정답 SQL은 다름), 정답 SQL 7건(id 6·187·284·295·303·345·449 — 질문 문구는 다름)이 겹칩니다. v2 증강 학습 데이터는 로컬에 없어 비교하지 못했습니다.
- **반복 시 흔들림:** 이 서버는 batch-invariant 모드가 꺼져 있어, 같은 요청도 드물게 다른 답이 나옵니다(병합 모델 순차 반복 시 0.2%, `repeat_query_test/tts_val100_merge`).
- **시스템 프롬프트:** 기존 평가와 비교할 수 있도록 학습 때 문구를 썼습니다. 운영(TTS)은 후보 선택·자리표시자 규칙이 담긴 별도 시스템 프롬프트를 쓰므로, 운영 조건의 점수는 다를 수 있습니다.

### 다음 단계 (권장)

1. **관찰기간·결과 항목의 출력 컬럼 규칙을 정하고 다시 채점합니다.** 정답을 학습 규칙에 맞추거나, 채점을 환자 집합 기준으로 바꿉니다. 응답은 `responses.jsonl`에 있어 모델을 다시 부르지 않아도 됩니다.
2. **같은 552건을 예전 `개념 값 조건` 형식(정답 앵커만 주는 재료)으로도 돌립니다.** 재료 형식(후보 고르기) 때문에 떨어진 것과 새 시나리오 때문에 떨어진 것을 나눌 수 있습니다.
3. **운영 시스템 프롬프트로도 한 번 돌립니다.** 후보 선택 규칙을 시스템 프롬프트로 받을 때 "선택 안 함"(20.1%)과 "다른 후보 선택"(12.9%)이 줄어드는지 봅니다.
4. **재료 구성을 정답 기준에 맞춥니다(→ 7.3절).**
   - 질의에 없는 표면어로 추가한 개념(193개 표면어, 137문항)은 질의에 실제로 나온 표면어(예: "HCTZ")의 후보 목록 안으로 옮깁니다.
   - `[상위개념]` 표시와 지시문을 정답 앵커 기준에 맞춥니다.
5. **학습 데이터를 보강합니다.** 앵커 4개 이상인 복합 질의와 `개념 후보` 형식 예시를 추가합니다(→ 7.5절).
