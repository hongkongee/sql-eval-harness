# NL2SQL 어댑터 평가 — 변형 테스트셋

> 종합 보고서와 지표 설명: [00_overview.md](00_overview.md) · 학습셋 결과: [01_train.md](01_train.md) · validation 셋 결과: [02_val.md](02_val.md)

- **테스트셋:** 학습셋(`proposed_input_train`)과 validation 셋(`proposed_input_val`)의 시드를 네 가지 방식으로 변형한 파일 4개예요. 시드 1건당 방법별로 변형 1건을 만들었고, 시드 원본은 넣지 않았어요.
  - 원본 파일: `test_set/{paraphrase,restructure,slot,concept}.jsonl`
  - 평가용 사본: `test_set/eval_ready/` — 같은 id가 두 번 나오는 2건(`seed_528_test_restructure`, `seed_420_test_concept`)의 두 번째 행에 `_2`를 붙였어요. 그 밖의 내용은 원본과 같아요.
- **집계 대상:** base+시스템 프롬프트의 few-shot 시드(290·535·721·447·299)에서 나온 변형은 모든 모델에서 빼고 집계해요(val과 같은 기준).
- **원본과 짝지어 비교:** 모든 변형에는 원본 시드 id(`seed_id`)가 있어요. 그래서 같은 모델의 원본 문항 결과(학습셋·val)와 짝지어 "원본은 맞혔는데 변형하니 틀린 문항 수"를 셀 수 있어요.
- **실행 설정:** 다른 테스트와 같아요. temperature 0, max_tokens 512, 동시 요청 1이에요. 모든 모델이 같은 사용자 메시지(질의 + 재료)를 받고, 시스템 프롬프트만 달라요([요청 프롬프트 구성](00_overview.md#요청-프롬프트-구성)).
- **현재 상태:** FT0만 평가했어요. 다른 모델은 서버에 다시 올려서 같은 조건으로 돌린 뒤 이 문서에 열을 추가해요.

| 변형 | 바뀌는 것 | 집계 문항 (train 출처 / val 출처) |
|---|---|---:|
| 3.1 자연어 패러프레이즈 | 자연어만 (SQL은 원본 그대로, 재료는 바뀐 문장으로 다시 부착) | 568 (515 / 53) |
| 3.2 SQL 재구성 | 정답 SQL만 (자연어·재료는 원본 그대로) | 384 (337 / 47) |
| 3.3 슬롯 치환 | 날짜·나이·기간 같은 값 (자연어 + SQL) | 138 (127 / 11) |
| 3.4 concept_id 변형 | 앵커 개념 1개 (자연어 + SQL + 재료) | 451 (401 / 50) |

---

## 1. 핵심 요약 (FT0)

1. **FT0는 변형에 대체로 강해요.** 원본 대비 EX 변화는 패러프레이즈 −2.5%p, SQL 재구성 +0.8%p, 슬롯 치환 −1.4%p, concept_id 변형 −7.3%p예요. concept_id 변형을 빼면 원본과 거의 같아요.
2. **concept_id 변형에서도 외운 코드를 쓰지 않아요.** 바뀌기 전 코드를 SQL에 쓴 문항은 451건 중 0건이고, 모든 문항에서 재료의 새 코드를 썼어요. 새 코드가 학습 때 본 코드인지(236건) 처음 보는 코드인지(215건)에 따른 EX 차이도 없어요(44.1% vs 46.0%).
3. **다만 원본에서 보인 약점이 변형에서도 그대로예요.** 재료의 리터럴 형식(`IN (9202)`)을 베껴서 하위 전개를 절반 가까이 빠뜨리고, 올바른 반영률은 네 변형 모두 46~52%예요(원본 학습셋 51.2%, val 45.6%).
4. **SQL 재구성은 모델이 아니라 채점 방식을 시험해요.** 모델이 받는 입력이 원본과 같아서 EX는 원본과 거의 같고(맞힌 문항이 바뀐 건 5건), 정답 SQL의 작성 방식만 바뀌어 EM은 0%가 돼요.

- **필요한 코드 반영률이 원본(약 95%)보다 높게 나와요.** 변형 문항의 재료에는 불필요한 코드가 원본보다 적고(학습셋 원본 612건에 92개, 변형은 138~568건에 8~42개), 변형이 적용된 시드 구성도 원본과 달라요. 그래서 이 값은 원본과 직접 비교하지 않아요.
- **모델 SQL 타임아웃 4건**(패러프레이즈 657·531, SQL 재구성 688·531번 시드)은 원본에서도 같은 시드가 타임아웃이었어요. 다른 테스트와 같이 실패로 셌어요.
- **변형 전체(참고)**는 네 변형의 문항을 단순 합산한 값이에요. 변형마다 문항 수가 달라서(138~568건) 패러프레이즈와 concept_id 변형의 비중이 커요. 판단은 변형별 값으로 해요.

## 3. 변형별 분석

### 3.1 자연어 패러프레이즈

| | 원본 맞힘 | 원본 틀림 |
|---|---:|---:|
| **변형 맞힘** | 271 | 53 |
| **변형 틀림** | 67 | 177 |

- 원본은 맞혔는데 변형하니 틀린 문항이 67건, 반대로 원본은 틀렸는데 변형하니 맞힌 문항이 53건이에요. 순수하게 잃은 건 14건(−2.5%p)이에요.
- 출처별로는 train 출처 296/515건(원본 310건), val 출처 28/53건(원본 28건)이에요.
- 같은 뜻의 다른 표현에는 대체로 강하지만, 문항 단위로는 결과가 꽤 흔들려요(양방향 합계 120건, 21%).
- 일부 패러프레이즈는 원문에 없던 반환 형식 힌트(예: "환자별로 집계하여")를 붙여서, 원본보다 쉬워진 문항도 있어요. 맞히게 된 53건 중 일부는 이 영향일 수 있어요.

### 3.2 SQL 재구성

| | 원본 맞힘 | 원본 틀림 |
|---|---:|---:|
| **변형 맞힘** | 231 | 4 |
| **변형 틀림** | 1 | 148 |

- 자연어와 재료가 원본과 똑같아서 모델이 받는 입력도 같아요. 그래서 모델 답변도 원본과 거의 같고, 결과가 바뀐 문항은 5건뿐이에요(temperature 0이지만 서버 상태에 따라 생성이 조금 달라질 수 있어요).
- **EM은 0%예요.** 정답 SQL의 작성 방식이 바뀌어서, 원본 정답 스타일을 학습한 모델의 답과 글자가 일치할 수 없어요.
- **이 변형이 보여주는 것:** EX는 작성 방식이 달라도 결과가 같으면 정답으로 인정해서 그대로 유지돼요. 반면 EM은 정답 SQL의 작성 방식에 완전히 의존해요. EX가 EM보다 신뢰할 만한 지표라는 근거예요.

### 3.3 슬롯 치환

| | 원본 맞힘 | 원본 틀림 |
|---|---:|---:|
| **변형 맞힘** | 66 | 2 |
| **변형 틀림** | 4 | 66 |

- 날짜·나이·기간을 바꿔도 결과가 거의 같아요(순 −2건, −1.4%p). 질문의 값을 SQL에 정확히 옮겨 쓰고 있어요.
- 실행검증 통과율(76.8%)이 다른 변형보다 낮지만, 실패 32건 중 25건은 같은 시드의 원본에서도 실패하던 문항이에요. 슬롯 치환 문항의 65%(90/138건)가 기간 계산이 들어가는 5.기간설정이라 원래 어려운 문항이 많아요.
- 집계 문항이 138건으로 가장 적어서, 1건이 약 0.7%p예요.

### 3.4 concept_id 변형

| | 원본 맞힘 | 원본 틀림 |
|---|---:|---:|
| **변형 맞힘** | 168 | 35 |
| **변형 틀림** | 68 | 180 |

- **네 변형 중 가장 많이 떨어졌어요(−7.3%p, 순 −33건).** train 출처 183/401건(원본 215건), val 출처 20/50건(원본 21건)이에요. 하락은 대부분 train 출처, 즉 학습 때 본 문항에서 나와요.
- **외운 코드는 쓰지 않아요.**

  | 새 코드 | 문항 | 새 코드를 씀 | 바뀌기 전 코드를 씀 | EX |
  |---|---:|---:|---:|---:|
  | 학습셋 SQL에 나오는 코드 | 236 | 236 | 0 | 104 (44.1%) |
  | 처음 보는 코드 | 215 | 215 | 0 | 99 (46.0%) |

  FT0는 재료에 적힌 코드를 그대로 베끼는 경향이 강해서, 개념이 바뀌어도 재료의 새 코드를 따라가요. 새 코드를 본 적이 있는지와 상관없이 결과도 같아요.
- **그런데도 EX가 떨어진 이유(추정):** 코드를 바꾼 것 자체보다, 바뀐 개념에 맞춰 자연어가 다시 쓰이면서 원본과 문장이 달라진 영향으로 보여요. train 출처 문항에서만 떨어진 점을 보면, 원본에서는 학습한 문장 그대로라 맞혔던 문항이 문장이 바뀌면서 틀린 것으로 보여요. 정확한 원인은 다른 모델과 비교한 뒤 다시 확인할게요.
- **이 변형의 핵심 비교는 파인튜닝 모델 간 비교예요.** FT0는 재료를 베끼는 성향 때문에 외운 코드 문제가 드러나지 않았어요. 재료를 학습한 FT1·FT2가 바뀌기 전 코드를 쓰는지가 이 테스트의 핵심 확인 사항이에요.

## 4. 주의 사항

- **모델 간 비교는 아직 불가해요.** 지금은 FT0만 평가했어요. FT1·FT2·base·base+시스템 프롬프트를 같은 조건으로 돌린 뒤 각 절에 열을 추가해요.
- **변형별 문항 구성이 달라요.** 변형마다 적용 가능한 시드가 달라서(예: 슬롯 치환은 값이 있는 문항에만 적용) 변형끼리의 EX를 직접 비교하기보다, 같은 시드의 원본 EX와 비교한 변화량으로 판단해요.
- **concept_id 변형의 새 코드 중 52%는 학습셋에도 나오는 코드예요.** 외워서 쓰는지 볼 때는 위 표처럼 "학습 때 본 코드"와 "처음 보는 코드"를 나눠서 봐요.
