# P07. 연령대별 집계 질의가 환자 목록으로 반환됨

- **상태**: 미해결 (최종 평가에서는 현재 모델의 한계로 보고, 개선은 다음 버전 과제)
- **이슈번호**: P07
- **유형**: 연령대별 집계
- **발견일**: 2026-11-16
- **대상**: NL2SQL 서버 `POST http://10.1.1.106:8080/nl2sql` (파인튜닝 모델)

## 요약

**한 줄 결론**: 베이스 모델은 "SQL 짜는 법"(집계 형태, 나이 계산)은 지시를 잘 따르지만 "의료 개념 고르기"가 불안정하고,
파인튜닝 모델은 의료 개념은 정확하지만 학습에 없던 집계 형태와 나이 계산은 지시해도 잘 따르지 않는다.
**파인튜닝 모델은 문장 지시보다 예시 SQL에 반응한다.** 시스템 프롬프트에 집계 규칙과 연령대 집계 예시 SQL 1개를 넣자
P07 질의가 맞게 생성됐다. 다만 "80세 초과" 같은 나이 조건 질의는 여전히 나이를 틀리게 계산한다
(SQL을 읽고 판단한 것이며 실행 확인은 하지 않음).

- **증상**: "고혈압 환자의 연령대별 환자 수"에 파인튜닝 모델이 연령대별 몇 줄 대신 환자 목록(55,435행)을 돌려준다.
  SQL이 환자 ID로 묶여(`GROUP BY person_id`) 연령대별로 합쳐지지 않기 때문이다.
- **원인**: 시드·학습 데이터에 "범주별로 묶어서 세는" SQL이 한 건도 없다(4장). 운영 시스템 프롬프트에도 범주별 집계 안내가 없다.
- **처리**: 최종 평가에서는 현재 모델의 한계로 보고하고, 개선은 다음 버전 과제로 분리한다(5장).

### P07 질의 진단 결과

`고혈압 환자의 연령대별 환자 수`를 운영 API 프롬프트로 다섯 조건에서 생성해 비교했다. 모두 시스템 프롬프트만 바꿨다.
- "+ 규칙": 운영 시스템 프롬프트 끝에 범주별 집계 규칙만 덧붙인 것(5.3)
- "+ 규칙 + 예시": 위에 더해 나이 계산 규칙(써야 할 식·금지할 식)과 연령대 집계 예시 SQL 1개를 덧붙인 것(5.3, 변형 2)

| 기준 | 베이스 | 베이스 + 규칙 | 파인튜닝 (운영과 동일) | 파인튜닝 + 규칙 | 파인튜닝 + 규칙 + 예시 |
|---|:---:|:---:|:---:|:---:|:---:|
| ① 연령대로 묶었나 | △¹ | ✓ | ✗² | ✓ | ✓ |
| ② 나이를 맞게 계산했나 | ✓ | ✓ | △³ | ✗⁴ | ✓ |
| ③ 환자 수를 셌나 (진단 기록 수가 아니라) | ✗⁵ | ✓ | ✗⁶ | ✓ | ✓ |
| ④ 고혈압 환자를 맞게 골랐나 | ✓ | △⁷ | ✓ | ✓ | ✓ |
| **결과를 그대로 쓸 수 있나** | ✗ | △ | ✗ | ✗ | **✓** |

1. 연령대가 아니라 나이 1세 단위로 묶음 (약 100행)
2. 환자 ID로 묶어 환자 목록이 나옴 (P07 증상 그대로)
3. 나이 대신 출생연도 20년 구간(`1941-1960` 등)으로 나눔. 계산 오류는 아니지만 나이 구간과 경계가 맞지 않아(1941~1960년생은 66~85세) "60대 몇 명"으로 바꿀 수 없음
4. 나이를 `기준일 - 생년월일`로 구한 뒤 거기서 "연도"를 꺼냄. PostgreSQL에서 날짜끼리 빼면 `29950 days`처럼 **일수**만 나오고 연도 칸은 비어 있어(0) 모든 환자가 0세 → 연령대 `0` 한 줄로 몰림. 운영 프롬프트가 이미 금지한 방식이며, 맞는 방법은 연·월·일로 나눠 주는 `AGE(기준일, 생년월일)`
5. 한 환자의 진단 기록이 여러 건이면 여러 번 셈
6. 환자별로 묶여 있어 모든 행의 값이 1
7. 원발성·이차 고혈압만 걸고 그 하위 개념은 빠뜨려 대상 환자가 줄어듦

### 다른 질의 한 줄 요약

| 질의 | 네 조건 결과 | 파인튜닝 + 규칙 + 예시 |
|---|---|:---:|
| 연령대 별 고혈압 환자 | 규칙이 없으면 두 모델 모두 환자 목록. 규칙을 넣으면 베이스는 연령대로 집계하지만 문맥고혈압 등 엉뚱한 개념을 포함하고, 파인튜닝은 연령대로 집계하지만 모두 0세로 계산 | ✓ |
| 성별 고혈압 환자 수 | **파인튜닝 + 규칙만 정답.** 나머지는 성별로 나누지 않고 숫자 하나만 냄 | ✓ |
| 진단 연도별 제2형 당뇨병 환자 수 (신규) | 네 조건 모두 정답 | ✓ |
| 성별·연령대별 심근경색 환자 수 (신규) | 베이스 + 규칙은 묶기·나이 계산은 맞지만 심근질환 등 엉뚱한 개념 포함. 파인튜닝 + 규칙은 모두 0세로 계산 | ✓ |
| 80세 초과 고혈압 환자 목록 (회귀 확인) | 규칙을 넣어도 목록 질의는 그대로 (부작용 없음). 베이스는 `[재료]`의 나이 조건을 그대로 쓰고, 파인튜닝은 무시하고 출생연도 차이로 계산(생일 전이면 1살 많게 계산됨) | ✗ 여전히 출생연도 차이 (예시가 연령대 집계만 보여주고 나이 조건은 보여주지 않음) |

- 신규 질의 2개는 규칙이 처음 보는 질의에도 통하는지, 회귀 확인 질의는 규칙 때문에 기존 환자 목록 추출이 망가지지 않는지 보려고 넣었다.
- 생성된 SQL만 읽고 판단했고 실행은 하지 않았다. 질의당 1회 실행한 결과라 경향 확인 수준이다.
  (파인튜닝 + 규칙은 한 번 더 생성해 6개 모두 글자까지 같은 SQL이 나오는 것을 확인했다.)
- 예시 SQL은 테스트 질의와 겹치지 않도록 가상의 "천식 환자의 연령대별 환자 수"로 작성했다. 예시 때문에 목록 질의가 집계로 바뀌는 부작용은 이번 6개에서는 없었다.
- 진단용 테스트이므로 최종 평가 결과에는 반영하지 않는다.
- 자세한 비교표는 4장 "종합 비교", SQL 전문은 [P07_베이스_vs_파인튜닝_SQL.md](P07_베이스_vs_파인튜닝_SQL.md)에 있다.

### 다음 버전 방향

파인튜닝 모델을 유지한다. 베이스의 개념 선택 오류는 대상 환자 집단을 조용히 바꿔 더 위험하기 때문이다.
대신 시드에 범주별 집계 예시와 `AGE()` 기반 나이 계산을 넣어 재학습한다(5.2). 학습 데이터는 나이를 `현재연도 - year_of_birth`로만
계산하고(37건) `AGE()`는 0건이라, 운영 스키마(`birth_datetime`만 있음)에서 나이 계산이 흔들린다.
시스템 프롬프트의 규칙 + 예시 SQL은 재학습 없이 바로 적용할 수 있는 보조 장치다(5.3). 다만 테스트한 질의가 6개뿐이고
나이 조건 질의는 고쳐지지 않았으므로, 나이 조건 예시 추가 등을 더 많은 질의로 검증한 뒤 적용한다.

## 1. 증상

| 질의 | 기대 결과 | 실제 결과 |
|---|---|---|
| `고혈압 환자의 연령대별 환자 수` | 연령대별 집계 행 (20행 이하) | 집계 없이 person_id·출생연도 1,000행(첫 페이지), `success` |

연령대 몇 줄로 끝나야 하는 집계 질문인데, 환자 한 명당 한 줄인 목록이 나온다.
SQL이 실행은 되기 때문에 응답은 `status: success`로 나가고, 실패로 잡히지 않는다.

## 2. 재현 (2026-11-16, 2회 호출)

### 요청 1: `고혈압 환자의 연령대별 환자 수`

```sql
SELECT p.person_id, EXTRACT(YEAR FROM p.birth_datetime) AS birth_year,
       CASE WHEN EXTRACT(YEAR FROM p.birth_datetime) BETWEEN 1900 AND 1920 THEN '1900-1920'
            ... ELSE 'Other' END AS age_group,
       COUNT(DISTINCT c.person_id) AS high_blood_pressure_person_count
FROM person p
LEFT JOIN condition_occurrence c
  ON c.person_id = p.person_id
 AND c.condition_concept_id IN (SELECT descendant_concept_id FROM concept_ancestor
                                WHERE ancestor_concept_id IN (320128, 319826))
GROUP BY p.person_id, birth_year, age_group          -- ← 원인
HAVING COUNT(DISTINCT c.person_id) > 0;
```

- 결과: 총 55,435행 (pagination total), 모든 행의 count 값이 1

### 요청 2: `연령대 별 고혈압 환자`

```sql
SELECT p.person_id, p.birth_datetime,
       CASE WHEN (EXTRACT(YEAR FROM DATE '2026-11-16') - EXTRACT(YEAR FROM p.birth_datetime)) BETWEEN 18 AND 24 THEN '18-24'
            ... >= 65 THEN '65+' ELSE 'under 18' END AS age_group
FROM person p
WHERE EXISTS (SELECT 1 FROM condition_occurrence co
              WHERE co.person_id = p.person_id
                AND co.condition_concept_id IN (SELECT descendant_concept_id FROM concept_ancestor
                                                WHERE ancestor_concept_id IN (320128, 319826)))
GROUP BY p.person_id, p.birth_datetime;               -- ← 같은 원인, COUNT 자체가 없음
```

- 결과: 역시 55,435행

## 3. 문제 분석

1. **`GROUP BY`에 `person_id`가 들어감.**
   환자 단위로 묶으면 그룹 하나에 환자가 한 명뿐이라 `COUNT(DISTINCT person_id)`는 항상 1이다.
   연령대별로 묶이지 않고 환자 수만큼 행이 나온다.
2. **문법상으로 맞는 SQL이라 실패로 잡히지 않음.**
   실행 성공 여부만 보는 검증으로는 이 오류를 걸러낼 수 없다.
3. **연령대 기준이 그때그때 다름.**
   요청 1은 출생연도 20년 단위(`1941-1960`), 요청 2는 현재 나이 구간(`18-24 … 65+`)으로 나눴다.
   질문 문구만 조금 바꿨는데 기준이 달라졌다.

고혈압 개념 매핑(320128 원발성 고혈압, 319826 이차 고혈압과 그 하위 개념)과 대상 환자 추출은 정상이다.
**마지막 집계 단계만 틀린다.**

## 4. 원인: 시드부터 집계 예시가 없음

| 데이터 | 건수 | `COUNT(` 사용 | person_id가 아닌 기준의 `GROUP BY` | `SELECT person_id`로 시작 |
|---|---|---|---|---|
| 시드: `allRe3.0_시드데이터셋_v4.50.xlsx` / `StudyBrief_v1.1_기준` 시트 (`query_토큰형`) | 769 | **0** | **0** | 585 (76%) |
| 학습: `test_set/proposed_input_train.jsonl` | 612 | **0** | **0** | 441 (72%) |
| 검증: `data/260914/auto_confirmed_val_260914.jsonl` | 1012 | 14 | 1 | 725 (72%) |

- **시드 단계부터 "범주별로 묶어서 세는" SQL이 한 건도 없다.**
  시드를 증강해 만든 학습셋·검증셋에도 자연히 없다(검증셋의 `COUNT` 14건은 증강 과정에서 우연히 생긴 것으로 보인다).
- 시드의 `GROUP BY` 368건은 전부 person_id 기준이다. 그 외 집계 함수도 `MIN(` 368, `AVG(` 2, `MAX(` 2건뿐이고
  모두 환자 단위 안에서 계산한다.
- **`STATISTICAL_AGGREGATION` 라벨과 실제 내용이 다르다.**
  '쿼리유형 기준' 시트에는 이 유형이 "group by/having·count, … 집계형 결과"로 정의돼 있다.
  그런데 시드의 이 유형 193건은 모두 마지막 결과에 `person_id`가 들어가는 환자 단위 출력이다.
  실제 내용은 환자별 최초 발생일(`MIN(event_date) … GROUP BY person_id`), 추적기간, 측정값 변화량 등이다.
  검증셋의 같은 유형 234건도 `COUNT`가 0건이다.
- 결과적으로 모델은 범주별 집계 SQL을 학습에서 본 적이 없다. 그래서 익숙한 코호트 추출 형태
  (`SELECT person_id … GROUP BY person_id`) 안에 CASE와 COUNT만 끼워 넣는다.

### 베이스 모델과 비교 (2026-11-16, 원인 진단용)

베이스 모델이 NL2SQL 특화인데도 파인튜닝 후 못 하는 것인지 확인하려고, 같은 입력을 베이스와 파인튜닝 체크포인트에 넣어 비교했다.
재학습이 아닌 진단이므로 최종 평가 결과에는 영향이 없다.

- **user 메시지**: 운영 서버 `POST /rag`(`{"query": …, "top_k": 5}`)가 돌려준 `prompt`(`[질의]` + `[재료]`) 그대로
- **system 메시지**: 두 가지로 각각 실행
  - (A) 학습용 시스템 프롬프트 (`results/adapter_eval/prompts/adapter_eval_train_system_prompt.txt`)
  - (B) 운영 API가 실제로 쓰는 시스템 프롬프트 (`system_prompt.txt`의 `{dialect}`=PostgreSQL + `placeholder_protocol.txt`)
- temperature 0, 질의당 1회
- **모델** (vLLM `10.1.1.69:8007`)
  - 베이스: `XiYanSQL-QwenCoder-14B-2504` (등록명 `xiyansql-qwencoder-14b-proposed-random-augment-v2`)
  - 파인튜닝: `by-loss` 체크포인트

생성된 SQL 12개 전문(질의 3개 × 프롬프트 2종 × 모델 2개)은 [P07_베이스_vs_파인튜닝_SQL.md](P07_베이스_vs_파인튜닝_SQL.md)에 정리했다.

#### (A) 학습용 시스템 프롬프트

| 질의 | 베이스 | 파인튜닝 (`by-loss`) |
|---|---|---|
| 고혈압 환자의 연령대별 환자 수 | △ `GROUP BY age_group` + `COUNT`로 **집계 형태는 맞음**. 단, 나이 대신 출생연도로 구간을 나눠 전부 `80+`로 몰리고, `COUNT(*)`라 환자가 아닌 진단 건수를 셈 | ✗ `GROUP BY p.person_id, age_decade` |
| 연령대 별 고혈압 환자 | ✗ 환자 목록 (연령대 구분 없음) | ✗ 전체 환자 목록 + 고혈압 여부 플래그, 없는 컬럼 `p.birth_date` 사용 |
| 성별 고혈압 환자 수 | ✗ 남성만 셈 (`gender_concept_id = 8507`), 성별로 묶지 않음 | ✓ `GROUP BY p.gender_concept_id` + `COUNT(DISTINCT p.person_id)` **정답** |

#### (B) 운영 API 시스템 프롬프트

| 질의 | 베이스 | 파인튜닝 (`by-loss`) |
|---|---|---|
| 고혈압 환자의 연령대별 환자 수 | △ `GROUP BY age` + `COUNT`로 **집계 형태는 맞음**. 나이는 지시대로 `AGE(DATE '2026-11-16', birth_datetime)`로 계산. 단, 연령대가 아닌 1세 단위로 묶었고 `COUNT(person_id)`에 DISTINCT가 없어 진단 건수를 셈 | ✗ `GROUP BY p.person_id, birth_year, age_group` + `HAVING`. **운영 서버 `/nl2sql` 결과와 거의 동일**(별칭 이름, `LEFT JOIN` 대신 `WHERE`만 다름) |
| 연령대 별 고혈압 환자 | ✗ 환자 목록 + 나이 | ✗ 환자 목록, `GROUP BY p.person_id, p.birth_date`, 없는 컬럼 `p.birth_date` 사용 |
| 성별 고혈압 환자 수 | ✗ 남성만 셈 | ✗ 성별로 묶지 않고 전체를 셈. `gender_concept_id`에 `concept_ancestor` 전개를 잘못 적용. **(A)에서는 정답이었음** |

**해석**

- **운영 서버 결과가 재현된다.** (B)에서 `by-loss`의 연령대 질의 출력이 운영 서버 결과와 거의 같다.
  운영 서버도 이 체크포인트(또는 거의 같은 모델)를 쓰는 것으로 보인다.
- **연령대 집계 실패는 파인튜닝 쪽 문제라는 근거가 강하다.**
  - 베이스는 두 프롬프트 모두에서 연령대 질의를 범주로 묶어 셌다(세부 계산은 틀림).
  - 파인튜닝 모델은 두 프롬프트 모두에서 `person_id`로 묶었다.
  - 파인튜닝 모델은 (B)의 나이 계산 지시(`AGE(…)`)도 무시하고 학습 때 익힌 방식(`EXTRACT(YEAR FROM birth_datetime)`)을 썼다. 베이스는 지시를 따랐다.
- **실패는 "계산해서 만든 범주"(연령대)에서 두드러진다.** 학습 데이터에서 나이 계산은 항상 환자 단위 필터
  (`... - p.year_of_birth >= 55`)로만 쓰였다. 그래서 나이 계산이 들어가면 환자 단위 형태
  (`SELECT person_id … GROUP BY person_id`)로 끌려가는 것으로 보인다.
  성별처럼 컬럼 값 그대로가 범주인 경우는 (A)에서 정확히 만들었다.
  다만 5.3의 사전 확인에서, 규칙 없이도 "성별·연령대별 심근경색 환자 수"는 `person_id` 없이 범주로 묶었다.
  따라서 "계산된 범주면 항상 환자 단위로 쏠린다"가 아니라, **문구에 따라 쏠리기도 한다**고 보는 것이 맞다.
- **운영 시스템 프롬프트에도 문제가 있다.** `[범주값 조건]`이 범주 컬럼을 "코드를 골라 `컬럼 = 코드`를 WHERE에 쓴다"는
  필터 용도로만 설명하고, "성별", "연령대별"처럼 범주로 묶어 세라는 질의를 `GROUP BY`로 처리하라는 안내가 없다.
  그 결과 성별 질의에서 베이스는 남성만 걸렀고, 파인튜닝 모델은 (A)에서 맞히던 것을 (B)에서 틀렸다.
- **베이스 모델이 전반적으로 낫지는 않다.** 집계 형태는 맞혀도 세부 계산이 틀리고, 성별 질의는 두 프롬프트 모두 틀렸다.
  파인튜닝은 도메인 형식(concept 하위전개, 기준일, `DISTINCT person_id`)을 크게 개선했고,
  **계산된 범주로 묶는 집계**만 학습 데이터 공백 때문에 환자 단위로 쏠린다고 보는 것이 맞다.
- (B)의 `[재료]`에는 `person.year_of_birth`가 없고 `birth_datetime`만 있다. 학습 데이터는 나이를 `p.year_of_birth`로 계산하므로,
  학습 때와 다른 컬럼이 주어지는 것도 연령대 질의가 흔들리는 데 영향을 줬을 수 있다.
- "연령대 별 고혈압 환자"는 "수"가 없어 목록 요청으로도 읽힐 수 있는 모호한 문구라, 두 모델 모두 목록을 낸 것은 판단 근거로 약하다.
- **스키마 적합성**: 레포의 OMOP CDM v5.3 스키마 검사(`scripts/eval_api_model.py`의 `check_schema`, `data/fixtures/omop_cdm_v53_ddl.sql` 기준)로 12개를 모두 검사했다.
  베이스 6개는 전부 통과했다. 파인튜닝은 "연령대 별 고혈압 환자" 2건이 v5.3에 없는 `person.birth_date`를 써서 실패했다.
  즉 베이스의 문제는 스키마가 아니라 집계 로직(구간 기준, `COUNT`의 DISTINCT 누락)과 개념 선택이다.
- 생성된 SQL만 비교했고 실행 결과(행)는 보지 않았다. 질의 3개 × 1회 표본이라 경향 확인 수준이다.

**다음 버전에 주는 시사점**

- 범주별 집계 예시를 넣을 때 성별·기관처럼 컬럼 그대로인 범주보다
  **연령대, 진단연도 구간, 추적기간 구간처럼 CASE·계산식으로 만든 범주**를 중심으로 넣는다.
- 학습 데이터의 나이 계산 방식(`year_of_birth`)과 운영 스키마·프롬프트의 방식(`birth_datetime`, `AGE(…)`)을 맞춘다.
- 운영 시스템 프롬프트에 범주별 집계 규칙을 추가한다(5.3 참고).

### 종합 비교: 운영 API 프롬프트 ± 집계 규칙, 베이스 vs 파인튜닝 (원인 진단용)

- 입력: 운영 서버 `POST /rag`의 프롬프트 + 운영 API 시스템 프롬프트. vLLM `10.1.1.69:8007`, temperature 0, 질의당 1회
- "+ 집계 규칙"은 운영 시스템 프롬프트 끝에 `[범주별 집계]` 규칙만 덧붙인 것이다 (규칙 원문은 5.3).
- 신규 질의 2개는 규칙이 처음 보는 질의에도 통하는지, 회귀 확인 질의는 기존 코호트 추출(환자 목록)이 망가지지 않는지 보려고 넣었다.
- 생성된 SQL만 비교했고 실행은 하지 않았다. 표의 결과는 SQL을 읽고 판단한 것이다.

#### 결론

- **베이스 + 집계 규칙**이 연령대 질의의 SQL 형태와 나이 계산은 가장 정확하다. 하지만 **개념 선택이 일관되게 틀린다**
  (문맥고혈압·심근질환 같은 엉뚱한 후보 포함, 하위 개념 전개 누락). 개념 오류는 대상 환자 집단 자체를 조용히 바꾸므로,
  의료 데이터에서는 집계 형태 오류보다 더 위험하다. 성별 질의도 여전히 틀린다.
- **파인튜닝 + 집계 규칙**은 묶는 형태와 개념 선택은 맞지만, 나이 계산 지시를 따르지 않아 연령대 결과가 깨진다.
- 즉 두 모델의 약점이 정반대다. 베이스는 도메인 지식(개념 선택)이 약하고, 파인튜닝은 학습에 없던 패턴(범주 집계, `AGE()`)을 프롬프트로 지시해도 잘 따르지 않는다.
  → 다음 버전: 파인튜닝 모델을 유지하고, 시드에 범주별 집계 예시와 `AGE()` 기반 나이 계산을 넣어 재학습한다(5.2).
  프롬프트 규칙과 나이 계산 검사는 보조 장치로 함께 적용한다(5.3).
- 질의당 1회 실행한 결과라 경향 확인 수준이다.

## 5. 처리 방침

### 5.1 이번 최종 평가: 현재 모델 그대로 실패로 보고

지금은 최종 평가 단계다. 여기서 발견한 실패를 보고 재학습한 다음 같은 평가로 다시 재면,
테스트셋 정보가 학습에 새어 들어가 점수를 신뢰할 수 없게 된다. 따라서 이번 평가에서는 다음과 같이 처리한다.

- **현재 모델로 최종 평가를 끝내고, P07은 실패로 기록한다.**
- **실패 원인을 함께 보고한다.** 시드·학습 데이터에 범주별 집계가 0건이라 생긴 데이터 범위 문제이고,
  원인이 밝혀진 한계로 남긴다.
- **평가 범위 근거:** '쿼리유형 기준' 시트가 `STATISTICAL_AGGREGATION`을 "group by/having·count, 집계형 결과"로
  정의하므로 이 질의는 평가 범위 안이고, 실패는 정당한 실패다.
  다만 실제 데이터는 이 정의와 달리 환자 단위 출력뿐이었다는 점도 함께 적는다.

### 5.2 다음 버전 과제: 시드에 집계 예시 추가 후 재학습

재학습은 이번 평가 결과를 덮어쓰지 않는 **새 모델 버전 작업**으로 진행한다. 지켜야 할 조건:

- **P07 질의나 그 변형을 학습에 넣지 않는다.** 집계 예시는 시드 단계에서 별도로 작성한다.
- **새 held-out 집계 평가셋으로 잰다.** 이번 테스트셋은 이미 "본" 데이터가 됐다.
  가능하면 학습 데이터를 만들지 않은 사람이 평가셋을 작성한다.

작업 내용:

- 시드에 연령대, 성별, 진단연도, 기관 등 범주별 환자 수·건수 질의를 추가하고 증강을 다시 돌린다
  (학습셋만 고치면 이후 증강에서 다시 빠진다). 기존 코호트 정의에 집계 단계만 씌우면 되므로 쉽게 늘릴 수 있다.
- 범용 NL2SQL 데이터(Spider, BIRD 등)의 집계 질의를 소량 섞어(replay / mix-in) 베이스 능력이 덜 지워지게 하는 것도 검토한다.
- 정답 SQL의 형태를 하나로 통일한다.

  ```sql
  SELECT (FLOOR((EXTRACT(YEAR FROM CURRENT_DATE) - p.year_of_birth) / 10) * 10) AS age_group,
         COUNT(DISTINCT p.person_id) AS patient_count
  FROM person p
  WHERE EXISTS (SELECT 1 FROM condition_occurrence co
                WHERE co.person_id = p.person_id
                  AND co.condition_concept_id IN ({{고혈압}}))
  GROUP BY 1
  ORDER BY 1;
  ```

- 연령대 기준도 하나로 정해 둔다(예: 현재 나이 기준 10세 단위). 그래야 3번의 흔들림이 사라진다.
- `STATISTICAL_AGGREGATION` 라벨을 바로잡는다. "환자 필터"와 "집계"를 서로 다른 유형으로 나누면
  이후 평가에서도 집계 문항을 따로 집계할 수 있다.

### 5.3 (다음 버전) 서버 쪽 안전장치

이 장치들도 이번 테스트 결과를 보고 만든 것이므로, 적용한다면 시스템 변경으로 명시하고 새 데이터로 평가한다.
이번 최종 평가 결과에는 반영하지 않는다.

- **검사 후 재시도**: 질문에 "~별", "분포", "몇 명", "환자 수"가 있는데 SQL의 `GROUP BY`에
  `person_id`가 들어 있으면 실패로 판정한다. "person_id로 묶지 말고 범주로 묶어 COUNT 하라"는
  피드백을 붙여 다시 생성한다. 기존 `retry_count` 재시도 경로를 그대로 쓰면 된다.
- **결과 모양 검사**: 집계 의도인 질문의 결과가 수백 행 이상이면 `success`로 내보내지 않는다.
- **RAG 프롬프트에 예시 1~2개 넣기**: 위와 같은 범주별 집계 SQL을 예시로 넣는다.
  당장 적용할 수 있지만, 파인튜닝된 모델은 프롬프트 예시를 잘 따르지 않을 수 있으니 효과는 직접 확인해야 한다.
- **시스템 프롬프트에 범주별 집계 규칙 추가**: 현재 `[범주값 조건]`은 범주 컬럼을 WHERE 필터로만 설명한다.
  "~별", "분포", "성별/연령대별 환자 수" 같은 질의는 범주를 `GROUP BY` 기준으로 쓰고
  `COUNT(DISTINCT person_id)`로 세며, `person_id`는 `GROUP BY`에 넣지 않는다는 규칙을 추가한다.
  연령대는 `AGE(…)`로 계산한 나이를 10세 단위 등 정해진 구간으로 나눈다는 기준도 함께 적는다.

  **사전 확인 결과 (2026-11-16, 진단용 — 최종 평가에는 반영하지 않음)**

  운영 시스템 프롬프트 끝에 아래 규칙만 덧붙여 `by-loss`로 테스트했다(temperature 0, 질의당 1회).
  P07 질의에만 맞추지 않도록 규칙 문구에 고혈압 예시를 넣지 않았고, 처음 보는 질의 2개와 코호트 추출 회귀 확인 질의 1개를 함께 넣었다.

  ```text
  [범주별 집계]
  - 질의가 "~별", "분포", "구성"처럼 범주로 나눠 세라는 경우(예: 성별 환자 수, 연령대별 환자 수), 범주는 WHERE 필터가 아니라 GROUP BY 기준이다. 특정 범주값(예: "남성")이 질의에 있을 때만 WHERE 로 거른다.
  - 결과는 범주당 1행이다: SELECT 범주식, COUNT(DISTINCT person.person_id) … GROUP BY 범주식. person_id 는 SELECT·GROUP BY 에 넣지 않는다.
  - 연령대는 나이를 EXTRACT(YEAR FROM AGE(DATE '기준일', person.birth_datetime)) 로 구한 뒤 10세 단위로 나눈다: FLOOR(나이 / 10) * 10 AS age_group.
  - 진단·처방·검사 등 이벤트 테이블과 조인하면 한 환자가 여러 번 나오므로, 대상 환자는 EXISTS 로 거르거나 반드시 COUNT(DISTINCT person_id) 로 센다.
  ```

  | 질의 | 구분 | 규칙 없음 (운영 프롬프트) | 규칙 추가 |
  |---|---|---|---|
  | 고혈압 환자의 연령대별 환자 수 | P07 | ✗ `GROUP BY person_id …` | △ `GROUP BY age_group` + `COUNT(DISTINCT)`. 형태는 맞지만 나이 계산 오류 |
  | 연령대 별 고혈압 환자 | P07 | ✗ 환자 목록 | △ 위와 같음 |
  | 성별 고혈압 환자 수 | P07 | ✗ 성별로 묶지 않고 전체를 셈 | ✓ `GROUP BY gender_concept_id` + `COUNT(DISTINCT)` |
  | 진단 연도별 제2형 당뇨병 환자 수 | 신규 | ✓ | ✓ (같은 SQL) |
  | 성별·연령대별 심근경색 환자 수 | 신규 | △ 범주로 묶었지만 구간이 출생연도 30년 단위 | △ 10세 단위로 묶었지만 나이 계산 오류 |
  | 80세 초과 고혈압 환자 목록 | 회귀(코호트) | 환자 목록 | 환자 목록 (같은 SQL) |

  - **집계 형태는 규칙으로 바로잡힌다.** P07 질의 3개 모두 범주당 1행으로 바뀌었고, 성별 질의는 정답이 됐다.
  - **나이 계산은 고쳐지지 않는다.** 규칙에 적힌 `AGE(…)` 대신 `EXTRACT(YEAR FROM (DATE '2026-11-16' - birth_datetime))`를 썼다.
    날짜끼리 뺀 값은 일수 간격이라 YEAR가 항상 0이므로, 실행하면 모든 환자가 `age_group = 0` 한 행으로 몰릴 것으로 보인다
    (DB 접속이 안 돼 실행으로 확인하지는 않음). 운영 프롬프트에 이미 같은 금지 문구가 있는데도 따르지 않았다.
    → 학습 데이터의 나이 계산을 `AGE()`로 통일하거나, 서버에서 이 패턴을 검사해 재시도시키는 장치가 함께 필요하다.
  - **코호트 추출은 규칙 때문에 바뀌지 않았다.** 다만 규칙 유무와 관계없이 `[재료]`의 `[나이]` 조건
    (`birth_datetime <= DATE '1945-11-16'`)을 무시하고 출생연도 차이로 계산한다. 이는 별도의 기존 문제다.

  **나이 계산 치환 추가 결과 (2026-11-16, 진단용 — 최종 평가에는 반영하지 않음)**

  파인튜닝 모델이 나이 계산 지시를 따르지 않으므로, 생성된 SQL에서 틀린 나이 계산식을 서버가 찾아 바꾸는 후처리를 시험했다.
  "파인튜닝 + 규칙"으로 질의 6개를 다시 생성(temperature 0, 6개 모두 이전과 같은 SQL)한 뒤 아래 두 패턴을 치환했다.

  | 패턴 | 문제 | 치환 결과 |
  |---|---|---|
  | `EXTRACT(YEAR FROM (DATE 'X' - col))` | 날짜끼리 빼면 일수 간격이라 연도가 항상 0 → 모든 환자가 0세 | `EXTRACT(YEAR FROM AGE(DATE 'X', col))` |
  | `EXTRACT(YEAR FROM DATE 'X') - EXTRACT(YEAR FROM col)` | 출생연도 차이라 생일 전이면 1살 많게 계산 | `EXTRACT(YEAR FROM AGE(DATE 'X', col))` |

  | 질의 | 치환한 곳 | 치환 후 |
  |---|---|---|
  | 고혈압 환자의 연령대별 환자 수 (P07) | 날짜 뺄셈 1곳 | ✓ 10세 연령대 + `AGE()` + `COUNT(DISTINCT)` + 고혈압 하위 개념 전개 |
  | 연령대 별 고혈압 환자 (P07) | 날짜 뺄셈 1곳 | ✓ 위와 같은 SQL |
  | 성별 고혈압 환자 수 (P07) | 없음 | ✓ |
  | 진단 연도별 제2형 당뇨병 환자 수 (신규) | 없음 | ✓ |
  | 성별·연령대별 심근경색 환자 수 (신규) | 날짜 뺄셈 2곳 (SELECT, GROUP BY) | ✓ |
  | 80세 초과 고혈압 환자 목록 (회귀 확인) | 출생연도 차이 1곳 | ✓ `AGE(…) > 80` — `[재료]`의 `birth_datetime <= DATE '1945-11-16'`과 같은 환자를 고름 |

  - 치환 후 6개 모두 문법 검사와 OMOP CDM v5.3 스키마 검사를 통과했다.
  - **한계**
    - 실제 DB에서 실행해 결과 행을 확인하지 않았다.
    - 질의 6개 × 1회 결과다. 다른 문구에서는 집계 형태가 다시 흔들릴 수 있다.
    - 치환은 위 두 형태만 잡는다. `CURRENT_DATE`, `::date` 형변환 등 다른 형태의 나이 계산은 놓친다.
      적용 전에 더 많은 질의로 놓치는 패턴을 확인해야 한다.
    - `AGE(…) > 80`처럼 컬럼에 함수를 씌우면 `birth_datetime <= DATE '…'`와 달리 인덱스를 쓰지 못해 큰 테이블에서 느릴 수 있다.

  **시스템 프롬프트만으로 나이 계산 고치기 (2026-11-16, 진단용 — 최종 평가에는 반영하지 않음)**

  후처리 없이 시스템 프롬프트만으로 파인튜닝 모델이 `AGE()`를 쓰게 할 수 있는지, 위 "규칙" 프롬프트에 아래를 더 붙여 `by-loss`로 시험했다(질의 6개 × 1회).

  - **변형 1 (강조 + 정확한 식)**: 프롬프트 맨 끝에 별도 블록으로 추가
    ```text
    [나이 계산 — 반드시 지킬 것]
    - 나이는 오직 아래 식으로만 계산한다. '기준일'에는 [재료]의 기준일 DATE 리터럴을 넣는다.
        EXTRACT(YEAR FROM AGE(DATE '기준일', person.birth_datetime))
    - 연령대(10세 단위)는 아래 식을 쓴다.
        FLOOR(EXTRACT(YEAR FROM AGE(DATE '기준일', person.birth_datetime)) / 10) * 10
    - 아래 두 식은 틀린 결과를 내므로 절대 쓰지 않는다.
        EXTRACT(YEAR FROM (DATE '기준일' - person.birth_datetime))                    -- 날짜 뺄셈은 일수 간격이라 항상 0
        EXTRACT(YEAR FROM DATE '기준일') - EXTRACT(YEAR FROM person.birth_datetime)  -- 생일 전이면 1살 틀림
    ```
  - **변형 2 (변형 1 + 예시 SQL 1개)**: 테스트 질의와 겹치지 않는 가상의 예시를 추가
    ```text
    [예시] (형식 참고용 — 개념 id 는 반드시 [재료]의 후보에서 고른다)
    질의: 천식 환자의 연령대별 환자 수 / 기준일: DATE '2025-01-12' / 앵커: 317009
    SELECT FLOOR(EXTRACT(YEAR FROM AGE(DATE '2025-01-12', p.birth_datetime)) / 10) * 10 AS age_group,
           COUNT(DISTINCT p.person_id) AS patient_count
    FROM person p
    WHERE EXISTS (SELECT 1 FROM condition_occurrence co
                  WHERE co.person_id = p.person_id
                    AND co.condition_concept_id IN (SELECT descendant_concept_id FROM concept_ancestor WHERE ancestor_concept_id = 317009))
    GROUP BY age_group
    ORDER BY age_group;
    ```

  | 질의 | 변형 1 | 변형 2 |
  |---|---|---|
  | 고혈압 환자의 연령대별 환자 수 (P07) | ✗ 여전히 날짜 뺄셈 | ✓ `AGE()` 사용, 완전히 맞음 |
  | 연령대 별 고혈압 환자 (P07) | ✗ 날짜 뺄셈 | ✓ |
  | 성별 고혈압 환자 수 (P07) | ✓ | ✓ |
  | 진단 연도별 제2형 당뇨병 환자 수 (신규) | ✓ | ✓ |
  | 성별·연령대별 심근경색 환자 수 (신규) | ✗ 날짜 뺄셈 | ✓ |
  | 80세 초과 고혈압 환자 목록 (회귀 확인) | ✗ 출생연도 차이 | ✗ 출생연도 차이 |

  - **문장 지시(변형 1)는 효과가 없었고, 예시 SQL(변형 2)은 효과가 있었다.** 파인튜닝 모델은 문장 지시보다 SQL 형태를 보여주는 쪽에 반응한다.
  - 학습 때 시스템 프롬프트가 늘 같은 짧은 문장이었고, 학습 데이터에 `AGE()`가 0건, `현재연도 - year_of_birth`가 37건이라
    시스템 프롬프트의 문장 지시가 학습된 습관을 이기지 못하는 것으로 보인다(추정).
  - 나이 조건 질의(회귀 확인)는 예시가 그 형태를 보여주지 않아 고쳐지지 않았다. 나이 조건 예시를 추가하는 것이 다음 시험 대상이다.
  - 예시 SQL로 인한 부작용(목록 질의가 집계로 바뀌는 등)은 이번 6개에서는 없었다.

### 5.4 (다음 버전) 평가 보강

결과의 행 수와 컬럼 형태를 검사하는 집계 문항을 새 평가셋에 넣는다.
이번처럼 "실행은 성공했지만 결과가 틀린" 경우는 실행 성공 여부만으로는 계속 놓친다.
